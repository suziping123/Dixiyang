## A1. 版本与运行时（L1）

**题目**：写出本项目的 Node、Python、Java 版本要求，并说明三者分别在哪个文件/脚本中体现。若本机 Node 是 18，会发生什么？

**参考答案**：

| 运行时 | 要求 | 出处 |
|---|---|---|
| Node | `^20.19.0 || >=22.12.0` | `dixiyang-vue/Dixiyang-vue3/package.json` 的 `engines` |

**解析**：考察"先看版本契约，再排错"。很多人一上来 `npm install` 报错就删 `node_modules`，根因其实是 Node 版本。

**评分**：三个版本各 1 分；出处 1 分；Node 18 的后果与正确处理 1 分。

**追问**：`package.json` 的 `engines` 默认会阻止安装吗？→ 不会，除非 `.npmrc` 设置 `engine-strict=true` 或使用 pnpm/yarn 的严格模式。

## A2. npm 脚本与构建闸门（L2）

**题目**：解释以下脚本的实际行为，并回答"`dist/` 已生成，能否说明构建成功"：

```json
"dev": "vite",
"build": "run-p type-check \"build-only {@}\" --",
"build-only": "vite build",
"type-check": "vue-tsc --build",
"lint": "run-s lint:*"
```

**参考答案**：

- `dev`：Vite 开发服务器，默认 5173，`/api` 代理到 8084。
- `build`：`run-p` **并行**跑 `type-check` 和 `build-only`；`run-p` 会聚合退出码。
- `build-only`：只做 Vite 打包，**不做类型检查**。
- `type-check`：`vue-tsc` 项目引用构建检查。
- `lint`：`run-s` **串行**跑 `lint:oxlint` 和 `lint:eslint`，两者都带 `--fix`。

`dist/` 存在不能说明构建成功：`vite build` 可能在 `vue-tsc` 报错的同时已经产出 `dist/`；必须以 `npm run build` 的**退出码**为准。

**验证**：

```bash
npm run type-check; echo "type-check=$?"
npm run build; echo "build=$?"
```

**解析**：CI 误判的高频原因。`run-p` 的退出码是聚合的，但人眼只看 `dist` 就会漏。

**评分**：每个脚本 0.5 分；`run-p/run-s` 0.5；dist 与退出码 1；验证命令 1。

**追问**：为什么 `lint` 用 `run-s` 而不是 `run-p`？→ 两个 lint 都可能改文件，串行避免互相覆盖/缓存不一致。

**参考答案**：

```bash
curl -s -X POST http://localhost:5173/api/auth/login \
  -H 'Content-Type: application/json' \
```

**解析**：这是项目明确的规范（`docs/开发环境与测试账号.md`）。评测岗必须用真实账号，否则复现结论不可信。

**追问**：登录风控有哪些限制？→ 10 分钟内第 3 次密码登录起要邮箱验证码；单点登录后登录会顶掉先登录。

## A7. 401 / 403 / 422 的区别（L2）

**题目**：解释 401、403、422 的语义；在本项目中各举一个可能场景。为什么"接口返回 200 但 code=500"不能当成功？

**参考答案**：

| 码 | 语义 | 项目场景 |
|---|---|---|
| 401 | 未认证/凭证失效 | token 过期、被顶号、没带 Authorization |
| 403 | 已认证但无权限 | 普通用户 token 打 `/api/admin/*`；访问他人资源 |
| 422 | 参数校验失败（FastAPI 默认） | 缺 query 参数、类型不符、body 字段错误 |

"HTTP 200 + code=500"是项目的业务错误约定（`Result.error`）。传输层成功不代表业务成功；调用方必须检查 `code`，否则会把失败当成功数据，出现空指针/静默失败。

**解析**：评测中大量"假成功"来自只看 HTTP 状态。要能区分传输层与业务层。

**评分**：三个码各 1；项目场景 1；200+500 的解释 1。

**追问**：FastAPI 缺 Authorization 时返回 401 还是 422？→ 取决于依赖实现；本项目 `auth_deps.py` 用 `HTTPBearer` 时缺头可能返回 422，这是需要统一的契约问题。

## A8. CORS 与 Vite 代理（L2）

**题目**：前端 5173 请求 8084，为什么开发环境通常不配 CORS 也能通？如果直连 8085 报 CORS，如何排查？

**参考答案**：

- `vite.config.ts` 配置了 `server.proxy['/api'] -> http://localhost:8084`；浏览器请求同源 `http://localhost:5173/api/...`，由 Vite 服务端转发，不触发浏览器跨域。
- 直连 8085 时，请求源是 5173、目标是 8085，属于跨域；需要在 8085 配 `CORSMiddleware`，或同样走 Vite 代理。
- 排查：DevTools Network 看请求 URL 是 5173 还是 8085；看响应有没有 `Access-Control-Allow-Origin`；`curl -i -X OPTIONS` 看预检。

**解析**：CORS 是浏览器行为，不是后端"坏了"。开发环境优先同源代理，生产再收敛 allow_origins。

**评分**：代理机制 2；CORS 触发条件 2；排查步骤 1。

**追问**：`allow_origins=["*"]` + `allow_credentials=True` 可以吗？→ 浏览器规范不允许，凭证请求不能配通配源；应显式列域名。

## A10. revert / reset / cherry-pick（L2）

**题目**：解释 `git revert`、`git reset --hard`、`git cherry-pick` 的区别与使用场景。已推送到共享分支的提交，应该用哪个撤销？

**参考答案**：

| 命令 | 行为 | 场景 |
|---|---|---|
| `git revert <sha>` | 生成一个反向提交，保留历史 | 已推送的共享分支撤销 |
| `git reset --hard <sha>` | 移动分支指针、丢弃工作区/索引 | 本地未推送，彻底回退 |
| `git cherry-pick <sha>` | 把某个提交应用到当前分支 | 挑修复到 release/评测分支 |

共享分支用 `revert`；`reset --hard` 会改写历史，别人拉取会冲突/丢提交。

**解析**：评测工作经常要在 `main` 和 `exam` 分支之间挑补丁； cherry-pick 比重做更可追溯。

**评分**：三个命令各 1；共享分支选择 1；风险说明 1。

**追问**：`revert` 一个 merge commit 为什么要 `-m`？→ 需要指定以哪个父提交为基线。

## A13. Python 依赖：uv / pip / requirements / pyproject（L2）

**题目**：本项目 `DixyangFast` 同时有 `pyproject.toml` 和 `requirements.txt`，且 `start_backend.sh` 用 `uv run`。说明三者关系与潜在风险；若要保证可复现，应该以哪个为准？

**参考答案**：

- `pyproject.toml`：项目元数据 + 依赖范围（如 `langchain-openai>=1.3`）。
- `requirements.txt`：固定版本清单（如 `langchain-openai==0.2.6`）。
- `uv run`：按 `pyproject.toml`/`uv.lock` 建环境并运行；若没有 lock，解析结果可能随索引变化。
- 风险：两份清单版本不一致，`pip install -r` 与 `uv run` 得到不同运行时，RAG/工具调用行为可能不同。
- 可复现：以 `uv.lock`（或统一的 lockfile）为准；CI 用 `uv sync --frozen`；`requirements.txt` 只作为导出产物。

**解析**：评测环境必须可复现，依赖漂移会制造"假 bug"。

**评分**：三者职责 2；版本漂移风险 2；lock/ frozen 方案 1。

**追问**：`uv run` 第一次执行会自动装依赖吗？→ 会按项目配置同步环境；生产/CI 建议 `uv sync --frozen` 显式执行。

**追问**：HAR 里怎么证明请求是 mock 的？→ 看 `remoteAddress`/无网络耗时、响应体与 demo 固定数据一致、Console 有 `[demo]` 日志。

## A18. 权限与进程管理（L2）

**题目**：`start_backend.sh` 报 `Permission denied`、`mvnw` 报 `Permission denied`，分别怎么处理？结束进程时 `kill` 与 `kill -9` 的区别？

**参考答案**：

```bash
chmod +x start_backend.sh
chmod +x dixiyang-engine/mvnw
# 若属主不对
sudo chown "$USER" start_backend.sh
```

`kill` 默认 `SIGTERM`，进程可捕获并优雅退出（关连接、落盘）；`kill -9` 是 `SIGKILL`，不可捕获，可能丢数据/留半截文件。优先 `SIGTERM`，等待后仍不退再 `-9`。

**解析**：评测中经常需要重启服务；优雅退出能避免"重启后数据损坏"的假 bug。

**评分**：chmod 1；chown 1；SIGTERM/SIGKILL 2；等待策略 1。

**追问**：`pkill -f chroma` 有什么风险？→ 可能误杀其他项目的 Chroma；应匹配更精确的启动命令/端口/PID 文件。

## A19. 编码、换行与时区（L3）

**题目**：Windows 上启动脚本报 `bad interpreter: /bin/bash^M`，原因是什么？如何修复？另外，聊天时间显示比本地少 8 小时，可能是什么问题？

**参考答案**：

- `^M` 是 CRLF 换行。Windows 编辑/检出把 LF 变成 CRLF，Linux 的 shebang 解析失败。
- 修复：

```bash
file start_backend.sh
sed -i 's/\r$//' start_backend.sh
# 或 dos2unix start_backend.sh
```

长期：`.gitattributes` 设 `*.sh text eol=lf`。

- 时间少 8 小时：后端存的是 UTC/无时区本地时间，前端 `new Date()` 按本地时区解析；或 Java `LocalDateTime` 与 UTC 混用。要统一：后端存 ISO8601 带时区/UTC，前端按本地时区展示；不要用字符串直接比较。

**解析**：跨平台评测的高频坑。编码/换行/时区会制造"代码没 bug 但就是不对"的假象。

**评分**：CRLF 原因 1.5；修复 1.5；时区原因 1.5；统一方案 0.5。

**追问**：Python 读写文件不指定 `encoding` 会怎样？→ 使用平台默认编码；Windows 可能是 GBK，中文/emoji 会乱码或 `UnicodeDecodeError`。

## A20. 可复现环境清单（L3）

**题目**：你要把"知识库分页 bug"交给同事复现。列出一份可复现清单，至少 10 项，并说明每项为什么必要。

**参考答案**：

| # | 项 | 为什么 |
|---|---|---|
| 1 | commit/tag SHA | 代码一致 |
| 2 | Node/Python/JDK 版本 | 运行时行为不同 |
| 3 | lockfile（package-lock/uv.lock） | 依赖一致 |
| 4 | 启动命令与端口 | 避免 8084/8085 混淆 |
| 5 | 测试账号与权限 | 数据归属/可见性 |
| 6 | 数据快照（11 本小说/文档数） | 触发边界 |
| 7 | 构建模式（`VITE_DEMO=0/1`） | 排除 mock |
| 8 | 浏览器/版本/视口 | 前端差异 |
| 9 | 操作步骤 + 预期/实际 | 最小复现 |
| 10 | 证据（HAR/截图/日志/DB count） | 可核对 |
| 11 | 时区/语言/编码 | 时间/排序差异 |
| 12 | 后端配置（Chroma 路径、RAG 端口） | 检索是否可用 |

**解析**：评测岗的交付物不是"我复现了"，而是"别人能按你的清单复现"。

**评分**：10 项以上 3；每项理由合理 2。

**追问**：为什么数据快照比"你多建几条"更好？→ 数量/内容/ID 固定，边界可重复；否则"我这也是 11 条"可能字段不同。
