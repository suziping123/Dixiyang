## B1. 小说下拉只有 10 本（L1/L2）★高频

**题目**：RAG 助手页的小说选择器只显示 10 本，但数据库有 30 本。前端代码：

```ts
// RagAssistantView.vue:451
const res = await http.get('/novel/listall', { params: { page: 1, pageSize: 100 } })
```

后端：

```python
# DixyangFast/src/dixiyang/routers/novel.py:11
async def list_all(page: int = 1, page_size: int = 10, user_id=Depends(...)):
    return svc.list_all(user_id, page, page_size)
```

请给出根因、影响范围、最小修复，并说明为什么"把 100 改成 10"是错的。

**参考答案**：

- **现象**：接口 200，`records.length === 10`；前端以为取了 100。
- **根因**：查询参数命名不一致。FastAPI 声明的是 `page_size`（下划线），前端发的是 `pageSize`（驼峰）。FastAPI 对未声明的 query 参数**忽略**，`page_size` 取默认 10。
- **影响范围**：`RagAssistantView.vue:451`、`src/api/ideaApi.ts` 的 `getNovelOptions`（同样发 `pageSize`），以及任何从 Java 契约复制过来的调用。
- **为什么不能把 100 改成 10**：10 是后端默认值，不是契约；改成 10 只是让"看起来对"，其他调用仍会静默截断，且未来默认值变化会再次出错。
- **最小修复**：前端按 FastAPI 契约发 `page_size`；或在 `novelApi` 层统一做参数映射。**不要全局盲改**——Java 版 `NovelController` 用的是 `pageSize`，需要按后端分支/网关适配。
- **长期治理**：在 `src/api` 层定义唯一参数名；加一条契约测试（见验证）。

**验证**：

```bash
# 直接打后端，确认参数名
curl -s "http://localhost:8084/api/novel/listall?page=1&page_size=100" -H "Authorization: Bearer $TOKEN" | jq '.data | length'
curl -s "http://localhost:8084/api/novel/listall?page=1&pageSize=100"  -H "Authorization: Bearer $TOKEN" | jq '.data | length'
```

断言：前者 30（或全部），后者 10。前端修完后 Network 的 query string 必须是 `page_size=100`。

**解析**：这是"跨语言契约漂移"的典型。注意 `getNovelOptions` 返回 `{records}` 分页对象，不是数组，unwrapping 也要一起看（项目已有同类坑）。

**评分**：根因 2；影响范围 1；修复 1.5；验证 1.5。

**追问**：为什么知识库页没暴露？→ `RagKnowledgeView` 的 `pageSize` 恰好是 20，等于 `rag.py` 的 `page_size` 默认 20，被默认值掩盖；改页大小就会复发。

## B2. 业务 500 被当成功：知识库页静默空白（L2）★高频

**题目**：后端返回 `HTTP 200` + `{ code: 500, msg: "Chroma 连接失败", data: null }`，`RagKnowledgeView` 页面表格空白、Console 只有一条 `加载文档失败`。请解释完整链路，并给出调用方修复。

**材料**：

```ts
// src/utils/http.ts:50-56
if (res && typeof res === 'object' && res.code === 401) { ... }
return res   // code=500 也 resolve

// RagKnowledgeView.vue:195-206
const res = await getRagDocuments(...)
const data = res.data as RagDocPage
docs.value = (data.ids || []).map(...)
totalDocs.value = data.total ?? stats.value.total_documents ?? 0
```

**参考答案**：

- **链路**：axios 响应拦截器只对 `code===401` 特殊处理，其余对象**原样 resolve**（包括 `code=500`）。`RagKnowledgeView` 直接读 `res.data`；此时 `data === null`，`data.ids` 抛 `TypeError`，被 `catch` 吞掉，只 `console.error`，所以页面空白。
- **根因**：拦截器把"业务失败"降级成"调用方自行判断"，但调用方没有判断。这是**契约设计 + 调用方漏检**的共同问题，不是 Chroma 单点问题。
- **影响**：用户看到空表格/旧数据，误以为"没有文档"；评测时会被记成"功能缺失"，实际是错误被吞。
- **修复（调用方）**：

```ts
const res = await getRagDocuments(...)
if (!res || typeof res.code === 'number' && res.code !== 200) {
  ElMessage.error(res?.msg || '加载文档失败')
  docs.value = []
  return
}
const data = res.data
if (!data) { ... }
```

- **修复（基础设施，二选一）**：拦截器对 `code!==200` 统一 `ElMessage` + `reject`，但会改变大量调用方；更稳的是提供 `request<T>()` 包装，强制检查 code，逐步迁移。
- **不要**把 `data.ids || []` 改成可选链就算修完——那只掩盖错误，用户仍不知道失败。

**验证**：用 CDP/代理把 `/api/rag/documents` 响应改成 `{code:500,data:null}`；断言出现错误提示、表格不显示旧数据、Console 有业务错误。再恢复正常，断言表格恢复。

**解析**：这是评测岗最常抓的"静默失败"。要能区分 `HTTP 500` 与 `业务 code 500`；本项目两者都可能出现。

**评分**：链路 2；根因 1.5；影响 1；修复 1.5；验证 1。

**追问**：为什么 `getRagStats` 的失败也不明显？→ 同样只 `console.error`，`stats` 保持初始值，页面显示 0。

## B3. 快速切换会话，消息串台/旧流写入新会话（L3）★★

**题目**：用户正在 A 会话生成回答，点击 B 会话；随后 B 里出现 A 的半截回答，或者 B 的历史被 A 的旧请求覆盖。请从 `useChatStream.ts` 找出至少两条竞态路径，并给出统一修复方案。

**材料**：

```ts
// useChatStream.ts:66-100
const loadSessionMessages = async (sessionId: string) => {
  if (abortController) { abortController.abort(); abortController = null }
  currentContent.value = ''
  isStreaming.value = false
  currentSessionId.value = sessionId
  try {
    const res = await http.get(`/chatHistory/session/${sessionId}`)
    messages.value = (res.data ?? []).map(...)
  } catch { messages.value = [] }
}
```

```ts
// sendMessage catch（约 225-245 行）
} catch (error) {
  if ((error as Error).name === 'AbortError') {
    messages.value.push({ role: 'assistant', content: currentContent.value || '未生成回答内容', ... })
  }
  ...
}
```

**参考答案**：

**竞态 1：历史请求乱序。**

1. 点 A → `loadSessionMessages('A')` 发请求 A。
2. 点 B → `loadSessionMessages('B')` 发请求 B。
3. B 先返回，`messages = B`；A 后返回，`messages = A`。此时 `currentSessionId='B'`，界面却是 A 的历史。

**竞态 2：abort 后的 catch 写入新会话。**

1. A 流式中，`abortController` 指向 A 的 controller。
2. `loadSessionMessages('B')` 先 `abort()`，然后 `messages=[]`、`currentSessionId='B'`。
3. A 的 `sendMessage` catch 异步执行，`messages.value.push(assistant)`——push 进的是 B 的数组。B 里出现 A 的半截回答。

**竞态 3：`currentSessionId` 在请求前就被改写。** `sendMessage` 用 `currentSessionId.value` 发请求，但异步返回后没有校验"响应属于哪个会话"。

**统一修复**：

1. 为每次加载/发送生成 `requestSeq`（或 `sessionToken`），返回后只接受 `seq === latestSeq && sessionId === currentSessionId` 的结果。
2. `loadSessionMessages` 用局部 `const sid = sessionId`，返回后 `if (sid !== currentSessionId.value) return`。
3. `sendMessage` 捕获开始时 `const sid = currentSessionId.value`；catch/finally 里 `if (sid !== currentSessionId.value) return`，不要把部分内容 push 到新会话。
4. `abort()` 后不要立即清空共享的 `currentContent`；用局部 buffer，成功/失败时再决定是否提交。
5. 最好把"每条会话的流"封装成独立 controller + buffer，切换会话只取消旧流，不共享可变状态。

**验证**：DevTools Network 限速（Slow 3G）；A/B 快速切换 5 次；断言 `messages` 的会话 ID 与 `currentSessionId` 一致；A 的 AbortError 不产生 B 的气泡；用 Vue DevTools 看 `messages` 长度。

**解析**：这是 L3 题，考"共享可变状态 + 异步边界"。只加 `abort()` 不够，因为 abort 的 catch 仍会写状态。

**评分**：两条竞态各 2；统一修复 2；验证 1。

**追问**：`loadSessionMessages` 里 `abortController = null` 后，旧 `sendMessage` 的 `finally` 也会把 `abortController` 置空，会覆盖新流的 controller 吗？→ 会；必须用局部 controller + 身份校验，不能共享单例。

## B4. 中文输入法回车误发送（L1）★高频

**题目**：用户用拼音输入"你好"，按回车选词，消息被直接发送。定位并修复。

**材料**：

```vue
<!-- RagAssistantView.vue:231 -->
<textarea v-model="inputMessage" @keydown.enter="handleSend" ... />
```

```ts
const handleSend = (e: KeyboardEvent) => {
  if (e.key === 'Enter' && !e.shiftKey) {
    e.preventDefault()
    sendStreamMessage()
  }
}
```

**参考答案**：

- **根因**：没有判断输入法组合态。中文 IME 选词的回车也是 `keydown.Enter`，`isComposing` 为 `true`；代码只看 `shiftKey`。
- **修复**：

```ts
const handleSend = (e: KeyboardEvent) => {
  if (e.isComposing || e.keyCode === 229) return
  if (e.key === 'Enter' && !e.shiftKey) { e.preventDefault(); sendStreamMessage() }
}
```

- 也可用 `@compositionstart/@compositionend` 维护 `composing` 标志；`keyCode===229` 兼容旧浏览器。
- **验证**：Chrome + 中文拼音，输入 `nihao`，按回车选词；断言不发送、文本框保留；再按一次回车才发送。

**解析**：这是中文 Web 应用的必测项。评测时要在"输入法组合态"下真实按键，不能只用英文。

**评分**：根因 2；修复 2；验证 1。

**追问**：`@keyup.enter` 能避免吗？→ 不一定；组合态结束的 keyup 也可能触发，仍要 `isComposing`。

## B5. 时间轴角色名被拆成单字（L1）

**题目**：后端返回 `characterNames: "江末,林晚"`（JSON 字符串），时间轴卡片显示"江 / 末 / , / 林 / 晚"五个标签。定位并修复。

**材料**：

```vue
<!-- TimelineView.vue:103-104 -->
<div v-if="node.characterNames?.length" class="detail-chars">
  <span v-for="c in node.characterNames" :key="c" class="detail-char">{{ c }}</span>
</div>
```

```ts
// 同文件 247-251 已有解析函数
const parseJsonField = (v: any): string[] => {
  if (Array.isArray(v)) return v
  if (typeof v === 'string' && v) { try { const p = JSON.parse(v); return Array.isArray(p) ? p : [] } catch { return [] } }
  return []
}
```

**参考答案**：

- **根因**：模板对字符串直接 `v-for`，Vue 把字符串当可迭代对象，逐字符渲染；而筛选逻辑用的是 `parseJsonField`，所以出现"筛选对、显示错"。
- **修复**：模板改用 `v-for="c in parseJsonField(node.characterNames)"`；或在 `refreshNodes` 映射时统一 `characterNames: parseJsonField(n.characterNames)`，模板只处理数组。
- **注意**：`tags` 同样可能是 JSON 字符串，检查是否也逐字渲染。
- **验证**：造一条 `characterNames: "[\"江末\",\"林晚\"]"` 和一条 `"江末,林晚"`，断言都显示两个标签；筛选"江末"仍命中。

**解析**：这是"数据层已修、展示层漏改"的典型。`parseJsonField` 的存在说明作者知道格式不统一，但只用在 computed。

**评分**：根因 2；修复 2；验证 1。

**追问**：为什么 `v-if="node.characterNames?.length"` 对空字符串不显示，但对 `"[]"` 会显示？→ `"[]".length === 2`，为真，然后渲染 `[`、`]` 两个字符。

## B6. 快速切换章节，正文串章（L3）

**题目**：在小说编辑器里快速点击章节 A、B，最终编辑区显示 A 的正文，但面包屑是 B。请定位并给出修复。

**材料**：

```ts
// NovelEditorView.vue:235-256
async function openChapter(ch: Chapter) {
  if (currentChapter.value?.id === ch.id) return
  await draft.flushSave()
  currentChapter.value = ch
  title.value = ch.title
  ...
  const res = await getChapterContent(ch.id)
  ...
  const loaded = await draft.loadDraft(novelId, ch.id, cloudContent, ...)
  content.value = loaded.content
  ...
}
```

**参考答案**：

- **根因**：`openChapter` 没有请求序号/取消。A 的 `getChapterContent`/`loadDraft` 较慢，B 先完成并把 `currentChapter` 设为 B；A 后完成，仍然无条件 `content.value = loaded.content`，并把 `syncCtx` 覆盖成 A。结果：面包屑 B、正文 A、自动保存上下文 A。
- **影响**：跨章内容污染，自动保存可能把 A 的内容写到 B 的草稿/服务端；属于数据正确性问题，P1 起。
- **修复**：

```ts
let openSeq = 0
async function openChapter(ch: Chapter) {
  if (currentChapter.value?.id === ch.id) return
  const seq = ++openSeq
  await draft.flushSave()
  if (seq !== openSeq) return
  currentChapter.value = ch
  ...
  const res = await getChapterContent(ch.id)
  if (seq !== openSeq) return
  const loaded = await draft.loadDraft(...)
  if (seq !== openSeq) return
  content.value = loaded.content
}
```

- 更彻底：`AbortController` 取消旧请求；`useChapterDraft` 的 `syncCtx` 由调用方在提交时校验 chapterId。
- **验证**：Network 限速；A/B 快速切换；断言 `currentChapter.id === B` 时 `content` 来自 B；看 IndexedDB `drafts` 的 `chapterId` 与内容一致；再快速切回 A。

**解析**：和 B3 同构：共享可变状态 + 异步返回无身份校验。区别是这里会造成数据写入错误。

**评分**：根因 2；影响 1；修复 2；验证 1。

**追问**：只比较 `ch.id === currentChapter.value?.id` 再赋值够吗？→ 不够；`currentChapter` 可能已被别的路径改了，必须比较本次请求的 seq。

## B7. 灵感流触底无限递归（L3）

**题目**：接口失败时，灵感流会瞬间发出大量请求甚至栈溢出。定位。

**材料**：

```ts
// IdeaLibraryView.vue:365-390
try {
  const data = unwrap<IdeaPostFeed>(await listPosts(params))
  ...
} finally {
  flag.value = false
  if (sentinelVisible() && feedHasMore.value) await loadFeed('more')
}
```

**参考答案**：

- **根因**：`finally` 无条件执行递归；`listPosts` 抛错时没有把 `feedHasMore` 置 false，`sentinelVisible()` 仍为 true，`loadFeed('more')` 再次进入，失败再递归。`loadingMore` 在 `finally` 里已置 false，挡不住下一次。
- **触发条件**：首屏内容不足一屏（sentinel 在视口内）+ 接口持续失败 + `feedHasMore` 初始为 true。
- **影响**：请求风暴、浏览器卡死、后端被打；评测中会被记为 P1 稳定性问题。
- **修复**：

```ts
try {
  ...
} catch (e) {
  feedHasMore.value = false
  ElMessage.error('加载失败')
} finally {
  flag.value = false
  if (sentinelVisible() && feedHasMore.value) {
    // 用微任务/下一帧，并加"本轮已补"标志，避免同步递归
    queueMicrotask(() => loadFeed('more'))
  }
}
```

- 更稳：用 `while` 循环 + `maxAutoFill`（如 3 次）+ 失败即停；不要用递归。
- **验证**：DevTools 把 `listPosts` 置为 500；断言只发 1 次请求、出现错误提示、`feedHasMore=false`；恢复后手动触底只发 1 次。

**解析**：`finally` 里做副作用很危险；递归 + 失败无终止条件是经典组合。

**评分**：根因 2；触发条件 1；修复 2；验证 1。

**追问**：为什么 `loadingMore` 防不住？→ 递归发生在 `finally` 里，此时 `flag=false` 已执行，守卫失效。

## B8. 便签乐观更新失败后不回滚（L2）

**题目**：断网时拖动便签，UI 停在新位置；刷新后回到旧位置。请判断这是不是 bug，并给出修复或说明设计取舍。

**材料**：

```ts
// stickyStore.ts:74-102
notes.value[idx] = { ...prev, ...optimistic }
try {
  const res = await updateNote(id, body)
  if (data) notes.value[i2] = data

  /* 保存失败：保留乐观值，用户下次操作覆盖（便签不做强一致） */
```

**参考答案**：

**解析**：考"注释与实现不一致"和"乐观更新的失败路径"。不要只看到 `catch` 就以为处理了。

**评分**：判断 1；根因 2；修复 1.5；验证 1.5。

**追问**：如果产品明确"便签不做强一致"，这题怎么答？→ 仍要指出 `loaded` 阻止重拉，至少修成可重试；并在文档写明取舍，不能把 bug 说成设计。

## B9. 删除小说：业务失败仍从列表移除（L2）

**题目**：后端返回 `{ code: 500, msg: "小说不存在" }`，前端列表仍然把这张卡片删掉。定位。

**材料**：

```ts
// HomeView.vue:323-341
await http.post(`/novel/delete/${novel.id}`)
novels.value = novels.value.filter(n => n.id !== novel.id)
...
} catch {
  // 取消确认或请求失败（失败时列表未动，保持原状）
}
```

**参考答案**：

- **根因**：`http` 拦截器对业务 `code=500` 也 resolve，`await` 不会抛；代码没有检查 `code`，直接过滤列表。`catch` 只覆盖网络异常/取消，不覆盖业务失败。
- **影响**：用户以为删除成功，刷新后小说又出现；如果后端实际删了但返回异常，则前端与后端状态不一致。
- **修复**：

```ts
const res = await http.post(`/novel/delete/${novel.id}`) as { code?: number; msg?: string }
if (res?.code !== 200) {
  ElMessage.error(res?.msg || '删除失败')
  return
}
novels.value = novels.value.filter(...)
await realignList()
```

**评分**：根因 2；影响 1；修复 2；验证 1。

## B10. 后台 403 被当登录失效（L2，易误判）

**题目**：管理员已登录，访问一个无权限的接口返回 403，后台直接退出登录。这是 bug 还是设计？请给出判断依据和改进。

**材料**：

```ts
// src/admin/api/http.ts:58-62
if (status === 401 || status === 403) {
  handleAdminAuthFail(extractMessage(error.response?.data))
  return Promise.reject(new Error('后台登录态已失效'))
}
```

**参考答案**：

- **是缺陷（P2）**：401 = 未认证/会话失效，403 = 已认证但无权限。把 403 当 401 会清掉有效会话，用户被"误踢"。
- **为什么作者这样写**：注释说"403=非后台令牌/权限不足"；如果后台接口用同一个 JWT，普通用户 token 打后台接口会 403，此时回登录页是合理的。但管理员 token 访问自己无权限的资源也 403，无法区分。
- **改进**：
  1. 后端对"非后台令牌"返回 401/专用错误码；对"后台令牌但权限不足"返回 403 + `code`。
  2. 前端只有 401（或 `code=401`）清会话；403 提示"无权限"，保留登录态。
  3. 若短期无法改后端，至少判断响应 `code/msg`，不要所有 403 都登出。
- **验证**：管理员登录 → 调一个 403 接口 → 断言仍在后台、出现"无权限"；token 过期/被顶号 → 401 → 断言回登录页。

**解析**：这是"易误判"题：看代码像故意设计，但语义上 403≠401。要能说出"在什么前提下可接受"。

**评分**：判断 1；语义 2；改进 2；验证 1。

**追问**：用户端 `http.ts` 会把 403 登出吗？→ 不会，只处理 401；这是两端不一致，也要指出。

## B12. `v-html` 渲染 Markdown 是 XSS 吗（L2，易误判）

**题目**：`ChatMessage.vue` 用 `v-html="renderMarkdown(...)"` 渲染 AI 输出。请审计是否 XSS，并指出剩余风险。

**追问**：`DOMPurify.sanitize` 能防 Markdown 里的 `data:` URL 吗？→ 默认会处理危险协议，但 `data:image` 等要按版本/配置确认；不要假设。

## B13. ECharts 组件是否内存泄漏（L1，易误判）

**题目**：`EChart.vue` 在 `onMounted` 里 `echarts.init`，有人报"切换页面后图表实例未销毁"。请审计。

**材料**：

**参考答案**：

**解析**：另一个"看起来像 bug"的题。要能说出"在 keep-alive 下才可能有问题"，而不是直接判泄漏。

**评分**：结论 2；证据 2；keep-alive 边界 1；验证 1。

**追问**：`echarts.init` 重复调用会怎样？→ 同一 DOM 上重复 init 会警告并返回已有实例/创建失败；本项目 `onMounted` 只一次，安全。

## B15. SSE 解析器的 4 个隐患（L3）

**题目**：`useChatStream` 里 `sendMessage` 和 `regenerateMessage` 各有一份 SSE 解析。请指出至少 4 个问题，并给出抽公共函数的方案。

**材料**：

```ts
buffer += decoder.decode(value, { stream: true })
const parts = buffer.split('\n')
buffer = parts.pop() ?? ''
for (const line of parts) {
  if (!line.startsWith('data:')) continue
  const jsonStr = line[5] === ' ' ? line.slice(6) : line.slice(5)
  const data = JSON.parse(jsonStr)
  if (data.type === 'done') { ... }   // 没有 break
}
```

**参考答案**：

1. **重复实现**：两份几乎相同的解析，修一处漏一处；应抽 `consumeSSE(response, handlers)`。
2. **没有 flush 尾缓冲**：流结束时 `buffer` 里可能还有最后一行（服务端最后一条不带 `\n`），直接丢弃；应在 `done` 后 `decoder.decode()` + 处理 `buffer`。
3. **`done` 不 break**：收到 `done` 后仍继续 `reader.read()`，若服务端不立即关闭连接，UI 会卡在"流式中"；应 `break` 并 `reader.cancel()`。
4. **异常处理不一致**：`sendMessage` 对 `SyntaxError` `continue`，`regenerate` 直接 `JSON.parse` 抛；同一协议两种行为。
5. **只按 `\n` 切**：SSE 规范允许 `\r\n`；当前 `data:` 行尾可能带 `\r`，`JSON.parse` 失败（被 `SyntaxError` 吞掉）。
6. **多行 data**：SSE 的 `data:` 可多行拼接；当前逐行 parse，遇到多行 JSON 会失败。
7. **没有 `reader.cancel()`**：组件卸载/切会话时只 abort fetch，reader 可能仍持有流；应在 finally 取消。
8. **`rag_references` 直接 push**：重复重连/重放会重复引用；应按 `source+title+content` 去重。

**修复方案**：

```ts
async function consumeSSE(res: Response, onEvent: (e: any) => void) {
  const reader = res.body!.getReader()
  const decoder = new TextDecoder()
  let buf = ''
  try {
    while (true) {
      const { done, value } = await reader.read()
      if (done) break
      buf += decoder.decode(value, { stream: true })
      let idx
      while ((idx = buf.indexOf('\n')) >= 0) {
        const line = buf.slice(0, idx).replace(/\r$/, '')
        buf = buf.slice(idx + 1)
        if (!line.startsWith('data:')) continue
        const payload = line.slice(5).trimStart()
        if (!payload) continue
        const evt = JSON.parse(payload)
        onEvent(evt)
        if (evt.type === 'done') { await reader.cancel(); return }
      }
    }
    buf += decoder.decode()
    if (buf.trim()) { /* 处理尾行 */ }
  } finally {
    reader.releaseLock?.()
  }
}
```

**验证**：mock 一个流：最后一条 `data:{"type":"content","delta":"尾"}` 不带换行；断言尾字显示；收到 `done` 后连接不关闭，断言 1s 内退出流式态；发 `\r\n` 行，断言不报错。

**解析**：SSE 是 Agent 评测的高频载体；解析器的鲁棒性直接影响"回答丢字/卡死"。

**评分**：4 个问题各 1；公共函数 1；验证 1。

**追问**：为什么 `TextDecoder({stream:true})` 还要在结束时再 `decode()`？→ 处理跨 chunk 的多字节字符尾字节。

## B18. 流式回答变长时不自动滚动（L2，体验）

**题目**：AI 流式输出到屏幕底部后继续增长，用户看不到新内容，必须手动滚动。定位并给出修复。

**材料**：

```ts
// RagAssistantView.vue:495/505
await sendMessage(...)

```

```ts
const scrollToBottom = () => {
```

**评分**：根因 2；修复 2；边界（用户上翻）1；验证 1。

**追问**：为什么 `nextTick` 后立刻 `scrollTop=scrollHeight` 仍可能不准？→ 图片/代码高亮/字体加载会二次改变高度；需要 ResizeObserver 或 `requestAnimationFrame`。
