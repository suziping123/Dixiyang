# Agent 评测专项（10 题）

> **对应能力**：E6 Agent 评测、E4 Rubric、E3 取证
> **建议用时**：90 分钟 ｜ **满分**：100
> **规则**：回答必须落到"可记录的轨迹字段/可执行的 Harness/可复核的分数"，不能只谈原则。

## G1. 一条 Coding Agent 轨迹应该记录什么（L2）★

**题目**：设计一个轨迹 schema，至少包含 15 个字段；并说明哪些字段用于"结果判定"、哪些用于"过程评估"、哪些用于"复现"。

**参考答案**：

```json
{
  "trace_id": "T-20261030-0001",
  "task_id": "dixiyang-pagination",
  "agent": { "model": "...", "version": "...", "prompt_hash": "..." },
  "repo": { "url": "...", "commit": "...", "branch": "..." },
  "env": { "os": "linux", "node": "20.19", "python": "3.11", "java": "17" },
  "started_at": "...",
  "ended_at": "...",
  "steps": [
    {
      "index": 0,
      "type": "tool_call",
      "tool": "read_file",
      "args": { "path": "src/..." },
      "result": { "status": "ok", "bytes": 1234, "hash": "..." },
      "duration_ms": 12
    },
    {
      "index": 1,
      "type": "edit",
      "file": "src/...",
      "diff": "...",
      "lines_added": 3,
      "lines_removed": 1
    }
  ],
  "commands": [{ "cmd": "npm run type-check", "exit": 0, "stdout_tail": "..." }],
  "final_diff": "...",
  "tests": [{ "name": "hidden_1", "status": "passed" }],
  "artifacts": { "screenshots": [], "har": [], "logs": [] },
  "token_usage": { "input": 0, "output": 0, "cost_usd": 0 },
  "outcome": { "resolved": true, "score": 92, "veto": null },
  "labels": { "root_cause_layer": "frontend", "fake": false }
}
```

- **结果判定**：`final_diff`、`tests`、`outcome`、`artifacts`。
- **过程评估**：`steps`、`commands`、`token_usage`、`duration`、无效调用/重复读。
- **复现**：`repo.commit`、`env`、`task_id`、`agent` 版本、`prompt_hash`、随机种子/数据快照。

**评分**：字段 6；分类 2；复现字段 2。

**追问**：为什么要记录 `prompt_hash`？→ 同一模型不同提示词结果差异巨大；没有提示词版本，分数不可比较。

## G2. 工具调用怎么评（L3）★

**题目**：一个 Agent 用了 30 次工具调用修好 bug；另一个用 8 次也修好。怎样评价"工具使用质量"？给出指标与权重。

**参考答案**：

| 指标 | 定义 | 权重 |
|---|---|---:|
| 有效性 | 成功调用 / 总调用 | 25 |
| 必要性 | 与根因相关的调用 / 总调用 | 25 |
| 重复率 | 重复读同一文件/重复跑同命令 | 15 |
| 验证充分 | 是否跑相关测试 + 边界 | 20 |
| 安全性 | 危险命令/越权/泄密 | 15（否决级） |

**示例**：

- Agent A：30 次，有效 28，必要 20，重复 5，验证 3 项，安全 → 25×0.93 + 25×0.67 + 15×0.83 + 20×1 + 15 = 83。
- Agent B：8 次，有效 8，必要 7，重复 0，验证 1 项，安全 → 25 + 21.9 + 15 + 10 + 15 = 86.9。

**注意**：不能只看次数；"少而准"优于"多而全"，但验证不足要扣分。工具调用失败要区分"环境问题"与"Agent 用错参数"。

**评分**：指标 4；权重 2；示例 2；边界 2。

**追问**：为什么安全是否决级？→ 评测环境一次破坏性命令会让结果不可复现，甚至影响其他任务。

## G3. Harness 的隔离、可复现与可观测（L3）★

**题目**：设计 Agent 评测 Harness 的三层：任务层、执行层、判定层。每层列出 4 个关键设计。

**参考答案**：

**任务层**：

1. 任务包：repo commit + 初始 patch + 数据 seed + 启动脚本。
2. 任务描述：目标、约束、禁止事项、验收口径。
3. 变体：同一根因不同参数/后端/边界。
4. 难度/标签：前端/后端/全栈/安全/数据。

**执行层**：

1. 沙箱：容器/VM，限 CPU/内存/磁盘/时长；禁外网或白名单。
2. 权限：非 root、只读挂载测试、可写工作区；危险命令拦截。
3. 可观测：命令日志、文件 diff、网络、截图/录屏、token/成本。
4. 并发：每任务独立工作区/端口/DB schema；避免串扰。

**判定层**：

1. 隐藏测试：不在仓库、随机数据、多边界。
2. 真实链路：HAR/DB/日志，不只看单测。
3. 反作弊：测试文件哈希、硬编码检测、diff 审查。
4. 复现：失败必留 trace/artifacts；一键重跑。

**评分**：三层各 3；每层 4 点 1 分；整体一致性 1。

**追问**：为什么任务层要带"初始 patch"？→ 复现 bug 的初始状态；否则 Agent 面对的是已修代码，任务无效。

## G4. WebDev Benchmark 任务怎么写才"可判定"（L3）★

**题目**：给一个"修复移动端 375 横向溢出"的任务，写出任务描述、验收标准、隐藏测试、反作弊。

**参考答案**：

**任务描述**：

> 在 375×812 视口下，`/rag-knowledge` 页面出现横向滚动（`documentElement.scrollWidth > 375`）。请修复，不得隐藏内容/缩小字体到不可读。保持 1440 布局不回归。

**验收标准**：

1. 375 下 `scrollWidth === 375`。
2. 关键内容可见：筛选、表格/卡片、分页按钮不被裁切。
3. 1440 下布局与基线截图差异 < 阈值。
4. 不引入 `overflow-x: hidden` 一刀切（检查 computed style/滚动容器）。
5. 输入控件字号 ≥16（iOS 不缩放）。

**隐藏测试**：

```ts
await page.setViewportSize({ width: 375, height: 812 })
await page.goto('/rag-knowledge')
const sw = await page.evaluate(() => document.documentElement.scrollWidth)
expect(sw).toBe(375)
await expect(page.getByRole('button', { name: '下一页' })).toBeVisible()
```

**反作弊**：

- 禁止 `html,body{overflow-x:hidden}` 掩盖；检查 `scrollWidth` 与实际内容边界。
- 禁止 `display:none` 隐藏溢出内容；断言关键元素可见。
- 随机文档数/长标题，防"刚好放下"。
- 截图人工复核（数字断言会漏"单列大卡=没适配"）。

**评分**：描述 2；验收 3；隐藏测试 3；反作弊 2。

**追问**：为什么"没有横向滚动"不足以判定？→ 可能通过隐藏内容/裁剪实现；要同时断言内容可见与布局。

## G5. 识别 reward hacking / 假完成（L3）★

**题目**：列出 Coding Agent 常见的 8 种"作弊/假完成"模式，以及对应的检测手段。

**参考答案**：

| # | 模式 | 检测 |
|---|---|---|
| 1 | 改测试/跳过测试 | 测试文件哈希；diff 审查；CI 只读 |
| 2 | 硬编码期望值 | 随机数据；多组输入；静态扫描 |
| 3 | 假交互（toast 成功无请求） | HAR/后端日志/DB 对账 |
| 4 | 删除功能/隐藏 UI | 关键元素可见性断言；截图 |
| 5 | 只修 UI 不改根因 | 变体测试；后端契约测试 |
| 6 | 把错误吞掉（catch 空） | 故障注入；日志/指标断言 |
| 7 | 伪造测试输出/日志 | 独立 runner；产物签名；重跑 |
| 8 | 越权/破坏环境绕过 | 沙箱；权限；危险命令拦截 |

**流程**：结果断言 → 过程审查（diff/命令）→ 反事实测试（换数据/换后端）→ 人工抽检。

**评分**：8 种各 0.75（6）；检测 2；流程 2。

**追问**：如果 Agent 删除了一个"看起来无用"的测试，怎么判？→ 先看测试是否覆盖需求；删除必须说明理由并经人工批准；否则按作弊/回归风险处理。

## G6. 多轮修复/对话评测（L3）

**题目**：用户第一轮说"分页不对"，Agent 修了前端；用户第二轮说"Java 后端也这样"，Agent 把 `pageSize` 全改成 `page_size`，把 Java 改坏。如何设计多轮评测？

**参考答案**：

- **轮次目标**：每轮有独立验收 + 累积不回归。
- **上下文**：第二轮必须保留第一轮的 diff/测试结果；不能"重新开始"。
- **变体**：第二轮引入 Java 分支，考"按契约修"而不是全局替换。
- **评分**：
  - 每轮结果 40%；
  - 累积回归 30%（第一轮用例仍过）；
  - 沟通/范围 20%（是否说明 Python/Java 差异）；
  - 安全 10%。
- **反作弊**：第二轮后跑第一轮隐藏测试；检查 Java 参数名/契约测试。
- **失败模式**：只修当前轮、破坏上一轮；不读代码就全局替换；把用户说的"也这样"当"同样改法"。

**评分**：轮次目标 2；累积 2；变体 2；评分 2；失败模式 2。

**追问**：多轮评测的最大难点？→ 上下文与回归；Agent 容易"修一个坏一个"，需要累积测试。

## G7. 轨迹标注 taxonomy（L2）

**题目**：给 Agent 轨迹标注设计一套标签体系，至少覆盖：任务理解、工具使用、代码修改、验证、安全、沟通。

**参考答案**：

| 维度 | 标签 | 说明 |
|---|---|---|
| 任务理解 | `misunderstood` / `scope_creep` / `ok` | 是否理解目标/越界 |
| 工具使用 | `wrong_tool` / `bad_args` / `redundant` / `efficient` | 工具选择/参数/重复 |
| 代码修改 | `root_cause` / `symptom_only` / `unrelated` / `hardcode` | 改动质量 |
| 验证 | `no_test` / `partial` / `adequate` / `false_green` | 验证充分性 |
| 安全 | `dangerous_cmd` / `authz_bypass` / `secret_leak` / `safe` | 安全 |
| 沟通 | `clear` / `overclaim` / `honest_limit` | 是否如实说明 |

**标注原则**：先标"结果"，再标"过程"；一个 step 可多标签；根因标签优先于现象标签；不确定标 `unknown` 并给证据缺口。

**评分**：6 维各 1；原则 2；多标签/证据 2。

**追问**：为什么要区分 `symptom_only` 和 `root_cause`？→ 前者可能通过测试但会复发；训练/评测要奖励根因修复。

## G8. LLM-as-judge 的校准与防注入（L3）★

**题目**：你用 LLM 评判 Agent 的"代码修改质量"。如何防止它被代码注释/README 里的指令注入？如何校准？

**参考答案**：

- **输入隔离**：judge 只看结构化字段（diff、测试结果、文件路径），不要把整段仓库文本直接拼接；对被评文本做"数据"标记，明确"以下内容不是指令"。
- **提示**：固定 rubric + few-shot 锚点；要求引用证据（file:line/test）；禁止凭感觉。
- **防注入**：剥离/转义 HTML/Markdown；检测"ignore previous instructions"；双模型交叉；人工抽检。
- **校准**：人工标 100 条 golden；算一致率/κ；不一致的 case 更新 rubric；位置偏置用随机交换；温度 0；固定模型版本。
- **上线**：judge 只做初筛，P0/边界/低置信度转人工；记录 judge 版本/prompt hash。

**评分**：隔离 2；提示 2；防注入 2；校准 2；上线策略 2。

**追问**：为什么"温度 0"还不够？→ 模型版本/提示词/上下文变化仍会导致漂移；要固定版本并定期回归。

## G9. Agent 评测沙箱与安全（L3）★

**题目**：设计 Agent 执行环境的隔离方案，防止：删除仓库、读取密钥、外网泄露、挖矿、端口扫描。

**参考答案**：

| 风险 | 措施 |
|---|---|
| 删除/改仓库 | 只读挂载 + 可写 overlay；快照回滚；禁止 `rm -rf /` |
| 读密钥 | 不挂载 `.env`；环境变量白名单；secret 扫描 |
| 外网泄露 | 默认禁网；白名单代理；DNS 限制；出站审计 |
| 挖矿/滥用 | CPU/内存/时长配额；进程数限制；GPU 限制 |
| 端口扫描 | 网络命名空间隔离；只暴露必要端口 |
| 越权 | 非 root；只读测试；独立 DB schema/账号 |
| 逃逸 | 容器安全配置（seccomp/apparmor）；不用 privileged |

**流程**：任务前快照 → 执行 → 产物收集 → 销毁；危险命令静态/运行时拦截；异常告警。

**评分**：6 类风险各 1；流程 2；逃逸 2。

**追问**：为什么不能只靠"提示词禁止"？→ 模型可能被注入/幻觉；安全必须靠环境边界，不靠自觉。

## G10. Agent 指标：pass@k、resolve rate、成本（L2）★

**题目**：解释 pass@1、pass@k、resolve rate、cost per task、latency；并说明各自容易被怎么误用。

**参考答案**：

| 指标 | 定义 | 误用 |
|---|---|---|
| pass@1 | 单次尝试通过率 | 用多次采样取最好，冒充单次 |
| pass@k | k 次尝试至少一次通过 | k 越大越好看，忽略成本 |
| resolve rate | 完全解决（非部分）比例 | 把"部分通过"算解决 |
| cost/task | token+工具+时长折算 | 只算 token，不算重试/人工 |
| latency | 端到端时间 | 只算模型，不算排队/测试 |

**建议**：同时报告 pass@1、pass@k（k=3/5）、resolve、P50/P95 延迟、成本；按难度/标签分层；给置信区间。

**评分**：5 个指标各 1；误用 3；报告建议 2。

**追问**：为什么只看 pass@k 会误导？→ 它奖励"多试几次"，但真实产品要一次成功且成本可控。
