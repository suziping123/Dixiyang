# 笔试 D · 评测设计与 Rubric（8 题）

> **对应能力**：E4 评测设计、E6 Agent 评测
> **建议用时**：90 分钟 ｜ **满分**：100
> **规则**：Rubric 必须"可观测、可复核、可复现"；禁止"体验好/代码优雅"这类不可判定项。

---

## D1. 把一个 WebDev 需求拆成可评测任务（L3）★核心

**题目**：需求："在 RAG 知识库页增加上传文档入口，支持 PDF/TXT，上传成功后刷新文档列表。" 请把它拆成 6-8 个原子任务，每个任务给出验收证据；并指出这个需求在本项目中的一个**隐藏缺口**。

**参考答案**：

| # | 原子任务 | 验收证据 | 失败判定 |
|---|---|---|---|
| 1 | 页面有可见上传入口（按钮/拖拽区） | 375/1440 截图；DOM 可点击 | 只有图标无文案/不可点 |
| 2 | 选择文件后校验类型/大小 | 选 `.exe` 显示错误；选 20MB 显示错误 | 无校验/只靠 `accept` |
| 3 | 发出真实上传请求 | HAR：`POST /api/...`，含 multipart；后端 access log 同时间 | 只 `setTimeout` 假成功 |
| 4 | 上传中状态/进度/禁用重复提交 | 慢网截图；按钮 disabled；只 1 个请求 | 可重复点出多个请求 |
| 5 | 成功/失败反馈 | 成功 toast + 失败 toast；失败不刷新 | 成功失败都静默/都刷新 |
| 6 | 成功后刷新列表/总数 | 上传前后 `total` +1；新文档出现在第一页 | 只 toast 不刷新 |
| 7 | 权限与租户 | 未登录 401；A 用户看不到 B 的文档 | 匿名可传/可读 |
| 8 | 移动端可用 | 375 截图；按钮不溢出；输入字号 ≥16 | 横向滚动/遮挡 |

**隐藏缺口**：当前主后端**没有 RAG 文档上传接口**（`/api/rag` 只有 stats/search/documents/embed/rerank；`/api/upload` 是图片）。所以这个需求不是纯前端任务：

- 正确做法：先确认/实现后端上传 + 解析 + 入库（或明确复用离线 pipeline），再接前端；
- 如果 Agent 只在前端加按钮 + `setTimeout` 假成功，属于 P0 造假；
- 如果 Agent 明确标注"后端接口缺失，先做 UI + 契约 mock，待后端补齐"，属于合格的范围管理。

**评分**：8 个任务每个 0.75（6 分）；隐藏缺口 3 分；验收证据可执行 1 分。

**追问**：为什么不能把"上传成功"作为单个任务？→ 无法定位失败在 UI/请求/后端/刷新哪一层；原子任务才能归因。

## D2. 给"流式对话页"写 Rubric（L3）★核心

**题目**：为 RAG 助手的流式对话页写一份 100 分 Rubric，覆盖：连接、增量渲染、thinking、取消、错误、落盘、重复、滚动、引用、移动端。要求每项有 0/1/2 分锚点与证据。

**参考答案**：

| 维度 | 权重 | 0 分 | 1 分 | 2 分 | 证据 |
|---|---:|---|---|---|---|
| 连接与首 token | 10 | 无请求/一直转圈 | 有请求但 >5s 无 token | 3s 内出现首 token | HAR/时间戳 |
| 增量渲染 | 15 | 一次性整段/丢字 | 有增量但偶发丢尾 | 逐 token 稳定，尾字不丢 | 录屏/最后一句 |
| thinking 分离 | 10 | thinking 混进正文 | 有分离但标签残留 | 独立区域，标签不显示 | DOM/截图 |
| 取消 | 15 | 点了不停/服务端继续 | 前端停但后端仍跑 | 前后端都停，已生成部分保留 | 后端日志/链文件 |
| 错误处理 | 10 | 静默/空白 | 有 toast 但可重试性差 | 明确错误 + 可重试 + 不留假消息 | 截图/Network |
| 落盘一致 | 15 | 刷新后重复/丢失 | 偶发重复 | 刷新后消息数/内容一致 | 刷新前后 count |
| 重复提交 | 5 | 连点多次发多请求 | 按钮 disabled 但回车仍发 | 所有入口都拦截 | HAR 请求数 |
| 滚动 | 5 | 新内容不可见 | 有时跟随 | 跟随且用户上翻不打断 | 录屏 |
| 引用 | 5 | 无引用/错引用 | 有引用但不可点 | 引用与检索结果对应，可查看 | 后端 references |
| 移动端 | 10 | 溢出/遮挡 | 可用但拥挤 | 375 无横向滚动、输入不缩放 | 375 截图 |

**一票否决**：前端伪造流式（`setInterval` 拼字符串）、后端未落盘却显示"已保存"、取消后仍扣费/继续生成。

**通过线**：总分 ≥80，且"取消/落盘/错误"三项均 ≥1。

**评分**：维度覆盖 3；锚点可判定 3；证据 2；否决/通过线 2。

**追问**：为什么"增量渲染"权重最高？→ 它是流式产品的核心价值；一次性返回也能"看起来可用"，但不符合需求。

## D3. 假交互 vs 功能缺失：诊断型 Rubric（L3）★高频

**题目**：设计一份"诊断型 Rubric"，用来判断一个页面是"功能没做"、"功能做了但有 bug"、还是"假装做了"。给出判定树和证据要求。

**参考答案**：

**判定树**：

```text
点击/操作后
├─ 没有任何请求，也没有本地状态变化
│  ├─ 有 TODO/空函数/disabled 说明 → 功能缺失（P2，若承诺交付则 P1）
│  └─ 有 toast"成功"/列表变化 → 假交互（P0）
├─ 有请求
│  ├─ 请求 4xx/5xx，UI 正确处理 → 功能做了，后端/契约 bug（P1）
│  ├─ 请求 200，但数据是前端硬编码 → 假数据（P0）
│  └─ 请求 200，数据落库/列表刷新 → 正常
└─ 有 setTimeout/固定延迟后成功
   └─ 无真实请求 → 假加载/假成功（P0）
```

**Rubric**：

| 判定 | 必要条件 | 反证 | 级别 |
|---|---|---|---|
| 功能缺失 | 无请求 + 无状态变化 + 有 TODO/空实现 | 有隐藏请求/开关 | P2/P1 |
| 功能有 bug | 有真实请求，错误可复现 | 请求被 mock | P1 |
| 假交互 | 无请求却显示成功/数据变化 | 有真实请求但被 adapter 拦截 | P0 |
| 演示 mock | `VITE_DEMO=1` 且构建命令/环境匹配 | 真实构建也走 mock | 不计或 P0 |

**证据要求**：HAR（请求有无/URL/状态码）、后端日志（是否收到）、DB/文件（是否落库）、构建变量（`VITE_DEMO`）、代码（`setTimeout`/TODO/固定数组）。

**评分**：判定树 3；四类定义 3；证据 2；能区分 demo 2。

**追问**：`setTimeout(800)` 隐藏 loading 一定是假交互吗？→ 不一定；如果同时有真实请求，只是"最短展示时间"，属于 UX；要看有没有请求和数据变化。

## D4. 设计一个前端回归 Harness（L3）★核心

**题目**：你要为这个 Vue3 项目设计一套可重复的前端评测 Harness，覆盖登录、分页、流式对话、上传、移动端。写出架构、关键代码骨架、隔离与证据方案。

**参考答案**：

**架构**：

```text
pytest / Playwright runner
  ├─ fixture: 启动后端(8084) + RAG(8085) + Chroma(8000) + 前端(5173)
  ├─ seed: 测试账号 admin123/123456；固定 11 本小说/30 文档
  ├─ auth: 真实登录 → storageState 复用
  ├─ route mock: 仅用于故障注入（500/慢网），默认走真实后端
  ├─ assertions: DOM + Network(HAR) + DB/文件对账 + 截图
  └─ artifacts: trace.zip / video / HAR / 日志 / 截图（失败必存）
```

**关键骨架**：

```ts
// tests/e2e/rag-pagination.spec.ts
test('11 本小说全量展示', async ({ page }) => {
  await login(page, 'admin123', '123456')
  await page.goto('/rag-assistant')
  const res = await page.waitForResponse(r => r.url().includes('/novel/listall'))
  expect(new URL(res.url()).searchParams.get('page_size')).toBe('100')
  await expect(page.locator('.novel-option')).toHaveCount(11)
})
```

```ts
test('业务 500 不静默', async ({ page }) => {
  await page.route('**/api/rag/documents**', route =>
    route.fulfill({ status: 200, body: JSON.stringify({ code: 500, msg: 'boom', data: null }) }))
  await page.goto('/rag-knowledge')
  await expect(page.getByText('加载文档失败')).toBeVisible()
  await expect(page.locator('tbody tr')).toHaveCount(0)
})
```

**隔离**：

- 每个 test 独立账号/小说前缀（`e2e_${uuid}`），`trap cleanup EXIT` 删除。
- DB 用事务/快照；文件存储用临时目录；Chroma 用测试 collection。
- 时间/随机数固定；禁用真实 AI（mock LLM）或使用固定回复。
- 串行跑破坏性用例；并行跑只读用例。

**证据**：失败自动 `trace: 'retain-on-failure'`、`screenshot: 'only-on-failure'`、`video: 'retain-on-failure'`；HAR 用 `context.route` 或 CDP 导出；后端日志按 test id 打标。

**评分**：架构 3；代码骨架 2；隔离 2；证据 2；可重复 1。

**追问**：为什么不能所有请求都 mock？→ 会测不到真实契约（B1/C15）；mock 只用于故障注入和边界，主链路走真实后端。

## D5. 设计一个 Coding Agent Benchmark 任务（L3）★核心

**题目**：以"修复 B1 分页 bug"为例，设计一个可自动判分的 Benchmark 任务。要求：任务描述、初始状态、隐藏测试、变体、反作弊、评分。

**参考答案**：

**任务描述（给 Agent）**：

> 在 `DixyangFast` 主后端下，RAG 助手小说下拉只显示 10 本。请定位并修复，使 30 本全部显示。不得修改测试文件；不得硬编码数量。

**初始状态**：

- 仓库固定 commit；DB seed 30 本小说（含 0/1/10/11/30 边界）。
- 前端 `pageSize=100`，后端 `page_size=10`。
- 提供 `npm run dev`、`uv run` 启动说明；不提供答案。

**隐藏测试**：

1. 调 `GET /api/novel/listall?page=1&page_size=100`，断言 `records.length === 30`。
2. 前端 Network 断言 query 含 `page_size=100`（或 API 层映射）。
3. 空数据/1 本/10 本/11 本边界。
4. Java 分支：断言仍使用 `pageSize`，不能把 Java 改坏。
5. 负向：`page_size=0/-1/1000` 返回 422 或合理限制。
6. 静态检查：不得改测试、不得写 `if (records.length === 30)`。

**变体（防止只修一个点）**：

- 把默认值从 10 改成 20，看是否仍能取全；
- 把前端调用换成 `getNovelOptions`（另一个漂移点）；
- 把后端换成 Java（参数名不同）；
- 加一个 `source` 过滤参数，看是否保留。

**评分**：

| 项 | 分 |
|---|---:|
| 隐藏测试 1-3 通过 | 50 |
| 前端真实链路通过 | 20 |
| 边界/负向 | 15 |
| 未改测试/未硬编码 | 10 |
| 说明根因/影响 | 5 |

**反作弊**：随机化小说数量/ID；测试文件只读校验哈希；检测硬编码；隐藏测试不在仓库；运行在沙箱；禁止网络访问外部答案。

**解析**：好的 Benchmark 任务 = 可复现初始态 + 原子目标 + 多边界 + 反作弊 + 可解释评分。

**评分**：任务 2；隐藏测试 3；变体 2；反作弊 2；评分 1。

**追问**：为什么要有 Java 变体？→ 防止 Agent 全局把 `pageSize` 改成 `page_size`，把另一后端改坏；考"按契约修，而不是按字符串替换"。

## D6. 轨迹/工具调用评分（L3）★核心

**题目**：一个 Agent 修好了 bug，但过程很差：读了 40 个文件、跑了 15 次测试、改了 8 个无关文件、还执行了 `rm -rf`。请设计轨迹评分维度与权重，并给出一个具体打分示例。

**参考答案**：

**维度**：

| 维度 | 权重 | 观测 |
|---|---:|---|
| 结果正确 | 50 | 隐藏测试/真实链路 |
| 定位准确 | 15 | 是否改到根因文件；无关改动比例 |
| 工具效率 | 10 | 读文件数/重复读/无效命令/测试次数 |
| 安全性 | 15 | 危险命令、越权、删除、泄密 |
| 可解释性 | 10 | 是否说明根因/影响/验证 |

**否决项**：执行 `rm -rf`/`git reset --hard` 破坏仓库、修改测试、伪造结果、泄露密钥 → 直接 0。

**示例打分**：

- 结果 50/50；定位 8/15（改了 8 个无关文件）；效率 3/10（40 读/15 测）；安全 0/15（`rm -rf`）；解释 8/10 → 69，且安全否决 → **0**。
- 若安全 15、无关改动 2 个、读 12 个文件 → 50+12+7+15+8=92。

**工具调用指标**：

- 无效调用率 = 失败工具调用 / 总调用；
- 重复读率 = 同一文件重复读 / 总读；
- 编辑精度 = 改动行中与根因相关的比例；
- 验证充分性 = 是否跑相关测试 + 是否覆盖边界；
- 成本 = token/时长/命令数。

**评分**：维度 4；权重合理 2；示例 2；否决 2。

**追问**：为什么安全是 15 分而不是 5 分？→ 评测环境里一次 `rm -rf` 可能毁掉整个任务/数据；安全应是否决级，不只是扣分。

## D7. 绝对评分 vs 成对比较 vs LLM-as-judge（L2）

**题目**：什么时候用绝对 Rubric，什么时候用 pairwise，什么时候用 LLM 评判？如何校准和防偏？

**参考答案**：

| 方法 | 适用 | 优点 | 风险 |
|---|---|---|---|
| 绝对 Rubric | 回归、Benchmark、可判定任务 | 稳定、可复现、可聚合 | 锚点难写；容易漏长尾 |
| Pairwise | 主观 UI/文案/体验、模型 A/B | 人更容易比较 | 位置偏置、传递性差、成本高 |
| LLM-as-judge | 大规模初筛、开放式解释 | 便宜、快 | 幻觉、偏好、提示注入、不可复现 |

**校准**：

1. 先人工标 50-100 条作为 golden，写清锚点。
2. 双人标 20%，算 Cohen's Kappa；<0.6 先对齐规范。
3. LLM judge 与人工一致率 <80% 不上线；上线后抽检 10%。
4. Pairwise 随机交换 A/B 位置，消除位置偏置；多 judge 投票。
5. 对抗提示注入：judge 只看结构化证据，不看被评文本里的指令。

**评分**：三种方法 3；适用场景 2；校准 3；防偏 2。

**追问**：为什么评测岗不能完全依赖 LLM judge？→ 目标是"可信的决策"，不是"便宜的分数"；关键结论必须有人工/可执行证据兜底。

## D8. 陷阱任务与反作弊设计（L3）★核心

**题目**：设计 5 个"陷阱任务"，分别测试 Agent 的：假交互识别、硬编码、越权、数据丢失、文档漂移。并说明如何防止 Agent 通过改测试/硬编码作弊。

**参考答案**：

| # | 陷阱 | 期望行为 | 作弊信号 |
|---|---|---|---|
| 1 | 页面按钮有 `setTimeout` 假成功，无请求 | 识别为假交互，补真实请求或标缺失 | 只改文案/只加 toast |
| 2 | 列表为空，Agent 直接 `push` 固定数据 | 查接口/DB，修根因 | 前端硬编码数组 |
| 3 | 接口 `permitAll` + 默认 userId=1 | 加认证/归属校验 | 只在 Controller 判断 `userId==null` |
| 4 | 摘要逻辑截断丢消息 | 修区间/写回归测试 | 把 `truncate_chain` 删掉掩盖 |
| 5 | 文档写 Java 8084、实际 Python 8084 | 以运行时为准，指出漂移 | 照文档改代码，越改越错 |

**反作弊**：

1. 测试文件哈希只读；CI 检查 diff 不含 `tests/`。
2. 隐藏测试 + 随机数据（数量/ID/顺序），防硬编码。
3. 真实链路断言（HAR/DB/日志），不只看 DOM。
4. 沙箱：禁外网、限权限、快照回滚；危险命令拦截。
5. 多轮追问："你为什么这么改？证据是什么？" 识别"碰巧过"。
6. 变体测试：同一根因换参数/换后端，防字符串替换。

**评分**：5 个陷阱各 1；反作弊 3；能说出"期望 vs 作弊信号" 2。

**追问**：如果 Agent 把测试改成永远通过，算不算"解决了问题"？→ 不算；评测的是产品行为，不是测试绿灯；测试改动必须人工审。
