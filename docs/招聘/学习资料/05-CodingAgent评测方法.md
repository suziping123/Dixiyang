# 05 · Coding Agent 评测方法

> **定位**：本岗位核心卷。从 Agent 执行机制到任务设计、Harness、Rubric、轨迹、指标、反作弊，形成可复现的评测闭环。
> **层级**：L2-L7
> **对应岗位能力**：发现假实现、复现缺陷、设计任务、写评分标准、读轨迹、做 badcase 归因、输出报告。


> **来源约定**：未标来源的段落为通用技术知识；标 `[项目]` 的有仓库代码/脚本/文档依据；`[项目-冲突]` 表示材料互相矛盾；`[推断]`/`[待确认]` 表示分析或尚需验证。

---

## 1. Agent 是什么

### 1.1 与普通 LLM 的区别

| 维度 | 普通 LLM | Coding Agent |
|---|---|---|
| 输入 | prompt | 任务 + 代码库 + 工具 + 环境 |
| 输出 | 文本 | 工具调用 + 代码修改 + 验证结果 |
| 过程 | 一次生成 | 多轮 observe-think-act |
| 成功 | 文本合理 | 任务在环境中真实通过 |
| 风险 | 幻觉 | 幻觉 + 破坏环境 + 假修复 + 越权 |

**核心**：Agent 的价值不在"说得像"，而在**能观察环境、采取行动、根据反馈调整，并最终交付可验证结果**。

### 1.2 基本循环

```text
目标/任务
  ↓
Observe：读文件、搜索、跑测试、看日志
  ↓
Think：理解、定位、计划
  ↓
Act：编辑、执行命令、调用工具
  ↓
Feedback：测试结果/错误/差异
  ↓
Adjust：修正计划/回滚/继续
  ↓
Stop：通过验证/达到上限/无法继续
```

### 1.3 Agent 的能力边界

- 能：读写文件、搜索、执行命令、跑测试、迭代修复。
- 不能/不可信：自身声称"已完成"、对未执行操作的描述、对隐藏测试的猜测。
- 评测要**以环境结果为准**，不以模型自述为准。

## 2. 工具调用

### 2.1 工具设计

```json
{
  "name": "run_tests",
  "description": "运行指定测试命令，返回退出码、stdout、stderr",
  "parameters": {
    "type": "object",
    "properties": {
      "command": { "type": "string" },
      "timeout_ms": { "type": "integer", "minimum": 1000, "maximum": 300000 }
    },
    "required": ["command"]
  }
}
```

原则：

- 单一职责、参数明确、返回结构化。
- 危险操作（删除/网络/部署）要审批/沙箱/白名单。
- 超时、输出上限、错误分类（可重试/不可重试）。
- 工具结果要可被模型理解，也要可被评测器记录。

### 2.2 工具调用失败

| 失败 | 例子 | 处理 |
|---|---|---|
| 参数错 | 缺必填/类型错 | 返回校验错误，让模型修正 |
| 命令失败 | 测试失败/编译错 | 返回 stderr/退出码 |
| 超时 | 长测试/死循环 | 终止并标记 |
| 权限 | 无写权限/网络禁用 | 明确拒绝，不静默 |
| 环境缺失 | 依赖未装/端口占用 | 提示安装/换端口 |

**评测关注**：是否选了正确工具、参数是否正确、失败后是否调整、是否重复无效调用。

### 2.3 工具调用与幻觉

- 模型可能声称"已运行测试"但实际没调用工具。
- 模型可能编造工具输出/退出码。
- 评测器必须记录真实工具调用与结果；报告只采信工具日志。

## 3. 上下文、代码库理解与规划

### 3.1 上下文来源

```text
任务描述
仓库结构/README/配置
相关文件内容
搜索结果
历史对话/摘要
工具输出（测试/日志/差异）
```

### 3.2 代码库理解

- 先定位入口/路由/组件/测试，再读实现。
- 用搜索（符号/字符串/调用点）建立调用链，不靠猜文件。
- 关注：类型/接口、数据流、错误处理、配置、测试。
- 大仓库要分层：目录→模块→文件→符号；避免一次性读太多。

### 3.3 规划

好的计划：

- 可验证的子目标；
- 每个子目标有文件/命令/预期结果；
- 有回滚点；
- 有停止条件。

差的计划：

- "优化一下代码"（不可验证）；
- 一次改十几个文件（难定位）；
- 不跑测试就宣布完成；
- 遇到失败不断重试同一命令。

### 3.4 上下文压缩

- 长对话/大文件要摘要，但摘要会丢细节；关键代码/错误要保留原文。
- 检索相关片段而不是全量塞入。
- 记录"已确认事实/待验证假设"，避免重复探索。

## 4. 修改、执行、验证、终止、恢复

### 4.1 修改

- 最小 diff：只改必要代码；避免顺手重构扩大风险。
- 保持风格/类型/错误处理一致。
- 修改后检查 diff：是否误删、是否调试残留、是否硬编码。
- 高风险改动（鉴权/事务/迁移）要有测试/回滚。

### 4.2 执行与验证

```text
静态：type-check / lint / build
单测：目标测试 + 相邻测试
集成：接口/DB/缓存
端到端：真实用户路径
回归：历史 badcase
```

**验证的层次**：

1. 代码能编译/导入；
2. 目标测试通过；
3. 相关测试不回归；
4. 真实请求/页面符合预期；
5. 边界/失败/并发也成立。

### 4.3 终止条件

- 成功：所有验收条件满足 + 回归通过。
- 失败：无法定位/环境不可用/达到步数/成本上限。
- 不确定：需要人工介入；不能假装成功。

**反模式**：

- 测试失败就删测试/改断言；
- 只跑一个测试就宣布全绿；
- 捕获异常让测试"通过"；
- 无限重试同一命令。

### 4.4 恢复与回滚

- 每步可回滚（git diff/快照/临时分支）。
- 失败时回到最后一个已知良好状态，不要叠加错误修改。
- 记录失败尝试，避免重复。
- 环境损坏（依赖/端口/数据）要重置沙箱。

## 5. 任务与 Benchmark 设计

### 5.1 任务类型

| 类型 | 例子 | 考察 |
|---|---|---|
| 缺陷修复 | 接口 500/页面不显示 | 定位、复现、修复、回归 |
| 功能实现 | 新增筛选/导出 | 需求理解、契约、测试 |
| 代码审查 | 找出安全/并发问题 | 发现力、证据 |
| 重构 | 拆分模块/去重 | 不破坏行为 |
| 测试编写 | 补单测/E2E | 覆盖率、断言质量 |
| 评测设计 | 写 Rubric/任务 | 标准化能力 |
| 假实现识别 | 页面看似可用但 mock | 真实性判断 |

### 5.2 好任务的标准

- **真实**：来自真实仓库/真实缺陷，不是玩具题。
- **可复现**：固定环境、数据、依赖、端口、账号。
- **可判定**：成功/失败有客观标准（测试/断言/人工 rubric）。
- **原子**：一个任务聚焦一个能力，避免混杂。
- **难度分层**：L1 定位→L2 修复→L3 跨文件→L4 并发/安全→L5 设计。
- **不泄题**：任务描述不直接给答案/文件/行号。
- **防污染**：不在训练数据/公开题库中；定期换题。

### 5.3 任务模板

```markdown
## 背景
项目/版本/运行方式/测试账号。

## 现象
用户可观察到的现象；错误日志/截图/请求。

## 期望
必须满足的行为；边界/兼容性要求。

## 约束
不能改的接口/不能引入的依赖/时间/安全要求。

## 验收
隐藏测试/命令/人工检查点。

## 禁止
不得删测试/硬编码/联网/读隐藏测试。
```

### 5.4 难度与区分度

- 太简单：所有模型都过，无区分度。
- 太难：所有模型都挂，无法比较。
- 好任务：不同能力模型有差异；错误模式可归因。
- 用试点（pilot）校准通过率/耗时/评分一致性。

### 5.5 隐藏测试设计

- 覆盖 happy path + 边界 + 失败 + 并发/权限。
- 测试不能只断言"没报错"；要断言数据/副作用/状态。
- 测试要独立、可重复、无外部依赖。
- 防止模型读取/修改测试：测试放在沙箱外/只读/运行后校验。

## 6. Harness、环境与可复现

### 6.1 Harness 组成

```text
任务加载器
 → 环境准备（镜像/依赖/数据/端口）
 → Agent 运行（工具/模型/超时）
 → 轨迹记录（消息/工具/文件 diff）
 → 测试执行（隐藏测试/回归）
 → 评分（自动 + 人工）
 → 报告（指标/日志/复现命令）
```

### 6.2 环境隔离

- 容器/虚拟机；非 root；只挂载必要目录。
- 网络默认关闭/白名单；禁止访问真实生产/外部 API。
- 资源限制：CPU/内存/磁盘/进程数/时间。
- 每任务重置快照；避免上一个任务污染。
- 端口动态分配，避免冲突。

### 6.3 可复现要素

| 要素 | 记录 |
|---|---|
| 代码 | commit SHA |
| 依赖 | lockfile/镜像 digest |
| 运行时 | Python/Node/Java 版本 |
| 数据 | 数据集版本/seed/快照 |
| 配置 | 环境变量（脱敏）/端口 |
| 模型 | 名称/版本/温度/最大 token |
| 工具 | 版本/权限/超时 |
| 评分 | rubric 版本/评审人 |

### 6.4 失败与重试

- 环境失败与模型失败要分开统计；不能把环境抖动算模型错。
- 重试次数固定；记录每次结果；不能只报最好一次。
- 超时/崩溃要归类；报告样本量与失败率。
- 评分者/模型版本变化要记录。

## 7. Rubric 与评分

### 7.1 好 Rubric 的特征

- **可观察**：基于代码/测试/轨迹，不基于"感觉"。
- **可判定**：每个档位有明确条件。
- **正交**：维度不重复计分。
- **有否决项**：安全/造假/删测试直接 0。
- **有示例**：边界案例怎么判。
- **版本化**：改规则要记录并重跑校准。

### 7.2 维度示例

| 维度 | 权重 | 0 分 | 满分 |
|---|---:|---|---|
| 问题定位 | 20 | 未定位/改错文件 | 根因准确，证据充分 |
| 修复正确性 | 30 | 未修复/引入新 bug | 通过隐藏测试+回归 |
| 验证充分性 | 20 | 未运行/只跑一个 | 单测+集成+边界 |
| 代码质量 | 15 | 硬编码/调试残留 | 风格一致/最小 diff |
| 过程规范 | 15 | 破坏环境/造假 | 工具使用合理/可复现 |

### 7.3 评分档位

```text
5 = 优秀：超出预期，边界/回归都考虑
4 = 良好：满足要求，少量改进
3 = 合格：基本满足，存在小问题
2 = 不合格：部分满足/有回归
1 = 差：未完成/误导
0 = 无效：造假/破坏/安全违规
```

### 7.4 双评与一致性

- 双盲独立评分；分歧大时仲裁。
- 计算一致率/Cohen's Kappa/ICC；低于阈值要校准。
- 校准集：覆盖各档位/边界；先培训再正式评。
- 记录评分理由/证据；不能只给分数。

### 7.5 自动评分 vs 人工评分

| 方式 | 优点 | 缺点 |
|---|---|---|
| 自动测试 | 客观、可重复、便宜 | 覆盖有限、可能被绕过 |
| 人工 rubric | 能评过程/质量 | 贵、主观、慢 |
| LLM judge | 便宜、可扩展 | 偏差/不稳定，需要校准 |

**推荐**：自动测试做硬门槛，人工/LLM 评过程与质量；关键任务双评。

## 8. 轨迹与过程评估

### 8.1 轨迹记录

```json
{
  "task_id": "fix-rag-500",
  "steps": [
    {"type": "tool", "name": "read_file", "args": {"path": "rag.py"}, "result": "..."},
    {"type": "tool", "name": "run_tests", "args": {"command": "pytest ..."}, "result": {"exit": 1}},
    {"type": "edit", "path": "rag.py", "diff": "..."},
    {"type": "message", "content": "..."}
  ],
  "final_diff": "...",
  "test_result": {"passed": 3, "failed": 0},
  "usage": {"tokens": 12345, "tool_calls": 8, "duration_ms": 45000}
}
```

### 8.2 过程指标

- 工具调用次数/无效调用率；
- 重复命令/重复读文件；
- 定位到根因的步数；
- 测试运行次数/失败恢复次数；
- 是否读隐藏测试/改测试；
- 是否越权/联网/破坏环境；
- token/时间/成本。

### 8.3 轨迹评审要点

1. 是否先理解再改？
2. 是否用证据定位，而不是猜？
3. 修改是否最小、聚焦？
4. 是否验证了失败场景？
5. 失败后是否调整策略？
6. 是否伪造工具输出/测试结果？
7. 是否遵守约束/权限？

### 8.4 过程与结果的关系

- 结果对但过程危险（删测试/硬编码）→ 不能给高分。
- 过程合理但结果失败 → 可能是任务/环境问题，需归因。
- 结果对且过程可复现 → 高分。

## 9. badcase、指标与报告

### 9.1 badcase 分类

```text
需求理解：漏需求/误解约束
定位：找错文件/只改表象
修改：引入回归/边界未处理
验证：没跑测试/断言太弱
环境：依赖/端口/数据问题
工具：选错工具/参数错/不读结果
过程：重复/死循环/超时
造假：硬编码/删测试/伪造输出
安全：越权/路径穿越/注入
表达：报告误导/隐瞒失败
```

### 9.2 归因方法

- 复现 → 看轨迹 → 找第一个错误决策点 → 判断是模型/任务/环境/评分问题。
- 区分"模型能力不足"与"任务描述不清/环境坏/测试错"。
- 同类 badcase 聚类，找系统性问题（prompt/工具/schema）。
- 修复后加入回归集。

### 9.3 指标

| 指标 | 说明 |
|---|---|
| Resolve Rate | 任务完全通过率 |
| pass@k | k 次尝试至少一次通过（注明 k/温度） |
| First-pass Rate | 第一次提交通过率 |
| Regression Rate | 引入回归比例 |
| Tool Accuracy | 工具/参数正确率 |
| Avg Steps/Tokens/Time | 效率 |
| Human Score | Rubric 均分 |
| Agreement | 双评一致性 |
| Cost per Task | 成本 |

**报告原则**：给样本量、配置、置信区间/波动；不能只挑成功案例。

### 9.4 报告模板

```markdown
## 结论
一句话：版本/模型在什么任务上表现如何。

## 范围与方法
任务集/样本量/环境/模型/评分规则。

## 结果
总体指标 + 分难度/分类型 + 失败分布。

## 典型 badcase
现象/轨迹/根因/证据/建议。

## 风险与限制
环境/样本/评分偏差/未覆盖项。

## 复现
命令/配置/数据版本。
```

### 9.5 从发现到标准化

岗位工作流：

```text
发现异常
 → 复现（固定环境/输入）
 → 取证（日志/请求/DB/轨迹）
 → 归因（模型/任务/环境/评分）
 → 标准化（任务模板/Rubric/分类）
 → 校准（双评/试点）
 → 回归（历史 badcase）
 → 报告/迭代
```

## 10. 反作弊、沙箱与公平

### 10.1 常见作弊

| 作弊 | 例子 | 防护 |
|---|---|---|
| 硬编码 | 按测试输入返回固定值 | 隐藏测试/随机化/多组数据 |
| 删/改测试 | 删除失败断言 | 测试只读/运行后校验/独立副本 |
| 读隐藏测试 | 搜索测试文件 | 测试隔离/权限 |
| 伪造工具输出 | 声称测试通过 | 只采信真实日志 |
| 改环境 | 改端口/配置绕过 | 快照/完整性校验 |
| 网络泄漏 | 请求外部答案 | 断网/白名单 |
| 依赖泄漏 | 从缓存/历史找答案 | 清缓存/隔离 |
| 时间作弊 | 跳过超时/异步 | 真实等待/超时检测 |

### 10.2 沙箱

- 容器隔离；非 root；只读基础镜像；临时工作区。
- 资源限制：CPU/内存/磁盘/进程/时间。
- 网络默认 deny；需要时白名单。
- 文件系统：只挂载仓库/测试；敏感目录不可见。
- 审计：命令/文件/网络/工具调用全记录。

### 10.3 公平性

- 所有模型相同环境/工具/超时/重试次数。
- 模型版本/温度/最大 token 固定并记录。
- 任务难度/领域均衡；避免数据污染。
- 评分者盲评；随机顺序；校准。
- 报告失败样本，不只报最好结果。

### 10.4 安全边界

- Agent 不应有生产凭据/真实用户数据。
- 工具最小权限；危险操作需审批。
- 输出/代码审查防注入/后门。
- 评测环境与生产隔离。

## 11. 项目映射：Dixiyang 可作为哪些评测任务

| 任务 | 现象 | 考察 | 验收 |
|---|---|---|---|

## 12. 高频追问

1. **Agent 评测和普通模型评测区别？** 评过程+环境结果，不只看文本；工具有副作用，要沙箱/轨迹。
2. **pass@k 怎么解释？** k 次独立尝试至少一次成功的比例；要注明 k、温度、重试策略，不能和单次成功率混。
3. **如何保证可复现？** 固定 commit/依赖/数据/环境/模型/评分；记录配置；沙箱快照。
4. **自动测试够了为什么还要人工？** 测试覆盖有限、可被绕过；过程质量/可维护性/安全需要人评。
5. **双评不一致怎么办？** 校准 rubric、仲裁、计算一致性、找分歧案例、更新标准。
6. **如何防 reward hacking？** 隐藏测试、随机化、测试只读、行为监控、代码审查、多任务泛化。
7. **如何处理环境失败？** 与模型失败分开统计；重试有限；报告失败率；修复 harness。
8. **如何设计一个有区分度的任务？** 真实、原子、可判定、难度分层；试点校准通过率。
9. **结果对但删了测试，怎么判？** 直接 0/否决；这是造假，不是能力。
10. **如何评估 Agent 的代码库理解？** 看定位路径、搜索策略、是否读相关文件/测试、是否解释调用链。
