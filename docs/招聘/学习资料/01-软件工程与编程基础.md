## 1. 程序如何运行

### 1.1 从源码到进程

```text
源码 .ts/.py
   │ 解析/类型检查（可选）
   ▼
构建产物 .js/.pyc/镜像
   │ 启动命令 + 环境变量 + 配置
   ▼
进程（PID）
   ├── 代码段：指令
   ├── 堆：对象/大对象/缓存
   ├── 栈：函数调用帧/局部变量/返回地址
   ├── 文件描述符：socket/文件
   └── 线程/协程：执行流
   │
   ▼
I/O：网络/磁盘/数据库/下游服务
```

**核心结论**：

- "代码写对了"不等于"运行时对了"：环境变量、端口、依赖版本、数据、权限都会改变结果。
- 排查先分层：**构建期 → 启动期 → 请求期 → 数据期 → 下游期**。
- 看到 500 不要直接读业务代码，先确认进程活着、端口对、日志有栈、请求真的到了这一层。

### 1.2 编译、解释、JIT

| 方式 | 代表 | 特点 | 典型问题 |
|---|---|---|---|
| 编译型 | Java、Go、Rust | 启动前生成字节码/机器码 | 编译通过但运行时依赖缺失 |
| 解释型 | Python、Shell | 边解释边执行 | 运行到某行才暴露错误 |
| 转译/打包 | TypeScript→JS、Vite | 开发期转换，生产打包 | 类型检查与构建是两道闸 |
| JIT | V8、JVM | 运行时热点编译 | 冷启动/预热影响性能 |

**项目例子**：

- 前端 `npm run type-check` 通过，不代表 `npm run build` 通过；构建还受入口、资源、环境变量影响。[项目]
- Python 没有编译期类型强制；Pydantic 校验发生在**请求边界**，内部函数仍可能传错类型。[通用]

### 1.3 栈、堆与引用

```js
function makeUser() {
  const user = { name: "A" };
  return user;
}
const u1 = makeUser();
const u2 = u1;
u2.name = "B";
console.log(u1.name); // "B"
```

- 变量存"值"或"引用"；对象/数组/函数是引用语义。
- 重新赋值与修改内容不同：`u2 = {...}` 不改变 `u1`；`u2.name = ...` 会。
- Python 同理：`b = a` 让两个名字指向同一对象；`b = b + [1]` 创建新对象。

**常见错误**：

- 以为 `const` 让对象不可变：`const` 只限制绑定，不冻结内容。
- 浅拷贝后修改嵌套对象，原对象被连带修改。
- 把可变对象当函数默认参数（Python 高频坑）。

### 1.4 内存、GC 与泄漏的工程表现

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 内存持续上涨 | 全局缓存无上限、事件监听未解绑、闭包持有大对象 | 堆快照、对象计数、压测 |
| 页面越用越卡 | DOM/监听器/定时器泄漏、图表实例未销毁 | Performance、Memory、`dispose` |
| 后端 RSS 高 | 大文件全量读入、连接/游标未关、缓存膨胀 | 进程内存、对象统计、分页/流式 |

**项目对照**：

- ECharts 组件卸载时 `dispose()`、`ResizeObserver.disconnect()`，否则切换页面实例累积。[项目]
- 上传若先 `await file.read()` 再校验大小，会把大文件整体读进内存，属于"校验顺序错误"。[项目]

## 2. 数据结构与算法：够用且能解释

### 2.1 常用结构

| 结构 | 平均复杂度（查找/插入/删除） | 典型用途 | 注意 |
|---|---|---|---|
| 数组 | O(1) 索引 / O(n) 插入删除 | 列表、分页结果 | 中间插入昂贵 |
| 哈希表 | O(1) / O(1) / O(1) | 去重、计数、映射 | 最坏 O(n)，键要可哈希 |
| 栈 | O(1) 顶 | 撤销、括号匹配、调用栈 | 后进先出 |
| 队列 | O(1) 两端 | 任务、消息、BFS | 注意背压 |
| 堆 | O(log n) 插入/取顶 | TopK、优先队列 | 不是有序数组 |
| 二叉搜索树 | 平均 O(log n) | 有序查找 | 退化成链表 |
| B+ 树 | O(log n) | 数据库索引 | 磁盘页友好、范围查询强 |

### 2.2 复杂度不是学术问题

- 前端：列表每次渲染都 `filter + sort`，数据量大时主线程卡顿；应 `computed` 缓存或后端排序。
- 后端：循环里查数据库 = N+1；应批量查询/join。
- 检索：每次请求全量扫描文档 = O(N)；应建索引/向量库。
- 分页：`OFFSET` 很深时仍要扫描前 N 行；大偏移用游标（cursor）。

**项目对照**：

- 灵感流曾把"加载下一页"放在 `finally` 中，失败后仍递归调用，形成无限请求；这是**控制流错误**，不是算法问题。[项目]
- 广场推荐用 Redis ZSET 维护热度，避免每次全表排序；Redis 挂掉后回源 DB 并降级。[项目]

### 2.3 哈希与一致性

需要关注：

- 哈希冲突：开放寻址/链地址；恶意构造可能拖慢服务。
- 可变键：Python 的 `list` 不能做 dict key；JS 对象键会被转字符串（除非 Map）。
- 顺序：普通对象属性顺序有规则但不应当作稳定排序；需要顺序用数组。
- 去重：`Set` 对对象比较引用，不对内容比较。

```js
const a = { id: 1 };
const b = { id: 1 };
console.log(new Set([a, b]).size); // 2，不是 1

const key = (x) => `${x.id}`;
console.log(new Set([a, b].map(key)).size); // 1
```

## 3. JavaScript / TypeScript

### 3.1 作用域、闭包、提升

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 3 3 3
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 0); // 0 1 2
}
```

- `var` 函数作用域，`let/const` 块作用域。
- 闭包捕获的是**变量绑定**，不是创建时的值。
- 经典修复：`let`、IIFE、`bind`、额外参数。

**工程影响**：

- 事件回调里引用循环变量/响应式对象，可能拿到"最新值"而非"当时值"。
- 卸载组件后异步回调仍执行，会更新已销毁状态；需要取消标记/AbortController。

### 3.2 `this` 与调用方式

| 调用形式 | `this` |
|---|---|
| `obj.fn()` | `obj` |
| `fn()`（非严格） | 全局对象；严格模式 `undefined` |
| `new Fn()` | 新实例 |
| `fn.call(x)` / `apply` | `x` |
| 箭头函数 | 词法作用域，定义时确定，不能被 `call` 改变 |

```js
const obj = {
  name: "A",
  regular() { return this.name; },
  arrow: () => this.name,
};
console.log(obj.regular()); // "A"
console.log(obj.arrow());   // 取决于外层 this（模块中通常 undefined）
```

### 3.3 原型链与 `class`

- 每个对象有内部原型 `[[Prototype]]`；属性查找沿原型链向上。
- `class` 是原型继承的语法糖；`extends` 建立原型链。
- `instanceof` 检查原型链；`typeof` 对 `null` 返回 `"object"`，对数组返回 `"object"`。

```js
class Animal { speak() { return "?"; } }
class Dog extends Animal { speak() { return "woof"; } }
const d = new Dog();
console.log(d.speak());            // woof
console.log(d instanceof Animal);  // true
```

### 3.4 相等、类型转换、判空

```js
0 == ""        // true
0 === ""       // false
null == undefined // true
null === undefined // false
NaN === NaN    // false
Object.is(NaN, NaN) // true
```

工程建议：

- 业务比较用 `===`；只有明确要兼容 `null/undefined` 时才用 `== null`。
- 判断数组用 `Array.isArray`；判断普通对象要排除 `null` 和数组。
- 数字输入要区分 `0`、`""`、`null`；`if (!value)` 会把 0 当空。

### 3.5 Promise 与错误传播

```js
async function load() {
  try {
    const res = await fetch("/api/data");
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (e) {
    console.error("load failed", e);
    throw e; // 不要静默吞掉，除非有明确降级
  }
}
```

- `await` 只等待 Promise；普通值会立即 resolve。
- `try/catch` 捕获同步异常和 `await` 的 rejection；未 `await` 的 Promise rejection 可能变成未处理拒绝。
- `Promise.all` 一败全败；`Promise.allSettled` 收集全部结果；`Promise.race` 取最先完成。
- 不要用 `try/catch` 包住整个请求后只 `console.log`，否则调用方以为成功。

**项目对照**：

- axios 默认对 4xx/5xx reject，但业务层返回 `code=500` 且 HTTP 200 时会 resolve；若 `unwrap` 只取 `data`，页面会"成功但空白"。[项目]
- SSE 流式请求用原生 `fetch`，401 不会走 axios 拦截器，必须单独处理。[项目]

### 3.6 TypeScript：类型是契约，不是装饰

| 概念 | 作用 | 常见坑 |
|---|---|---|
| `interface` / `type` | 描述对象形状/联合 | 把运行时数据直接断言成类型 |
| 联合/字面量 | 收窄取值范围 | `string` 太宽，拼写错误不报 |
| 泛型 | 复用且保留类型 | 滥用 `any` 让泛型失效 |
| `unknown` | 安全未知 | 直接当 `any` 用 |
| `never` | 不可能值/穷尽检查 | 漏分支 |
| 类型收窄 | `typeof`/`in`/判别字段 | 运行时没校验，只靠 `as` |

```ts
type ApiResult<T> =
  | { code: 200; data: T; msg: string }
  | { code: number; data: null; msg: string };

function unwrap<T>(r: ApiResult<T>): T {
  if (r.code !== 200) throw new Error(r.msg);
  return r.data;
}
```

**原则**：

- 边界（HTTP、localStorage、URL、文件）进来的数据先校验，再赋类型。
- `as` 是"我保证"，不是"帮我检查"；外部数据用运行时校验（Zod/Pydantic/手写 guard）。
- `strictNullChecks` 能消灭大量 `undefined` 崩溃，但会增加迁移成本；项目采用渐进治理。[项目]

### 3.7 模块化

- ESM：静态分析、tree-shaking、顶层 `await`；CJS：运行时 `require`。
- 循环依赖会导致部分导出为 `undefined`；通过拆分公共模块/延迟调用解决。
- 桶文件 `index.ts` 方便但可能造成大包/循环依赖；按需导出。
- 前端路径别名要与 `tsconfig`、Vite 配置同时一致，否则"编辑器能跳、构建找不到"。

## 4. Python

### 4.1 对象、引用、可变性

```python
a = [1, 2]
b = a
b.append(3)
print(a)  # [1, 2, 3]

c = a[:]   # 浅拷贝
c.append(4)
print(a)   # [1, 2, 3]

d = {"x": [1]}
e = dict(d)      # 浅拷贝
e["x"].append(2)
print(d)         # {"x": [1, 2]}
```

- 赋值不复制对象；参数传递是"对象引用按值传递"。
- 浅拷贝只复制第一层；嵌套用 `copy.deepcopy`。
- 不可变类型：`int/float/str/tuple/frozenset`；可变：`list/dict/set/bytearray`。

### 4.2 可变默认参数（高频坑）

```python
def add(item, bucket=[]):   # 错：默认列表只创建一次
    bucket.append(item)
    return bucket

print(add(1))  # [1]
print(add(2))  # [1, 2]，不是 [2]
```

正确写法：

```python
def add(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket
```

### 4.3 迭代器、生成器、惰性求值

```python
def read_lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:          # 逐行，不一次性读入
            yield line.rstrip("\n")

lines = (x for x in read_lines("big.log") if "ERROR" in x)
for line in lines:
    ...
```

- 生成器函数调用返回生成器对象，`yield` 时才执行。
- 生成器只能遍历一次；需要重复用要转 `list` 或重新创建。
- 大文件/大结果集优先流式，避免内存峰值。

### 4.4 异常处理

```python
try:
    data = load_json(path)
except FileNotFoundError:
    data = {}
except json.JSONDecodeError as e:
    raise ValueError(f"配置格式错误: {path}") from e
finally:
    cleanup()
```

原则：

- 只捕获能处理的异常；不要裸 `except:`。
- 捕获后要么恢复，要么加上下文重抛，不要静默。
- 自定义异常表达业务语义；边界层统一转 HTTP 错误。
- `finally` 适合释放资源，但不要在里面 `return` 覆盖异常。

### 4.5 上下文管理器

```python
from contextlib import contextmanager

@contextmanager
def transaction(session):
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()
        raise
```

- `with` 保证退出时释放资源，即使中途异常。
- 数据库 Session、文件、锁、临时目录都适合上下文管理。
- 注意提交/回滚边界：在 `yield` 后提交，异常时回滚。

### 4.6 装饰器

```python
import functools, time

def timed(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__}: {time.perf_counter() - start:.3f}s")
    return wrapper
```

- 装饰器本质是"接收函数，返回新函数"。
- 带参装饰器多一层工厂。
- 必须 `functools.wraps` 保留元信息，否则 FastAPI/日志/调试会看到 `wrapper`。
- 不要用装饰器隐藏关键控制流（重试、鉴权、事务），否则排错困难。

### 4.7 类型标注与数据模型

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class User:
    id: int
    name: str
```

- 类型标注不强制运行时；Pydantic 在边界做校验。
- `dataclass` 适合内部值对象；Pydantic 适合 API 输入输出。
- 避免 `dict[str, Any]` 贯穿全层；用模型约束字段和默认值。

## 5. 异步与并发

### 5.1 并发 ≠ 并行

- **并发**：多个任务在重叠时间段推进（单核也能）。
- **并行**：多个任务同时执行（多核/多进程）。
- **异步**：不阻塞等待 I/O，完成后回调/恢复协程。

### 5.2 事件循环（先建立直觉）

```text
调用栈清空
  → 取微任务队列（Promise.then/queueMicrotask）全部执行
  → 取一个宏任务（定时器/I/O/事件）
  → 再清微任务
  → 渲染（浏览器）
  → 循环
```

```js
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");
// 1 4 3 2
```

详细浏览器机制见 [02 卷 2.3](./02-Web前端与Vue3.md)。

### 5.3 async/await 的阻塞风险

```python
import asyncio

async def handler():
    # 错：同步 requests 会阻塞事件循环
    # data = requests.get(url).json()
    async with httpx.AsyncClient() as client:
        resp = await client.get(url)
        return resp.json()
```

- 在 async 路由里调用同步阻塞库（`requests`、`time.sleep`、大文件同步读、CPU 密集计算）会卡住整个事件循环。
- 解决：异步库、`run_in_threadpool`、`asyncio.to_thread`、进程池/任务队列。
- 不是所有操作都值得异步；小规模同步代码更简单。

### 5.4 GIL、线程、进程、协程

| 模型 | 适合 | 限制 |
|---|---|---|
| 多线程 | I/O 密集、阻塞库 | GIL 限制 CPU 并行；共享状态要锁 |
| 多进程 | CPU 密集 | 进程间通信/内存开销 |
| asyncio | 高并发 I/O | 不能有阻塞调用；生态需异步库 |
| 线程池 | 把阻塞调用隔离出事件循环 | 池大小/队列要限制 |

**Python GIL**：同一进程内同一时刻通常只有一个线程执行 Python 字节码；I/O 等待会释放 GIL。CPU 密集多线程不会线性加速。[通用]

### 5.5 超时、取消、重试、幂等

```python
async def call_with_timeout(client, url):
    try:
        return await asyncio.wait_for(client.get(url), timeout=5)
    except asyncio.TimeoutError:
        raise RuntimeError(f"下游超时: {url}")
```

- 所有外部调用都要有超时；没有超时的等待会拖垮线程/连接池。
- 重试只用于**可重试错误**（超时、503、连接失败），且要指数退避 + 抖动；不要重试 400/401/403。
- 重试必须考虑幂等：GET 通常幂等；POST 创建可能重复下单/重复消息，需要幂等键。
- 取消要传播：前端 `AbortController`，后端检测断开；否则任务继续跑、资源不释放。

**项目对照**：

- Java 聊天 SSE 每请求新建线程池且无超时，`sendEvent` 异常被吞，客户端断开后任务可能继续。[项目]
- 前端流式请求用 `AbortController` 取消；切换会话时要避免旧流把内容写进新会话。[项目]

### 5.6 背压与队列

- 生产速度 > 消费速度时，队列无限增长会 OOM。
- 需要：有界队列、拒绝策略、限流、批处理、消费者扩容。
- 前端高频事件（滚动/输入）用防抖/节流，不是"来一个请求一个"。

## 6. 抽象、分层与错误处理

### 6.1 分层不是形式

```text
路由/控制器：解析请求、鉴权、参数校验、返回统一结构
服务层：业务规则、事务边界、编排
数据访问层：SQL/ORM/文件/缓存
基础设施：日志、配置、HTTP 客户端、存储
```

**判断分层是否合理**：

- 路由里是否直接写复杂 SQL/文件路径拼接？
- 服务层是否依赖 FastAPI 的 `Request`/`HTTPException`（导致难复用/难测试）？
- 数据访问是否泄漏到前端响应（ORM 对象直接序列化）？
- 事务边界是否在服务层，而不是每个小函数各自 commit？

### 6.2 组合优于继承

- 继承表达"is-a"，组合表达"has-a/uses-a"。
- 深层继承会导致脆弱基类；用策略/依赖注入/组合替代。
- 前端 composable、后端 service 注入都是组合思路。

### 6.3 错误分类

| 类型 | 例子 | 处理 |
|---|---|---|
| 用户输入错误 | 缺字段、格式错 | 400/422，返回可读字段错误 |
| 未认证 | 无 token/过期 | 401，前端跳登录 |
| 无权限 | 普通用户访问后台 | 403，不泄露资源存在性 |
| 不存在 | 资源 ID 无效 | 404 |
| 冲突 | 重复创建/版本冲突 | 409 |
| 限流 | 登录频繁 | 429 |
| 下游失败 | 超时/连接拒绝 | 502/503/504，降级/重试 |
| 程序缺陷 | 空指针/类型错 | 500，日志+堆栈，不暴露内部细节 |

**关键原则**：

- 不要把所有错误都返回 200 + `code=500`；HTTP 状态码与业务码要有明确约定。
- 前端不能只看 HTTP 200，必须检查业务码；后端不能只返回业务码而让监控看不到失败。
- 错误信息给用户要可行动，给日志要可定位；两者可以不同。

### 6.4 重试、熔断、降级

- 重试：临时故障；限制次数；退避；只重试幂等操作。
- 熔断：下游持续失败时快速失败，避免雪崩；半开探测恢复。
- 降级：缓存/默认值/只读模式；必须明确"降级后功能边界"。
- 超时：必须小于上游超时，形成预算链。

**项目对照**：

- Redis 不可用时广场回源 DB，并加冷却避免每次请求都重连；18000 请求 0 错误，代价是 P95 变差。[项目]
- RAG rerank 端点错误时静默返回原顺序，用户不知道精排失效；应记录指标/日志并可观测。[项目]

### 6.5 日志与可观测性

```python
import logging, uuid

logger = logging.getLogger(__name__)

def handle(req_id: str, user_id: int):
    logger.info("request.start", extra={"req_id": req_id, "user_id": user_id})
    try:
        ...
    except Exception:
        logger.exception("request.failed", extra={"req_id": req_id})
        raise
```

- 结构化日志优于字符串拼接；至少包含时间、级别、请求 ID、用户 ID、路由、耗时、错误码。
- 不要记录密码、token、完整身份证/手机号；敏感字段脱敏。
- 指标：QPS、错误率、P50/P95/P99、队列长度、缓存命中率、下游耗时。
- 追踪：跨服务传递 trace ID；前端用 HAR/Network 关联请求。

| `git diff` | 未暂存差异 | 审查自己的改动 |

### 7.2 依赖与锁文件

- 依赖漂移会导致"我这里能跑"：Node/Python 版本、系统库、可选依赖、环境变量。
- 升级依赖要跑类型检查、单测、构建、关键路径冒烟。

**项目对照**：

- `pyproject.toml` 与 `requirements.txt` 可能存在范围/版本漂移；部署前要以实际安装结果为准并锁定。[项目]
- 前端 Node engines 明确 `^20.19.0 || >=22.12.0`，低版本可能构建失败。[项目]

### 7.3 构建产物与部署

- 开发服务器（Vite dev）与生产构建（rollup）行为不同：代理、base、环境变量、tree-shaking、代码分割。

- 反向代理要处理：`/api` 转发、WebSocket/SSE、超时、缓冲、gzip、跨域。

## 8. HTTP、API 与安全基础

### 8.1 方法与状态码

| 方法 | 语义 | 幂等 | 常见用途 |
|---|---|---|---|
| GET | 读取 | 是 | 列表/详情 |
| POST | 创建/动作 | 否 | 登录、创建、提交 |
| PUT | 全量替换 | 是 | 更新配置 |
| PATCH | 部分更新 | 不一定 | 改字段 |
| DELETE | 删除 | 是 | 删除资源 |

常见状态码：200 成功、201 创建、204 无内容、301/302 重定向、304 未修改、400 参数错、401 未认证、403 无权限、404 不存在、409 冲突、422 校验失败、429 限流、500 服务端错误、502/503/504 下游/不可用/超时。

**易错**：

- 401 与 403 混用：401 是"你是谁不清楚"，403 是"知道你是谁但你不能做"。
- 业务失败返回 200：监控/网关无法识别，前端也容易漏判。
- 404 用来掩盖 403 可以防止资源枚举，但要与产品/安全约定一致。

### 8.2 REST 与 RPC

- REST 以资源为中心，利用 HTTP 语义；RPC 以动作为中心（如 `/createNovel`）。
- 本项目混合使用：`/novel/listall`、`/chat/stream`、`/api/admin/stats`，不必教条。
- 关键是**契约稳定**：字段名、类型、分页结构、错误结构、鉴权方式一致。

### 8.3 认证与授权

- 认证（Authentication）：你是谁。授权（Authorization）：你能做什么。
- Session/Cookie：服务端存会话，浏览器自动带 Cookie；要防 CSRF。
- JWT：自包含令牌，服务端验签；适合无状态，但撤销/顶号需要额外状态（如 `session_id`）。
- 权限模型：RBAC（角色）、ABAC（属性）、资源归属校验（owner）。
- **IDOR**：只校验登录，不校验资源是否属于当前用户；`GET /config?userId=2` 可越权读取。

**项目对照**：

- Python 侧角色/时间线/故事节点部分接口无鉴权；`userConfig` 接受任意 `userId`，存在 IDOR。[项目]
- Java 侧大量 `permitAll` + 默认 `userId=1L`，未带 token 的请求可能以固定用户身份执行。[项目]
- 后台独立 token scope + 独立 session，用户端 token 不能访问后台接口，后台 token 也不能访问用户端接口。[项目]

### 8.4 常见 Web 安全风险

| 风险 | 说明 | 防护 |
|---|---|---|
| SQL 注入 | 拼接 SQL | 参数化查询/ORM 绑定 |
| XSS | 不可信 HTML 注入 | 输出编码、DOMPurify、CSP |
| CSRF | 借用 Cookie 发请求 | CSRF token、SameSite、校验 Origin |
| 路径穿越 | `../` 读写任意文件 | 规范化路径 + 白名单根目录 |
| 任意文件上传 | 可执行/超大文件 | 类型/大小/内容校验、隔离存储、重命名 |
| SSRF | 服务端请求任意 URL | 目标白名单、禁内网、DNS 重绑定防护 |
| 敏感信息泄露 | 日志/错误/响应带密钥 | 脱敏、统一错误、密钥管理 |
| 越权 | 水平/垂直 | 每个资源校验 owner/role |

**项目对照**：

- `/chat/regenerate` 的 `sessionId` 若未校验格式，可能通过 `../` 读写任意链文件；修复是白名单/正则 + 根目录约束。[项目]
- 上传接口若先读入内存再校验大小、且无鉴权，会被大文件/匿名请求打爆；应先校验 `Content-Length`/流式限制 + 鉴权。[项目]
- CORS 若 `allow_origins=["*"]` 且 `allow_credentials=True`，浏览器会拒绝通配，且配置本身危险；应明确来源白名单。[项目]

### 8.5 密钥与配置

- 密钥只放环境变量/密钥管理，不进仓库、不进前端包、不进日志。
- `.env` 是本地真实凭据，禁止读取/提交；只参考 `.env.example`。
- 配置缺失要**启动失败或明确降级**，不要用不安全的默认值（如默认管理员、默认 JWT 密钥）。

## 9. 代码质量、测试与调试入门

### 9.1 可读性

- 命名表达意图：`pageSize` vs `page_size` 的口径差异要在边界统一，不能靠猜。[项目]
- 函数短小、单一职责；复杂条件提取为有名字的布尔变量。
- 早返回减少嵌套；错误分支优先处理。
- 注释解释"为什么"，不重复"是什么"。

### 9.2 测试的最小认知

- 单测：函数/模块，快速、隔离。
- 集成测试：路由+DB+缓存，验证契约和事务。
- E2E：真实浏览器/真实服务，验证用户路径。
- 测试要有**断言**：状态码 + 业务码 + 数据 + 副作用；只打印不 assert 是假测试。[项目]

详细见 [06 卷](./06-测试调试与质量保障.md)。

### 9.3 调试的基本方法

```text
1. 稳定复现：记录环境、账号、输入、时间、请求 ID
2. 缩小范围：前端/网络/后端/DB/下游，逐层排除
3. 形成假设：一次只验证一个变量
4. 收集证据：日志、断点、HAR、SQL、堆栈、监控
5. 修复根因：不是只消除症状
6. 回归验证：原场景 + 相邻场景 + 自动化
```

**反模式**：

- 看到报错就重启/清缓存，不记录现象。
- 同时改多个地方，无法判断哪个生效。
- 只验证成功路径，不验证失败/边界/并发。
- 把"日志里没报错"当成"没有问题"。

|---|---|---|---|

## 12. 面试表达与追问

### 12.1 60 秒回答模板

> "这个问题本质是 ___。它的机制是 ___。在本项目中，我遇到的具体场景是 ___，现象是 ___，我用 ___ 取证，根因是 ___，修复/取舍是 ___。如果规模变大，我会 ___。"

示例（竞态）：

> "本质是异步结果与当前 UI 状态不一致。请求 A 发出后用户切到会话 B，A 的响应回来仍写入当前视图，就会串台。项目里流式聊天用 AbortController + 会话 ID/请求序号双重校验；切换时先取消旧流，回调里再比对 sessionId。取舍是增加一点状态管理复杂度，换来不会污染新会话。"

### 12.2 常见追问

1. **为什么不用 `==`？** 类型转换规则复杂，容易出 `0 == ""`；统一 `===`，仅 `== null` 兼容空值。
2. **闭包会内存泄漏吗？** 会持有外部变量；如果闭包长期存活且引用大对象/DOM，就泄漏。解决：解除监听、置空引用、缩短生命周期。
3. **Promise 和 async/await 区别？** async/await 是 Promise 的语法糖，便于顺序书写和 try/catch；本质仍是微任务。
4. **并发和并行区别？** 并发是任务重叠推进，并行是同时执行；单核可并发不可并行。
5. **GIL 下多线程有用吗？** I/O 密集有用（等待时释放 GIL）；CPU 密集用多进程。
6. **事务应该放哪层？** 服务层，围绕一个业务用例；不要在 DAO 每个方法里自动 commit。
7. **401 和 403 区别？** 未认证 vs 已认证但无权限；前端处理也不同。
8. **如何保证接口幂等？** 幂等键 + 唯一约束/去重表 + 状态机；重试只对幂等操作。
9. **如何排查内存泄漏？** 复现增长 → 堆快照对比 → 找 retained size 最大的对象/监听器 → 修复 → 压测回归。
10. **为什么需要超时？** 资源有限；无超时会耗尽线程/连接，引发雪崩。

### 12.3 反例：这样回答会减分

- "加个 `try/catch` 就好了"——没有错误分类和可观测性。
- "重启一下"——没有根因。
- "这是框架的 bug"——没有最小复现和版本证据。
- "用了 Redis 所以快"——没有命中率、P95、降级策略。
- "用了 JWT 所以安全"——没有撤销、过期、存储、越权讨论。
