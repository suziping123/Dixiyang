# 06 · 测试、调试与质量保障

> **定位**：把"我觉得没问题"变成"有证据、可重复、可回归"。这是评测岗的日常方法论。
> **层级**：L1-L7
> **对应岗位能力**：复现、取证、归因、写测试、设计门禁、判断真假修复。


> **来源约定**：未标来源的段落为通用技术知识；标 `[项目]` 的有仓库代码/脚本/文档依据；`[项目-冲突]` 表示材料互相矛盾；`[推断]`/`[待确认]` 表示分析或尚需验证。

---

## 1. 测试体系

### 1.1 测试金字塔

```text
        E2E（少、慢、真实）
      integration（接口/DB/缓存）
    unit（多、快、隔离）
```

| 层 | 目标 | 工具示例 | 优点 | 缺点 |
|---|---|---|---|---|
| 单元 | 函数/模块逻辑 | pytest、Vitest | 快、定位准 | 不验证集成 |
| 集成 | 路由+DB+缓存 | pytest + TestClient、Testcontainers | 契约/事务 | 环境复杂 |
| E2E | 用户路径 | Playwright/Cypress | 真实 | 慢、易 flaky |
| 契约 | 前后端字段 | schema 测试、OpenAPI diff | 防漂移 | 需维护 |
| 静态 | 类型/lint | mypy/tsc/eslint/ruff | 早期发现 | 不能证明行为 |

### 1.2 测试要验证什么

- 正常路径：输入→输出。
- 边界：空、0、1、最大长度、特殊字符、时区。
- 失败：非法输入、依赖失败、超时、权限。
- 副作用：DB 写入、文件、缓存、消息。
- 并发：重复提交、竞态、锁。
- 回归：历史 bug 不再出现。

### 1.3 测试 oracle

"预期结果"从哪来？

- 需求/契约；
- 现有正确实现；
- 手工计算；
- 属性（排序后有序、总额守恒）；
- 快照（谨慎，易掩盖变化）。

没有明确 oracle 的测试容易变成"跑通即通过"。

## 2. 单元、集成、E2E 实践

### 2.1 pytest

```python
import pytest
from app.services.price import total

def test_total_empty():
    assert total([]) == 0

def test_total_basic():
    assert total([{"price": 10, "qty": 2}]) == 20

@pytest.mark.parametrize("items,expected", [
    ([], 0),
    ([{"price": 1, "qty": 1}], 1),
])
def test_total_param(items, expected):
    assert total(items) == expected

def test_invalid_raises():
    with pytest.raises(ValueError):
        total([{"price": -1, "qty": 1}])
```

- fixture 管理临时 DB/客户端/登录态；`yield` 清理。
- `monkeypatch` 替换环境变量/时间/外部调用。
- 参数化覆盖边界，减少重复。
- 断言具体值/异常类型，不只 `assert result`。

### 2.2 FastAPI TestClient

```python
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_health():
    r = client.get("/docs")
    assert r.status_code == 200

def test_login_required():
    r = client.get("/api/rag/stats")
    assert r.status_code == 401
```

- 集成测试要覆盖鉴权、业务码、数据副作用。
- 测试 DB 用独立库/事务回滚；不要污染开发数据。
- 外部服务用 mock/容器；不要让测试依赖真实 LLM/网络。

### 2.3 Vitest

```ts
import { describe, it, expect, vi } from "vitest";
import { unwrap } from "./api";

describe("unwrap", () => {
  it("returns data on success", () => {
    expect(unwrap({ code: 200, data: { id: 1 }, msg: "" })).toEqual({ id: 1 });
  });

  it("throws on business error", () => {
    expect(() => unwrap({ code: 500, data: null, msg: "boom" })).toThrow("boom");
  });
});
```

- 组件测试用 `@vue/test-utils`；断言渲染/emit/交互。
- 定时器用 fake timers；网络用 mock。
- 不要只测实现细节（内部变量）；测行为。

### 2.4 E2E

```ts
import { test, expect } from "@playwright/test";

test("login and open rag", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("账号").fill("admin123");
  await page.getByLabel("密码").fill("123456");
  await page.getByRole("button", { name: "登录" }).click();
  await expect(page).toHaveURL(/home/);
  await page.goto("/rag-knowledge");
  await expect(page.getByRole("table")).toBeVisible();
});
```

- 用真实测试账号；注意登录风控/顶号。
- 选择器用 role/label，少用脆弱 CSS。
- 等待网络/元素，不用固定 `sleep`。
- 失败保存截图/trace/video。

## 3. Mock、Fixture、Flaky 与覆盖率

### 3.1 Mock 的边界

- Mock 外部不稳定依赖（邮件、LLM、支付、第三方 API）。
- 不要 mock 被测逻辑本身，否则测试无意义。
- Mock 要验证调用参数/次数；只返回假数据不够。
- 过度 mock 会让集成问题漏掉；关键路径保留真实集成测试。

```python
def test_send_code(monkeypatch):
    called = {}
    def fake_send(email, code):
        called["email"] = email
        called["code"] = code
    monkeypatch.setattr("app.services.mail.send", fake_send)
    ...
    assert called["email"] == "a@b.com"
```

### 3.2 Fixture

- 数据库 schema/种子数据/登录 token/临时目录。
- 作用域：function（隔离）vs session（快但易污染）。
- 清理必须可靠；异常也要执行。
- 测试数据要可读、最小、与用例相关。

### 3.3 Flaky 测试

| 原因 | 表现 | 解决 |
|---|---|---|
| 时间 | 依赖当前时间/时区 | 注入时钟/固定时区 |
| 随机 | 未固定 seed | 固定 seed |
| 网络 | 真实外部调用 | mock/容器 |
| 并发 | 共享状态/端口 | 隔离/随机端口 |
| 等待 | `sleep` 不够/太久 | 条件等待/重试 |
| 顺序 | 测试互相依赖 | 独立数据/清理 |

**处理原则**：flaky 是缺陷，不是"重跑就好"；要定位根因并隔离。

### 3.4 覆盖率

- 行覆盖/分支覆盖只是"执行过"，不代表断言正确。
- 高覆盖但弱断言 = 假安全感。
- 关注关键路径/错误分支/边界，不追求 100%。
- 覆盖率下降要审查；但不要为了数字写无意义测试。

### 3.5 假测试识别（评测岗高频）

| 信号 | 问题 |
|---|---|
| 只 `print` 不 assert | 永远通过 |
| 断言 `status in (200,500)` | 失败也通过 |
| 捕获所有异常不失败 | 掩盖错误 |
| 只测 mock 返回 | 没测真实逻辑 |
| 删除/跳过失败测试 | 作弊 |
| 测试与实现完全耦合 | 改实现就碎，没测行为 |

**项目对照**：`tests/api_test.sh` 使用错误账号、弱断言、`sed` 解析脆弱；这类脚本不能作为质量门禁。[项目]

## 4. 静态检查与代码评审

### 4.1 工具链

| 层 | 工具 |
|---|---|
| Python 类型 | mypy/pyright |
| Python 风格 | ruff |
| JS/TS 类型 | vue-tsc/tsc |
| JS/TS 风格 | eslint |
| 格式 | prettier/ruff format |
| 安全 | bandit/npm audit |
| 依赖 | lockfile/依赖扫描 |

### 4.2 评审重点

- 正确性：边界/错误/并发/权限。
- 契约：字段/状态码/分页/鉴权。
- 可维护性：命名/分层/重复/复杂度。
- 测试：是否覆盖失败/边界；断言是否有效。
- 安全：输入/路径/上传/日志/密钥。
- 性能：N+1/大循环/无缓存/阻塞。
- 可观测性：日志/指标/错误信息。

### 4.3 Diff 审查

```bash
git diff --stat
git diff --check          # 空白错误
git diff --staged
git log --oneline -5
```

- 先看范围：是否改了不相关文件。
- 再看关键逻辑：鉴权/事务/路径/并发。
- 最后看测试：是否真的验证行为。
- 警惕调试残留：`console.log`、`print`、临时开关、硬编码。

## 5. 日志、指标与追踪

### 5.1 日志

```python
logger.info("request", extra={
    "request_id": rid,
    "user_id": uid,
    "path": path,
    "status": status,
    "duration_ms": ms,
})
```

- 结构化、可检索；包含请求 ID。
- 错误日志带堆栈；业务日志带关键上下文。
- 脱敏：token/密码/邮箱/手机号/prompt 隐私。
- 日志级别合理；不要用日志当数据库。

### 5.2 指标

- RED：Rate、Errors、Duration。
- USE：Utilization、Saturation、Errors（资源）。
- 业务：登录成功率、RAG 空召回率、聊天完成率、上传失败率。
- 分位数 P50/P95/P99；平均值会掩盖长尾。

### 5.3 追踪

- trace ID 贯穿前端→网关→后端→DB/下游。
- span 记录耗时/状态/参数（脱敏）。
- SSE/流式记录开始/首 token/结束/取消。
- 前端 HAR 与后端 trace 关联。

### 5.4 告警

- 告警要可行动：阈值 + 影响 + 排查链接。
- 避免告警疲劳；分层（P0/P1/P2）。
- 错误率/延迟/队列/磁盘/证书过期。
- 告警后要有 runbook。

## 6. 调试方法论

### 6.1 六步法

```text
1. 稳定复现：环境/账号/输入/时间/请求 ID
2. 缩小范围：前端/网络/后端/DB/下游
3. 提出假设：一次只验证一个
4. 收集证据：日志/断点/HAR/SQL/堆栈/监控
5. 修复根因：不是消除症状
6. 回归验证：原场景+相邻+自动化
```

### 6.2 分层排查表

| 层 | 检查 |
|---|---|
| 浏览器 | Console、Network、Application、Performance |
| 前端代码 | 路由/状态/请求参数/渲染条件 |
| 网络/代理 | URL/Method/Header/Body/状态码/超时 |
| 后端路由 | 是否命中、鉴权、参数校验 |
| 服务层 | 业务分支、异常、事务 |
| DB/缓存 | 数据、索引、锁、连接 |
| 文件/下游 | 路径、权限、磁盘、超时 |
| 部署 | 版本、环境变量、端口、进程 |

### 6.3 二分与对照

- `git bisect` 找回归提交。
- 注释/开关二分定位代码。
- 对照组：正常账号/正常数据/正常环境。
- 最小复现：去掉无关依赖，保留触发条件。

### 6.4 对账

```text
DB 全量行 vs 磁盘文件：缺失/孤儿
前端显示 vs 接口响应：字段/分页/业务码
接口响应 vs DB：写入/事务/缓存
日志时间 vs 请求时间：时区/延迟
```

**项目案例**：文件缺失排查不能只看一个方向；DB 有文件无 = 缺失，文件有 DB 无 = 孤儿；两边都查才能下结论。[项目]

### 6.5 证据链

一次可信的 bug 报告应包含：

- 环境/版本/账号；
- 复现步骤；
- 期望/实际；
- 请求/响应/日志/截图；
- 根因（文件/函数/行）；
- 修复/验证；
- 影响范围/回归。

### 6.6 常见误判

- 把缓存当数据：清缓存后现象消失，不等于后端修好。
- 把前端当后端：页面没显示可能是接口失败。
- 把业务码当 HTTP：200 不代表成功。
- 把日志缺失当无错误：可能被吞。
- 把一次成功当稳定：并发/边界未测。

## 7. 安全、性能与回归

### 7.1 安全测试

- 未登录/过期 token/越权账号。
- 水平越权：改 `userId/novelId` 访问他人资源。
- 垂直越权：普通用户访问管理接口。
- 路径穿越：`../`、URL 编码、绝对路径。
- 上传：超大/伪造类型/双扩展名/压缩炸弹。
- 注入：SQL/命令/模板/XSS。
- 敏感信息：错误响应/日志/前端包/URL。
- CORS/CSRF/SSRF。

### 7.2 性能测试

- 明确目标：吞吐/延迟/并发/资源。
- 负载模型：固定并发/阶梯/峰值；思考时间。
- 指标：P50/P95/P99、错误率、吞吐、CPU/内存/连接池。
- 数据规模要接近真实；小数据集结论不能外推。[项目]
- 压测环境隔离；避免打生产。
- 结果给边界/限制，不只给最好数字。

### 7.3 回归

- 每次修复加回归用例。
- 回归集覆盖历史 badcase/高风险路径。
- 版本升级/依赖升级跑全量回归。
- 回归失败阻断发布。

### 7.4 发布门禁

```text
lint + type-check
→ 单测
→ 集成测试
→ 构建
→ 安全扫描
→ E2E 冒烟
→ 灰度/回滚预案
```

- 门禁要快、稳定、可复现；flaky 测试不能长期阻塞。
- 关键路径必须有测试；不是所有代码都要求 100%。
- 发布记录版本/变更/回滚点。

## 8. 项目实战

### 8.1 可复现命令

```bash
# 后端编译/导入检查
cd DixyangFast && uv run python -m compileall src

# 前端类型/构建
cd dixiyang-vue/Dixiyang-vue3 && npm run type-check && npm run build-only

# 后端健康（8084）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8084/docs

# 登录拿 token（测试账号）
curl -s -X POST http://127.0.0.1:8084/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin123","password":"123456"}'
```

**注意**：

- 真实登录，禁伪造 token；10 分钟 3 次密码登录触发验证码。
- 8084 RAG 是嵌入式 Chroma；停 8000 不影响 8084 检索。[项目]
- 复现 500 可用坏 `CHROMA_PERSIST_DIR`，测完恢复。

### 8.2 项目缺陷测试设计

| 缺陷 | 测试 |
|---|---|
| 分页字段漂移 | 用 `pageSize=20` 请求，断言返回 20 条；用默认断言 10 条 |
| 业务 500 假成功 | mock 返回 `{code:500}`，断言页面提示错误 |
| 401/403 | 普通 token 访问后台，断言 403 不登出 |
| 竞态 | 快速切换会话，断言旧响应不写入 |
| 路径穿越 | `sessionId=../x`，断言 400/403 |
| 上传超限 | 超大小文件，断言 413/400 且内存不暴涨 |
| 链文件并发 | 两请求同时写，断言消息不丢/不交错 |
| 移动端 | 375 视口断言无横向溢出/双列 |

### 8.3 评测岗的测试审查

看到一份测试，问：

1. 有没有断言？断言是否可能永远为真？
2. 是否覆盖失败/边界/权限？
3. 是否依赖真实网络/时间/顺序？
4. 是否删了/跳过了失败用例？
5. 是否能复现历史 bug？
6. 测试失败时，能否定位到具体行为？

## 9. 高频追问

1. **单测和集成测试边界？** 单测隔离依赖测逻辑；集成测路由/DB/缓存/契约。
2. **覆盖率越高越好吗？** 不是；关键路径/断言质量更重要。
3. **如何测并发？** 固定 seed/屏障/多线程/重复运行；断言不变量，避免只测一次。
4. **如何测时间？** 注入时钟/冻结时间/固定时区。
5. **如何处理 flaky？** 定位根因（时间/网络/顺序/并发），隔离/重试只暂时缓解。
6. **如何测 LLM/RAG？** 固定模型/数据/配置；检索指标+生成评分+人工抽检；mock 只测工程链路。
7. **如何做回归？** 历史 badcase 入库，自动化，版本门禁。
8. **如何判断假修复？** 看 diff/测试/真实请求/副作用；不能只看"测试绿"。
9. **日志和指标怎么分工？** 日志定位个体，指标看趋势/告警。
10. **压测结果怎么讲？** 给环境/数据/负载/分位数/限制，不外推。
