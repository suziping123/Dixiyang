## 1. 项目定位与全景

Dixiyang 是一个小说创作管理平台，核心能力：

- 小说/卷/章节/角色/时间线/故事节点管理；
- AI 聊天（流式、工具调用、重新生成、编辑修正）；
- RAG 知识检索（Chroma + bge）；
- 灵感墙便签；
- 广场社区（发布/评论/点赞/收藏/推荐）；
- 独立管理后台（用户/内容/便签治理）。

### 1.1 运行时拓扑

```text
浏览器
 ├── 5173（Vite dev）──/api 代理──┐
 └── 8080（Nginx/Docker）────────┼──→ Python FastAPI 8084（主后端）
                                  │      ├── MySQL 3306
                                  │      ├── Redis 6379（可选，自动降级）
                                  │      ├── uploads/（图片/文件/JSON 存储）
                                  │      └── 嵌入式 Chroma（8084 进程内）
                                  │
                                  └──→ RAG 服务 8085（可选）
                                         ├── ChromaDB Server 8000
                                         └── Embedding/Reranker
```

### 1.2 主/备后端

| 实现 | 技术 | 端口 | 状态 |
|---|---|---|---|
| `DixyangFast` | Python 3.11 + FastAPI | 8084 | **主后端，当前使用** |
| `dixiyang-engine` | Java 17 + Spring Boot 3.4 | 8084 | 历史并存实现，当前未使用，二选一 |
| `DixyangFast/python_api` | Python + Chroma HTTP | 8085 | RAG/Embedding 独立服务 |

**注意**：

- Java 与 Python 同占 8084，不能同时启动。
- Java 侧能力并非全部与 Python 等价；跨后端契约存在漂移（见 §13）。
- `README.md` 已明确 Java 未使用；`docs/系统总览.md` 仍写 Java 8084 生产/Python 8085，属于过期描述。[项目-冲突]

## 4. 后端请求链路

### 4.1 典型请求

```text
浏览器 /api/novel/listall?page=1&pageSize=10
 → Vite/Nginx 代理到 127.0.0.1:8084
 → FastAPI 路由 novel.list_all
 → Depends(get_current_user_id) 解 JWT/sid
 → Depends(get_db) 创建 Session
 → NovelService 查询
 → Result.success(...)
 → JSON
```

### 4.2 统一响应

```json
{ "code": 200, "msg": "成功", "data": ... }
```

- 成功/业务失败都可能 HTTP 200；前端必须检查 `code`。
- 部分接口用 `HTTPException`（401/403/404），部分用 `Result`；契约不完全统一。[项目]
- 这会导致：监控按 HTTP 状态看不到业务失败；前端只 unwrap data 会把失败当成功。

### 4.3 鉴权依赖

```text
Authorization: Bearer <JWT>
 → 解 payload: sub(userId), sid(sessionId), scope
 → 查 app_user.session_id / admin_session_id
 → 不匹配 401（顶号）
 → scope=admin 只能访问后台接口
 → scope=user 不能访问后台接口
```

**现状**：

- 用户端与后台 token 隔离；后台登录不顶用户端。[项目]
- 但部分业务路由未加鉴权依赖（角色/时间线/故事节点），匿名可访问。[项目]
- `user_config` 接受任意 `userId`，存在 IDOR。[项目]

## 6. 认证、单点登录与权限

### 6.1 登录

```text
POST /api/auth/login { username, password }
 → 查 app_user
 → 校验密码
 → 风控检查（10 分钟窗口，第 3 次触发验证码）
 → 生成 session_id，覆盖写 app_user.session_id
 → 签发 JWT（sub/sid/scope/exp）
 → 返回 token/username/userId/nickname/email/role
```

### 6.2 单点登录

- 同一账号后登录覆盖 `session_id`，旧 token 下次请求 401。
- 旧 token 无 `sid` 时兼容放行至过期（避免升级后全员重登）。[项目]
- 前端收到 401 清会话、跳登录、提示原因。

### 6.3 风控

| 项 | 值 |
|---|---|
| 窗口 | 10 分钟 |
| 阈值 | 3 次成功密码登录 |
| 后果 | 要求邮箱验证码 |
| 解除 | 验证码登录成功 |

**测试注意**：

- 频繁登录会触发风控；验证时用测试账号，必要时等待/走验证码。
- 单点登录会顶号；不要用他人正在使用的账号。

### 6.4 后台隔离

```text
用户端：token + session_id + scope=user
后台：  admin_token + admin_session_id + scope=admin
```

- 后台独立入口 `admin.html`、独立路由/壳/样式。
- 用户端 token 访问 `/api/admin/**` → 403。
- 后台 token 访问用户端接口 → 403。
- 登后台不顶用户端；用户端重登也不影响后台。[项目]

### 6.5 权限缺陷

| 缺陷 | 影响 |
|---|---|
| 角色/时间线/故事节点无鉴权 | 匿名读写 |
| `user_config` 任意 userId | IDOR |
| Java `permitAll` + 默认 userId=1 | 匿名以固定用户执行 |
| 前端角色判断 | 可篡改，不能作为安全边界 |
| CORS 通配 + credentials | 配置无效/风险 |

## 7. 聊天、SSE 与链文件

### 7.1 流式链路

```text
前端 POST /api/chat/stream
 → 后端构建 messages（系统 prompt + 历史 + edits + RAG 工具）
 → LLM stream（Flux/异步生成器）
 → 逐 token SSE：type=content/thinking
 → 前端增量渲染
 → 完成后追加链文件
```

### 7.2 重新生成

```text
POST /api/chat/regenerate { sessionId, messageIndex }
 → 校验 session
 → 截断链（保留前 N 条）
 → 用截断历史 + edits 构建 prompt
 → 流式生成
 → 追加新回答
```

**风险**：

- `sessionId` 未严格校验时可能路径穿越。[项目]
- 截断后生成失败会丢失原回答；应先备份/事务化。
- 并发重新生成会互相覆盖。

### 7.3 编辑修正

- 用户编辑 AI 回答 → 写入 `edits.json` + 替换链中消息。
- 下次请求把修正记录注入 system prompt，让模型学习偏好。
- 编辑记录要版本化/可审计；当前是追加 JSON。

### 7.4 摘要

- 历史过长时生成 `summary.json`，压缩早期对话。
- 已知缺陷：摘要可能漏掉第 7-12 条消息，导致上下文丢失。[项目]
- 摘要是有损压缩；关键事实/约束要保留原文。

### 7.5 并发/取消

- 前端 `AbortController` 取消；后端应检测断开。
- 旧流回调必须校验 `sessionId`/请求序号，否则写入新会话。[项目]
- Java SSE 每请求线程池 + 无超时 + `sendEvent` 吞异常，资源风险高。[项目]

## 8. RAG 实现

### 8.1 两套服务

| 服务 | 端口 | Chroma 访问 | 用途 |
|---|---|---|---|
| 主后端 | 8084 | 嵌入式 `PersistentClient` | `/api/rag/*` 检索/统计 |
| RAG 服务 | 8085 | HTTP `localhost:8000` | Embedding/Rerank/健康 |

### 8.2 数据与配置

| 项 | 值/说明 |
|---|---|
| 集合 | `dixiyang_knowledge` |
| 距离 | `cosine` |
| 文档规模 | 70458 chunks（文档示例） |
| Embedding | 文档 `BAAI/bge-m3`；共享默认 `bge-small-zh-v1.5`，以实际配置为准 |
| 切分 | 600 / overlap 120 / min 50（离线示例） |
| 召回 | `topK * 4`，上限 100 |
| Rerank | `BAAI/bge-reranker-base`，`/api/rag/rerank` |

### 8.3 路径冲突

至少三处默认路径/集合：

| 位置 | 默认 |
|---|---|
| `routers/rag.py` | `./storage/vectordb_4060` |
| `services/knowledge_search_tool.py` | `./chroma_db` |
| `services/novel_tools.py` | `./chroma_db` |
| `config.py` | `./chroma_db` |
| `rag-shared/config.py` | 配置/环境变量 |

**后果**：同一进程不同工具可能查不同库；表现为"统计有数据但检索为空"。[项目]

### 8.4 已知缺陷

- rerank 工具调用 `/api/rerank`（错误），正确是 `/api/rag/rerank`；404 后静默回退。[项目]
- 无 golden set/评估集，效果无法量化。
- 无引用校验/权限过滤。
- 离线资产缺失时无法重建。
- 嵌入式 vs HTTP 混用，多实例数据不共享。

### 8.5 复现

## 9. 广场、Redis 与便签

### 9.1 广场

- 帖子/草稿/附件/标签/点赞/收藏/评论/图片 8 张表。
- 推荐：Redis ZSET 热度 + 时间衰减 + 标签加成；热门按 ZSET；详情浏览去重 + 延迟计数。
- Redis 不可用：3s 冷却回源 DB，业务不挂。[项目]

### 9.2 Redis 一致性

- 浏览增量 `view_take` 若先 `DEL` 再业务 commit，commit 失败会丢增量。[项目]
- 缓存穿透/击穿/雪崩要有策略。
- 压测结论边界：小数据集 SQLite，不能外推生产容量；P95 提升 5 倍、吞吐 +71% 是特定环境数字。[项目]

### 9.3 便签

- 便签墙支持新建/编辑/完成/删除/颜色/拖拽。
- `sticky_note.done` 通过启动补列加入。[项目]
- 乐观更新失败不回滚会导致"假保存"。[项目]
- 每日清理孤儿文件/空目录。

## 10. 前端架构

### 10.1 入口与状态

- `main.ts` 挂载应用；演示模式先 `await` 安装 mock 适配器，避免首个请求泄漏到真实后端。[项目]

### 10.2 关键交互

| 功能 | 实现 | 风险 |
|---|---|---|
| 聊天流 | `useChatStream` + fetch SSE | 会话竞态/401 |
| RAG 助手 | 会话/小说选择 + 流式 | `pageSize`/竞态 |
| 知识库 | 文档列表/搜索 | 业务 500 静默 |
| 时间线 | 节点/事件 | 字符串逐字渲染 |
| 小说编辑 | 卷/章/内容 | 章节切换竞态 |
| 灵感流 | 瀑布流/游标 | 递归请求 |
| 便签 | 拖拽/乐观更新 | 失败不回滚 |
| 后台 | 独立 token/多页签 | 403 误登出 |

### 10.3 移动端

- 断点 768；弹窗全局贴底抽屉。
- FAB 右侧避让 64px；双列 `minmax(140px, 1fr)`。
- 筛选组各自横滑；禁止整行长组撑破 375。
- 输入 ≥16px 防 iOS 放大。
- 验收必须 375 截图肉眼复核。

### 10.4 演示模式

- `VITE_DEMO=1` 使用 mock 适配器；用于 GitHub Pages/展示。
- 演示登录任意账号直通；后台也有演示入口。
- **评测注意**：演示模式不是生产缺陷；但生产/真实交付出现 mock、硬编码、假请求就是 P0。

## 16. 面试怎么讲这个项目

### 16.1 30 秒版本

> "这是一个 Vue3 + FastAPI 的小说创作平台，包含 AI 聊天、RAG、广场和独立后台。我主要做了全栈实现和缺陷治理：比如聊天流的会话竞态、RAG 的 Chroma 部署形态、后台会话隔离、移动端适配。项目里也保留了一些真实缺陷作为评测样例，比如业务 500 被前端当成功、路径穿越、链文件并发。"

### 16.2 3 分钟版本（结构）

1. 业务与用户：谁用、解决什么。
2. 架构：前端/后端/DB/Redis/RAG/部署。
3. 难点：流式竞态、RAG 路径、鉴权隔离、并发写。
4. 证据：具体文件/接口/日志/测试。
5. 取舍：文件存储 vs DB、嵌入式 vs 服务化、前端 mock vs 真实。
6. 反思：哪些是历史债、怎么改。

### 16.3 追问

1. 为什么 Python 主后端、Java 备用？——历史并存，统一端口；当前以 Python 为准。
2. 为什么聊天存文件不存 DB？——大文本/追加写/避免行膨胀；代价是一致性。
3. 为什么 RAG 两套服务？——8084 嵌入式便于单机；8085 提供 embedding/rerank；应统一配置。
4. 怎么保证后台隔离？——独立入口/token/session/scope + 后端校验。
5. 怎么发现假实现？——Network/DB/刷新/权限/边界/轨迹，不只看页面。
6. 项目最大的技术债？——契约不统一、鉴权缺口、链文件并发、缺评估集。
