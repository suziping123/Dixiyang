# Redis 优化效果对比（JMeter 压测）

## 需求
量化 Redis 接入（频控 TTL / 热门 ZSET / 浏览去重+增量回写）对广场读接口的性能收益，产出可见对比。

## 压测方案
- 工具：JMeter 5.6.3 CLI（`idea_bench.jmx`）
- 负载：20 线程 × 100 轮 × 3 接口 = 每轮 6000 请求，**零思考时间**（压吞吐上限），每态先 5 线程×10 轮预热（不计入）
- **每态 3 轮独立运行，报 3 轮合并分位数 + 各轮吞吐中位数**（非单次抽样）
- 目标接口（均为 GET，免登录）：
  - `GET /api/idea/posts?sort=recommend`（综合推荐：ZSET 热度×时间衰减+标签加成）
  - `GET /api/idea/posts?sort=hot`（热门：ZSET 排序）
  - `GET /api/idea/posts/{id}`（详情：浏览去重+Redis 延迟计数）
- 双态：**UP** = Redis 6379 运行；**DOWN** = kill redis-server，后端走内存降级路径（3s 冷却快速失败回源 DB）

## 环境与数据规模（必须连同结论一起读）
- Windows 11 本机 + **SQLite**（单写锁）+ FastAPI 单进程；Redis 5.x Windows 版
- 数据量：**published 帖 49 条**、ZSET `idea:hot` 49 成员——**小数据集**，DB 排序成本低；生产 MySQL/PG 多连接池下 DOWN 态长尾大概率低于本文数值，UP/DOWN 差距方向不变但倍数会收窄
- 未采集：Redis QPS/延迟分布、DB CPU/IO/慢查询、连接池、进程 CPU/内存——本对比只度量**端到端 HTTP 延迟与吞吐**

## 结果（2026-10-10，每态 3 轮 × 6000 = 18000 样本，0 错误）

### 吞吐（各轮 req/s，取中位）
| 态 | 第1轮 | 第2轮 | 第3轮 | 中位 | 变化 |
|----|-------|-------|-------|------|------|
| UP | 59.8 | 69.0 | 67.6 | **67.6** | — |
| DOWN | 40.8 | 39.6* | 32.7 | **39.6** | **基线（UP +71%）** |

*DOWN 第 2 轮含一次超时续写残留，样本截半清洗后使用。

### 延迟（3 轮合并，ms）
| 接口 | UP 中位 | UP P95 | UP P99 | DOWN 中位 | DOWN P95 | DOWN P99 | P95 提升 |
|------|---------|--------|--------|-----------|----------|----------|----------|
| 推荐 recommend | 311 | **379** | 420 | 333 | 1852 | 1917 | **4.9×** |
| 热门 hot | 303 | **371** | 405 | 336 | 1861 | 1919 | **5.0×** |
| 详情 view | 300 | **368** | 407 | 318 | 1844 | 1897 | **5.0×** |

### Redis 侧
- keyspace 命中率：18246 hits / 1 miss = **99.99%**（UP 态 18000 请求仅 1 次 miss）

## 结论
1. **中位数差距小（~5%），P95/P99 差 5 倍**——Redis 的收益不在平均路径而在**消除长尾**：DOWN 态热门全表排序 + 浏览同步 commit 在并发下排队，P95 从 ~370ms 恶化到 ~1.85s；UP 态这些写全部进 ZSET/延迟队列，DB 只在 60s 周期批量回写，延迟分布收窄。
2. **吞吐 +71%**（67.6 vs 39.6 req/s）：本压测为闭环负载（20 线程固定），吞吐由响应时间决定，本质仍是同一收益的另一面——**不是系统极限吞吐对比**（要测极限需阶梯加压找拐点，未做）。
3. **降级铁律成立**：Redis 挂掉后 18000 请求 0 错误，业务全可用（3s 冷却防雪崩），代价仅性能回退。
4. **附加收益（非本次度量项）**：频控 TTL 跨重启不丢/多实例共享；浏览 600s 去重减少无效计数写；DB 写入量下降（每详情请求 DB 0 commit vs 1 commit）。

## 本对比的边界（诚实声明）
- **负载属小基准非容量测试**：20 线程、每接口 6000 样本，足够看出数量级差距，不足以标定容量上限
- **单机 SQLite 放大了 DOWN 态长尾**：SQLite 单写锁使"每次请求一个 commit"的代价被放大，生产关系库差距会收窄
- **小数据集**（49 帖）：ZSET 与全表排序在 49 行上的差距远小于百万级数据
- **未做**：阶梯加压找拐点、稳定性长跑（>30min）、Redis/DB 侧资源监控、多机分布式

## 已知问题
- JMX 里 `${threads}` 直接写变量不解析，需用 `${__P(threads,20)}`（JMeter 属性函数）
- JMeter `-l` 输出默认 append，同一 jtl 跑两次会混样本；超时被杀的 JMeter 子进程可能续写完导致双份样本

## 验证方式
```powershell
# UP 态
D:\Redis\redis-server.exe D:\Redis\redis.windows.conf   # 或桌面 start_redis.bat
D:\apache-jmeter-5.6.3\bin\jmeter.bat -n -t idea_bench.jmx -l up1.jtl -Jthreads=20 -Jloops=100
# DOWN 态：kill redis-server 后
D:\apache-jmeter-5.6.3\bin\jmeter.bat -n -t idea_bench.jmx -l down1.jtl -Jthreads=20 -Jloops=100
```
