# 广场真瀑布流与增量加载

> 需求来源：用户反馈「广场没有实现真正的瀑布流，而且不应该需要加载全部内容」。
> 本文档记录广场 Tab 从「CSS multi-column 伪瀑布流 + 页码器」改为「手写短列优先真瀑布流 + 无限滚动游标分页」的全过程。

**版本**: v1.0 ｜ **日期**: 2026-10-10 ｜ **范围**: 仅广场 Tab（草稿箱/我发布的/我的收藏不动）

---

## 1. 需求与决策

### 1.1 两个问题
1. **伪瀑布流**：旧实现用 CSS `column-width`（multi-column），浏览器**按列灌内容**——先灌满第 1 列再灌第 2 列。视觉上是「竖着读」，不是小红书那种「新卡片进最短列、横向铺开」。且 multi-column 要求一次性拿到全部卡片才能平衡分列，**无法增量追加**（追加会导致整列重新平衡、卡片跳动）。
2. **需要加载全部内容**：页码器模式下要靠 `total`（后端每次 `COUNT` 全表）驱动，且翻页会把瀑布流「截断重排」。

### 1.2 技术选型决策（经评审确认）
| 决策点 | 结论 | 理由 |
|---|---|---|
| 瀑布流实现 | **手写短列优先算法（无第三方依赖）** | 调研发现：Vue3 生态最活跃的 `vue3-masonry-css` 底层**仍是 CSS columns**（README 原话 "powered by native CSS columns"），引入它等于换个马甲的伪瀑布流；真正短列优先的 `masonry-layout` 已 2018 年停止维护。手写约 60 行，行为完全可控。 |
| 加载模式 | **无限滚动（触底 append），删除页码器** | 每次只加载可视区 + 预取量，不再一次性拉全部 |
| 分页语义 | **后端游标 cursor 分页** | 深翻页不重不漏；`recommend` 排序例外（见 §2.3） |
| 改动范围 | **仅广场 Tab** | 草稿/我发布的/收藏是管理场景，保留页码器更好定位 |

## 2. 方案设计

### 2.1 后端：游标分页（`/idea/posts`）

**接口变更**：新增 `cursor` 查询参数（`str | None`）。响应统一新增 `hasMore`（`bool`），游标模式下新增 `nextCursor`（`str | None`）。

**排序 → 分页策略映射**：

| sort | 分页方式 | 游标内容 | 翻页条件 |
|---|---|---|---|
| `new` | 真游标 | `(createTime, id)` 元组 | `(create_time, id) < (游标值, 游标id)`，DB 元组比较 |
| `like` | 真游标 | `(likeCount, id)` 元组 | 同上，按 `like_count` |
| `hot` | 真游标 | ZSET 名次 `r` 或 `hot_score` | Redis 路径按榜单名次窗口前移；降级路径 DB `hot_score` 元组比较 |
| `recommend` | **保留页码** | 无 | 内存算法（时间衰减 + 个人兴趣分），**每请求分数都变**，游标无意义；候选池本就 ≤200 条，深翻没价值 |

**游标编解码**：`_enc_cursor` / `_dec_cursor`（`idea_service.py` 顶部）——`dict` → URL-safe base64（去 `=` 填充）。对前端不透明，格式可随时改。损坏游标 → `_dec_cursor` 返回 `None` → 当最后一页处理（`list=[]`, `hasMore=False`），前端下次触底自动停。

**性能优化**：游标模式（带 `cursor`）**跳过 `COUNT` 全表**；首页（`cursor=None`）仍返回 `total` 保持向后兼容。

**hot 排序凑批细节**：分区/搜索/标签会过滤掉榜内帖子，单窗口可能凑不满一页。`_cursor_page` 采用**逐段凑批**（`while idx < len(ranked) and len(matched) <= page_size`），防止过滤场景下提前误判「到底」。

### 2.2 前端：手写短列优先瀑布流（`IdeaLibraryView.vue`）

**布局算法**（`relayout()`）：
```
列数 cols = max(1, floor((容器宽 + gap) / (最小列宽 + gap)))
列宽 colW = (容器宽 - gap*(cols-1)) / cols
每张卡：选当前最矮列 col → left = col*(colW+gap), top = colY[col]
        列高 colY[col] += 卡高 + gap
容器高度 = max(colY)
```
- 断点常量：桌面 `最小列宽 220 / gap 14`；移动端(≤768) `140 / 10`
- 卡片 `position: absolute`，用 `left/top` 定位（**`transform` 留给 hover 动效**，避免互相覆盖）
- 容器 `position: relative` 作为定位锚点（防逃逸出层叠上下文——根 AGENTS 坑1）

**高度测量**：先给全部卡片写统一 `colW` 宽度，再读 `offsetHeight`（封面卡 3:4 定高，无封面卡文字不定高，必须定宽后量）。`ResizeObserver` 监听每张卡，高度变化（字体加载/图片）→ rAF 节流重排。

**无限滚动**：
- `IntersectionObserver` 监听哨兵 `.feed-sentinel`，`rootMargin: '600px 0px'` 提前预取
- `loadFeed(mode: 'reset' | 'more')`：`reset` 清空 cursor/hasMore 重拉第一页；`more` 带游标（recommend 带 page）追加
- **防并发**：`loadingMore` 锁 + `hasMore=false` 停更
- **防呆**：游标模式下 `cursor` 为空时禁止 `more`（防退化成页码模式反复拉第一页）
- **去重**：追加时按 `id` 过滤（recommend 深翻可能重复）
- **填满视口兜底**：`finally` 里若哨兵仍在视口内则继续 `more`（修复：首屏不足一屏时，IO 初次 observe 已在视口内但被 `loading=true` 挡掉，之后滚动状态不变不再触发）

**状态清理**：分区/排序/标签/搜索变化 → `resetFeed()`（清空 `posts`/`cursor`/`hasMore`/`page`）。

### 2.3 recommend 排序的特殊性

`recommend` 是内存算法：候选池 = 热度 Top200 ∪ 近 14 天新帖，分数含 48h 时间衰减（`now` 参与计算）+ 用户个人点赞/收藏兴趣标签加成。**每次请求分数都变**，拿「上一页最后一条的分数」当游标去切，和下一页重算的顺序对不上。故保留页码语义，前端用 `page++` 追加，靠 `id` 去重兜底。

## 4. 已知问题与边界

1. **`like` 排序深翻页微移**：游标按 `(likeCount, id)` 切，翻页过程中他人点赞会使排序键变动，可能漏/重一条。比现状（全靠 OFFSET 瞬切）好，站内量小无感知。
2. **`recommend` 深翻页可能重复**：内存算法每请求重算分，前端靠 `id` 去重兜底；候选池 ≤200 条，深翻无意义。
3. **无限滚动无页码跳转**：无法直达第 N 页（广场场景本就没人这么用）。
4. **图片加载后高度变化**：封面卡 3:4 `aspect-ratio` 定高，图片加载不改高度；无封面卡文字渲染后高度稳定。`ResizeObserver` 兜底重排，极端情况（字体晚加载）可能有一次重排。
5. **游标损坏兜底**：返回空 list + `hasMore=false`，前端停更；用户切筛选即恢复正常。
