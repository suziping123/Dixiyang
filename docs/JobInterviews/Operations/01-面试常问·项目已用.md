## Q1. 前后端端口体系怎么组织？代理链路怎么排障？

**代码**（项目 `vite.config.ts` + `start_backend.bat` 真实）：

```ts
// 前端唯一入口：/api → 8084（后端换语言/换实例，前端零改动）
server: {
  host: true,                 // 监听所有网卡：局域网设备用本机 IP 直接访问
  port: 5173,
  proxy: { '/api': { target: 'http://localhost:8084', changeOrigin: true } }
}
```
```bat
rem start_backend.bat —— 后端一键启动（Redis 连接串仅本地 dev，不入库）
cd /d %~dp0DixyangFast
set REDIS_URL=redis://:123321@127.0.0.1:6379/0
.venv\Scripts\python.exe src\dixiyang\main.py
```

**排障顺序（项目验证过的三步）**：
```powershell
# 1) 后端活着吗？（端口在听 = 进程 OK）
Get-NetTCPConnection -State Listen | Where-Object LocalPort -in 5173,8084
# 2) 代理对吗？（curl 直打后端，绕开前端）
curl http://127.0.0.1:8084/api/sticky/notes     # 401/422=活着；拒绝连接=后端挂
# 3) 前端拿到的是什么？（黑屏时看返回类型：HTML=打到 dev server、JSON=接口正常）
```
**答法**：**分层定位、逐层收窄**——浏览器 → vite proxy → 后端，每层单独可测；经验口诀"**返回 HTML 说明代理没命中、返回 JSON 说明链路通**"（项目局域网文档原话）。

## Q2. Windows 下 uvicorn reload 为什么慢？怎么取舍？

**代码**（`main.py` 真实，带注释）：

```python
# reload 默认关闭（Windows 下 WatchFiles 启动极慢）；需要热重载时设 RELOAD=1
uvicorn.run("dixiyang.main:app", host="0.0.0.0", port=8084,
            reload=os.getenv("RELOAD", "0") == "1")
```

**数据**（docs 版本记录真实）：开启 reload 后 Windows 启动 **30s → 关闭后 2s**。
**答法**：
1. **原因**：reload 要 watch 整棵源码树（含 venv/node_modules 误伤风险），Windows 文件系统监控（ReadDirectoryChangesW）+ Python 启动开销叠加；
2. **取舍**：开发需要热重载就忍 30s，**生产/常规开发默认关**——用"改完手动重启"换 15 倍启动速度；
3. **加分**：watchfiles 库（uvicorn 新版）比 stat 轮询快；`--reload-dir` 收窄监视范围、`.gitignore` 复用为 watch 忽略规则是通用解法。

## Q3. Redis 挂了怎么办？（高可用与降级）

**项目真实做法**（docs 记录 + 源码模式）：
- Redis 只承载**可降级的加速数据**（广场推荐缓存、浏览量缓冲）——**未起/宕机自动降级直查 DB**，JMeter 压测降级路径 **0 错误**；
- 源码层：`idea_cache` 每次 Redis 调用包 `try/except` + `_mark_down()` 记录故障态，失败返回降级值而非抛错。

```python
# 项目模式（idea_cache 同构示意）
def get_hot(self) -> list:
    if self._down:                       # 已知故障：不再频繁撞 Redis（熔断思路）
        return self._fallback_from_db()
    try:
        v = self._redis.zrevrange("hot", 0, 9)
        return v or self._rebuild_hot()  # 空也回源
    except Exception as e:
        self._mark_down(str(e))          # 标记降级 + 日志告警
        return self._fallback_from_db()
```

**答法**（分级降级四层，可直接当答案）：
1. **角色定位**：缓存是加速器不是事实源 → 任何时刻 Redis 不可用，DB 都能独立支撑正确性；
2. **快速失败**：故障后进 `_down` 态短路重试（避免每次请求都等 Redis 连接超时拖垮 P95）；
3. **数据回填**：恢复后从 DB 重建缓存（预热或懒加载）；
4. **量化验证**：降级不是"应该没问题"，是压测出来的 0 错误 → [Redis优化效果对比](../../../docs/Redis优化效果对比.md)。

## Q4. Git 协作里怎么保护"不入库但必须存在"的本地文件？

**代码**（项目真实方案，`docs/技能库出库与同步.md`）：

```powershell
# 一次性启用 hooks（每台机器执行一次）
git config core.hooksPath .githooks
# 效果：pull/merge 前钩子拦截，防止远程删除操作误伤本地技能目录
# 兜底：文件万一丢了，从 git 历史一键恢复
powershell -File scripts/restore-skills.ps1
```

**答法**：
1. **问题形态**：某些目录（本地技能/密钥/大资源）**本地必须有、远程不能有** → 普通 `.gitignore` 只挡"不追踪"，挡不住"远程已删除 → pull 把本地删了"这类**同步方向的删除**；
2. **方案**：`core.hooksPath` 指向仓库内 hooks → pre-merge/pre-pull 钩子检查并保护；**双保险** = hooks 防删 + restore 脚本可恢复（任何保护措施都要配"失效后的后悔药"）；
3. **追问替代方案**——`.gitattributes` 的 `merge=ours` 策略、submodule 化、或干脆独立仓库：说清各自适用面即可，本项目选 hooks 是因为协作方零学习成本。

## Q5. 局域网/真机联调怎么做？（手机直接访问本机服务）

**代码**（`vite.config.ts` 真实——dev 启动自动建 adb 隧道）：

```ts
function autoAdbReverse(): Plugin {
  return {
    name: 'auto-adb-reverse',
    configureServer() {
      const adb = ADB_CANDIDATES.find((p) => existsSync(p));
      if (!adb) return;
      for (const port of [5173, 8084]) {                     // 前后端都隧道到手机
        execFile(adb, ['reverse', `tcp:${port}`, `tcp:${port}`], { timeout: 5000 }, (err) => {
          if (err) return;   // 手机未连/adb 异常：静默跳过，不阻塞启动
        });
      }
    }
  };
}
```

**答法**：
1. **三种接入**：同一 WiFi（`host: true` + 本机 IP）、**USB `adb reverse`**（手机 `localhost:5173` 直达电脑，免配 IP/免防火墙）、网线直连（固定网段）；
2. **工程化细节**：隧道做成 vite 插件**启动自动建**（5s 超时静默失败——开发工具绝不能因外设缺失而挂掉）、前后端双端口都反代、验证一条 `curl localhost:5173` + 手机浏览器开 `localhost:5173`；
3. **追问为什么不用手机填电脑 IP**——企业 WiFi 常有 AP 隔离，adb reverse 是最稳路径。

## Q6. 后台文件/存储的清理巡检怎么做？

**代码**（`DixyangFast/src/dixiyang/services/sticky_cleanup.py` 真实节选——运维视角的"自愈任务"）：

```python
INTERVAL = 24 * 3600          # 每日一轮 + 启动即跑

def sweep() -> dict:
    try:
        ids = {r[0] for r in db.query(StickyNote.id).all()}
    except Exception as e:
        log.warning("DB 查询失败，跳过孤儿判定（%s）", e)
        ids = None            # ← 降级：DB 不可用时绝不盲删文件（安全阀）
    # 孤儿 json（DB 无行）→ 删；空用户目录（递归无文件）→ os.rmdir
    ...
```

**答法**（巡检任务四要素，直接当模板背）：
1. **幂等**：重复执行无副作用（判定基于当刻状态，不记上次水位）；
2. **降级**：依赖系统（DB）不可用时**跳过危险判定**而不是硬做——清理任务最怕"错误地删对了"；
3. **可观测**：每轮打点（`orphan_files/empty_dirs` 计数）+ 逐项日志，删了什么可追溯；
4. **收尾**：daemon 线程 + `Event.wait(timeout)`（停机秒响应，见 [Python 01 Q3](../PythonBackend/01-面试常问·项目已用.md)）。
