## Q1. 实施方案包含哪些章节？（框架模板）

```markdown
# XX 系统实施方案（模板骨架）
1. 项目概述      —— 目标、范围、干系人、里程碑（一页）
2. 现状调研      —— 客户环境清单（OS/中间件/网络/数据量）、业务痛点、约束条件
3. 环境设计      —— 拓扑图、账号权限、参数基线（端口/超时/连接池）、依赖清单
4. 部署计划      —— 步骤分解（可重复执行的命令级 checklist）、责任人、时间窗
5. 数据迁移      —— 源→目标映射、清洗规则、试迁移、对账标准（行数/抽样/哈希）
6. 切换与回滚    —— 切换窗口、冻结范围、回滚触发条件与回滚步骤（写清楚！）
7. 验收计划      —— UAT 用例、性能基线、通过标准、签字人
8. 培训与交接    —— 对象分层（管理员/业务用户/运维）、材料、考核方式
9. 风险与预案    —— 风险矩阵（概率×影响）+ 每条的缓解动作
10. 售后支持      —— 保修期、SLA、问题升级路径、驻场安排
```

**答题要点**：
- **范围与不做清单同等重要**——实施翻车 top1 是范围蔓延，"本期不含 XX"必须白纸黑字；
- **每个阶段有 DoD**（完成定义）：部署完成 ≠ 服务被探活、数据导入完成 ≠ 对账通过；
- 追问"客户不签字怎么办"——阶段验收邮件确认 + 每周例会纪要，留痕即证据。

**先讲清楚基础：实施方案是给谁看的、骨架按什么逻辑排**

实施方案是"**怎么把这个项目交付上线**"的完整承诺书——读者不是技术评审专家，而是**客户项目经理 + 自己团队**：前者关心"什么时候好、出事怎么办"，后者关心"每一步怎么干"。所以它按"**现状 → 目标 → 路径 → 验收 → 兜底**"组织：现状调研（客户环境长什么样）→ 环境/部署设计（怎么搭）→ 计划（谁、何时、干什么）→ 验收（什么算干完）→ 风险与售后（出岔子怎么办）。

两个实施专用概念：**不做清单**（"本期不含 XX"白纸黑字——范围蔓延是实施翻车第一名）；**DoD（完成的定义）**（"部署完成"=服务被探活通过，不是"命令跑完了"——没有 DoD 就会互相扯皮"这算不算做完"）。

**延伸追问（同一知识面）**
- 为什么不做清单比做清单还重要？——"顺便加个小功能"会连锁拖垮工期；边界写清才能挡住。
- 里程碑怎么定才有意义？——每个里程碑关联"可验收的产出"（环境就绪=能登录演示），而不是单纯一个日期。
- 沟通留痕有什么技巧？——重要节点走**邮件确认**（比群消息正式）、每周例会出**纪要**——"留痕即证据"。

## Q2. 数据迁移的校验 SQL 与方法

```sql
-- ① 总量核对（迁移前后各跑，结果必须一致）
SELECT 'users' t, COUNT(*) FROM app_user
UNION ALL SELECT 'novels', COUNT(*) FROM novels
UNION ALL SELECT 'characters', COUNT(*) FROM novel_character;

-- ② 增量边界核对：最新/最早时间戳 + 自增主键 max（防"漏了最近一天"）
SELECT MIN(create_time), MAX(create_time), MAX(id), COUNT(*) FROM novels;

-- ③ 抽样字段哈希比对（内容级，防行数对内容错）
SELECT MD5(GROUP_CONCAT(id, title ORDER BY id)) AS fingerprint FROM novels WHERE status = 1;

-- ④ 关键关联完整性：孤儿行检查（迁移最容易断的就是外键关系）
SELECT c.id FROM novel_character c
LEFT JOIN novels n ON n.id = c.novel_id
WHERE n.id IS NULL;                       -- 期望 0 行

-- ⑤ 迁移日志表核对：失败行必须为 0，非 0 逐条处理
SELECT status, COUNT(*) FROM migrate_log GROUP BY status;
```

**答法（四层递进）**：行数对齐（量）→ 边界值对齐（时）→ 抽样指纹对齐（质）→ 关联完整性（关系）。**任何一层不过就不算迁移完成**；补充：先**试迁移**跑全量对账 → 窗口内**增量/停写切换** → 正式切换后再对账一次（切换后对账才是终审）。

**先讲清楚基础：迁移的本质是什么、"对账"为什么是核心**

迁移=把数据从旧系统搬到新系统，并**证明没搬坏**——"证明"的通用手段就是**对账**（逐层比对）。为什么不能"导完就算完"？——导入程序可能截断长字段、丢特殊字符、断外键关系、漏最近一天的数据——这些都不会报错，只会在上线后变成业务故障。

四层对账从粗到细：**量**（行数对不对）→ **时**（时间边界/主键边界——防"漏了最后一批"）→ **质**（抽样做内容指纹——防"行数对、内容错"）→ **关系**（孤儿行检查——防"外键断了"）。任何一层不过，都不算迁移完成。

**延伸追问（同一知识面）**
- 迁移怎么做到"可重跑"？——**幂等**（`INSERT IGNORE`/`REPLACE`/按主键 upsert）：失败重来不产生脏数据——否则中途失败就要"清库重来"。
- 大表怎么迁不锁爆线上？——分批切片（按主键区间）+ 避开高峰；一次性巨量事务会长时间持锁、打满 IO。
- 为什么"切换后还要再对账"？——切换窗口内的增量（停写前最后一刻的数据）也要进对账——终审在切换之后。

## Q3. 切换与回滚预案怎么写？

```markdown
## 切换窗口（例：周日 02:00-04:00，业务低峰）
T-7d  通告 + 冻结需求      T-2d  预演切换全流程（在演练环境按真实命令跑一遍）
T-1d  全量备份 + 校验      T-0   02:00 停写 → 最后增量 → 对账 → 起新服务 → 冒烟

## 冒烟通过标准（全部满足才对外放量）
[ ] 登录/核心链路 3 条用例通过
[ ] 关键接口 P95 ≤ 基线 × 1.5
[ ] 错误率 < 0.5% 持续 10 分钟

## 回滚触发条件（写死，不现场争论）
- 冒烟 30 分钟内未通过 / 数据对账差异 > 0 / P95 超阈值 2 倍

## 回滚步骤（与切换同粒度）
1) 切 nginx upstream 指回旧服务（< 1 min，流量即回）
2) 数据回滚：恢复 T-1d 备份 + 重放窗口期操作日志（若无反向脚本则不回滚数据，人工补）
3) 通告恢复 + 记录事件时间线
```

**答法要点**：
1. **回滚的第一手段永远是流量开关**（DNS/nginx upstream/feature flag），秒级止血，数据回滚放第二步；
2. **预案必须演练**——没预演过的预案等于没有（和备份不演练同理）；
3. **触发条件写成可判断的数字**，避免现场"要不要回滚"的主观扯皮；
4. 追问"数据回不去怎么办"——所以要**变更日志/操作流水**，能重放就能反向；高风险变更上**灰度/蓝绿**，根本不进回滚剧本。

**先讲清楚基础：切换和回滚各自是什么、预案的核心原则**

切换=把生产流量从旧系统交给新系统（有"窗口"——通常选业务低峰）；回滚=切换失败时**快速退回**的预案。"能不能回滚"不是上线时决定的——是**设计阶段**决定的（数据模型如果改得回不去，就根本谈不上回滚）。

预案三条核心原则：**回滚第一手段是流量开关**（nginx upstream/DNS/功能开关——秒级止血，代码都不用动）；**触发条件写死成数字**（冒烟 30 分钟不过/对账有差/性能超 2 倍——避免现场争论"要不要回滚"耽误时间）；**必须演练**（没预演过的预案等于没有——每个人要知道"我点哪一行"）。

**延伸追问（同一知识面）**
- 数据回滚为什么最难？——结构变更（删表/改字段）可能物理上回不去——所以用"**向后兼容**"改法：先加新字段、双写、确认稳定再删旧字段——每一步都可回退。
- 怎么"根本不进回滚剧本"？——灰度/蓝绿：先放小比例流量验证，出问题只影响那一小撮用户。
- 切换清单为什么要"执行人+验证人"两列？——每步"谁做、谁检查"分离——防止"做了但没验证=假完成"。

## Q4. UAT 验收用例怎么设计？

```markdown
| 用例ID | 模块 | 前置 | 步骤 | 期望结果 | 优先级 | 结果 |
|--------|------|------|------|----------|--------|------|
| UAT-AUTH-01 | 登录 | 账号已存在 | 输入正确账密 → 登录 | 跳转首页，token 写入 | P0 | ☐ |
| UAT-AUTH-02 | 登录 | 账号已存在 | 连续 5 次错误密码 | 第 6 次触发限流提示，账号不锁死 | P0 | ☐ |
| UAT-DATA-01 | 数据 | 迁移后环境 | 按迁移前抽样 20 条核对 | 字段级完全一致 | P0 | ☐ |
| UAT-PERM-01 | 权限 | 用户 A/B | A 的 token 请求 B 的资源 | 403/404，不泄露 B 数据 | P0 | ☐ |
| UAT-PERF-01 | 性能 | 生产规格 | 核心接口 50 并发 10 分钟 | P95 ≤ 基线×1.5，错误率<0.5% | P1 | ☐ |
| UAT-EDGE-01 | 容错 | Redis 停止 | 正常浏览核心页 | 自动降级，功能可用，无 500 | P1 | ☐ |
```

**答题要点**：
1. **P0 用例围绕钱、数据、权限**——越权/数据一致/资金类必须 P0 全过才签验收；
2. **每条用例独立可判定**（步骤→期望是机器可判断的，不写"系统正常"）；
3. **必含异常路径**：错密码、断网、依赖宕机（Redis 挂了还能用——本项目压测过降级 0 错误，见 [运维 01 Q3](../Operations/01-面试常问·项目已用.md)）；
4. **客户侧执行**：验收用例要让客户**自己勾**，实施方陪同演示——签字的是他跑过的，不是你演示过的。

**先讲清楚基础：UAT 是什么、和普通测试什么区别**

UAT（用户验收测试）=**由客户按真实业务场景执行**的测试——验证"系统是不是满足需求、能不能上岗干活"。它和测试工程师的功能测试区别在"视角"：功能测试按用例过功能点（技术视角），UAT 按**业务流程**走场景（业务视角）——比如"一个客服完整处理一次用户申诉"，而不是"调用某接口返回 200"。

用例设计三条要点：**用业务语言写**（"客服给用户重置密码"，而不是"POST /user/reset"）；**每条独立可判定**（步骤 → 期望结果是明确结论，不写"系统正常"）；**P0 盯住钱、权限、数据**（这三类出问题不可接受）。

**延伸追问（同一知识面）**
- 用例从哪来？——业务流程清单 + 高频场景 + 历史报障榜（问题高发处就是重点验证处）。
- 为什么要测"异常路径"？——正常路径开发自测就覆盖了；断网/无权限/并发冲突这些"真实但少见"的场景才是 UAT 的价值区。
- 遗留缺陷怎么处理？——验收前把话说清：P0 必须清零、P1/P2 有明确修复计划且客户书面认可——不然验收会变成持久战。

## Q5. 用户培训怎么组织？（分层 + 材料 + 检验）

```text
分层：
  管理员/运维 —— 部署架构、启停、日志、备份恢复、应急联系（半天，含实操）
  业务用户    —— 核心流程场景化演练（按"一天的工作"设计剧本，不念菜单）（1-2h）
  决策者      —— 价值与指标汇报（30 min，讲能看什么数、省什么事）

材料（跟项目走，不跟人走）：
  ① 快速上手卡（一页 PDF：登录/三个高频操作/常见问题）
  ② 操作手册（截图版，含"出错了看哪里"）
  ③ 录屏（新员工 onboarding 复用）
  ④ FAQ + 问题提交入口（工单/群 + 响应时限）

检验（培训有效的唯一标准）：
  现场小测/实操任务：学员独立完成 3 条核心操作 → 通过率 <90% 则补训
```

**答法**：培训的对象是**留存的材料**不是那场会——人会流动，手册和录屏才是资产；**按岗位设计剧本**（业务用户学"完成什么事"，不学"模块叫什么"）；**有效性的检验是学员动手**，不是"讲完了"。

**先讲清楚基础：培训的目标是什么、为什么要分层**

培训的目标不是"把功能讲一遍"，而是"**学员能独立干活**"——衡量标准是学员动手能完成核心操作，不是你讲完了。所以要**分层设计**：每类人"需要会做什么"不同——管理员（会运维：启停/备份/查日志）、业务用户（会走核心流程）、决策者（看得懂价值）——按"角色需要会什么"组织内容，而不是按"系统有哪些模块"。

材料要**跟项目走而不是跟人走**：快速上手卡、操作手册、录屏、FAQ——人会流动，材料才是资产。

**延伸追问（同一知识面）**
- 怎么检验培训有效？——现场实操考核（学员独立完成 3 条核心操作），通过率不达标就补训——"讲过"不等于"学会"。
- 材料怎么保证不烂尾？——确定维护责任人 + 随版本迭代同步更新——发版时把"文档更新"当检查项。
- 怎么放大效果？——在客户内部培养"种子用户"（先教会少数人、让他们带新人）——比厂商长期驻场可持续。

## Q6. 现场问题怎么闭环？（分级 + SLA + 复盘）

```markdown
分级定义（签进合同，别私下定）：
  P1 致命：核心业务中断 / 数据错误 / 安全事件      → 响应 15min，恢复 2h，随时电话
  P2 严重：主要功能不可用有绕行 / 性能严重劣化     → 响应 1h，恢复 8h
  P3 一般：次要功能异常 / 界面问题                 → 响应 4h，随版本修复
  P4 建议：优化类 / 新需求                         → 进需求池排期

闭环流程：
  报障(现象+环境+复现步骤) → 定级 → 止血 → 根因 → 修复+回归 → 客户确认 → 复盘归档
```

```text
复盘输出固定三问（避免变成追责会）：
  1) 根因是什么？（5 Whys 打到机制层：是"忘了做"还是"机制没保证它被做"）
  2) 为什么没被拦截？（哪道闸门缺失：测试/监控/评审）
  3) 机制性改进是什么？（加检查项/加告警/改流程——只改人不改机制必然复发）
```

**答法**：实施岗的口碑=**问题闭环质量**——报障模板（现象/环境/复现）决定排错效率，分级进合同避免拉扯，**复盘打到机制层**才是防复发的关键。项目同款实践：`docs` 每篇必有"已知问题"节，历史问题全部留痕可查。

**先讲清楚基础：什么叫"闭环"、为什么实施岗最看重它**

闭环=从"用户报障"到"**确认修好 + 复盘归档**"的完整回路。半截子处理（修了但没验证、验证了但没复盘）都会让同类问题复发——实施岗的口碑就看这个回路转得顺不顺。

流程链：**报障（现象/环境/复现）→ 定级（P1~P4 + SLA）→ 止血 → 根因 → 修复+回归 → 客户确认 → 复盘归档**。其中两个抓手：报障模板（信息全不全决定排错效率——"系统不能用"和"点保存报 500、复现步骤是…"是两个世界）；分级进合同（P1 响应 15 分钟、P4 进需求池——不给现场留"到底急不急"的争论空间）。

**延伸追问（同一知识面）**
- 5 Whys 是什么？——连问五个"为什么"打到机制层："忘了做"→"为什么没被拦住"→"检查项缺失"→……——停在"某某粗心"就是没到根因。
- 复盘怎么不变成追责会？——**对事不对人**（没人敢报真相的团队，复盘=互相甩锅）——目标是"机制怎么改"。
- 为什么"只改人不改机制"必复发？——人是会轮换、会疏忽的变量；机制（检查项/告警/流程）才是稳定的防线。

## Q7. 现场环境体检脚本（交付前跑一遍）

```bash
#!/bin/bash
# env_check.sh —— 交付/巡检一键体检，输出绿✓红✗清单
pass=0; fail=0
check() {  # check "描述" "命令"
  if eval "$2" >/dev/null 2>&1; then echo "✓ $1"; pass=$((pass+1));
  else echo "✗ $1  ← $(eval "$2" 2>&1 | tail -1)"; fail=$((fail+1)); fi
}

check "端口 8084 在听"        "ss -lnt | grep -q ':8084'"
check "健康检查返回 JSON"     "curl -fs http://127.0.0.1:8084/api/ping | grep -q code"
check "MySQL 可连接"          "mysqladmin ping -uroot -p\$DB_PASS"
check "Redis PONG"            "redis-cli -a \$REDIS_PASS ping | grep -q PONG"
check "磁盘使用率 < 80%"      "[ \$(df -m / | awk 'NR==2{print \$5}' | tr -d %) -lt 80 ]"
check "内存可用 > 500MB"      "[ \$(free -m | awk '/Mem:/{print \$7}') -gt 500 ]"
check "服务开机自启已启用"    "systemctl is-enabled dixiyang | grep -q enabled"
check "最近 1h 无 ERROR 日志" "! journalctl -u dixiyang --since '-1 hour' | grep -qi error"
check "昨日备份存在且 >1MB"   "[ \$(find /backup -name '*.sql.gz' -mtime -1 | head -1) ] && [ \$(stat -c%s \$(find /backup -name '*.sql.gz' -mtime -1 | head -1)) -gt 1048576 ]"

echo "------------------------"; echo "PASS=$pass FAIL=$fail"
[ $fail -eq 0 ] || exit 1     # 非 0 退出码 → 可挂 cron/CI，红了告警
```

**答法**：
1. **清单即资产**——把"老师傅的检查习惯"固化成脚本，新人交付不漏项；退出码非 0 可直接接巡检告警（[运维 02 Q6](../Operations/02-面试常问·通用高频.md) 的监控纪律）；
2. 检查项分四类：**连通性**（端口/探活）、**依赖**（DB/缓存）、**容量**（磁盘/内存）、**卫生**（自启/日志/备份）；
3. 追问"怎么变成常态巡检"——cron 每小时跑 + 失败发通知，体检从"交付那天"变成"每一天"。

**先讲清楚基础：交付前为什么要"体检"、脚本比人强在哪**

上线交付最怕"漏检"——一个人凭记忆查十项，总会忘一项（而且每次忘的还不一样）。**体检脚本=把"老师傅的检查习惯"固化成可重复执行的一遍**：同一套标准、次次不落项——这就是它比"人查"强的地方。

脚本的设计：每项检查=一条命令 + 一个通过标准（命令成功=✓）；输出一张清单 + 汇总（PASS/FAIL）；失败以**非 0 退出码**结束——这个退出码一接，cron/CI/告警就能自动挂上（从"交付那天查一次"变成"每天查"）。

**延伸追问（同一知识面）**
- 检查项分哪四类？——**连通性**（端口/探活/接口）、**依赖**（DB/Redis 能连）、**容量**（磁盘/内存余量）、**卫生**（自启/错误日志/备份新鲜度）——覆盖"能跑吗/跑得动吗/长期稳吗"。
- 为什么检查项要"少而精"？——每项都要有人维护；无用的检查项会稀释信号（狼来了）。
- 怎么和监控衔接？——脚本的退出码直接接告警管道；巡检结果留档（出事故时可回看"之前体检是不是已经黄了"）。
