## Q1. GIL 是什么？多线程/多进程/asyncio 怎么选？

```python
import threading, multiprocessing, asyncio, time

def cpu_bound(n):                      # CPU 密集：GIL 下多线程无收益
    return sum(i * i for i in range(n))

def io_bound(url):                     # IO 密集（网络/磁盘）：多线程/协程都行
    return requests.get(url, timeout=3)

# 三种并发的真实分工
# ① 多线程：IO 密集（GIL 在 IO 等待时会释放）——requests + ThreadPool
with ThreadPoolExecutor(max_workers=8) as ex:
    list(ex.map(io_bound, urls))
# ② 多进程：CPU 密集（每个子进程独立解释器、独立 GIL）——进程池
with ProcessPoolExecutor(max_workers=os.cpu_count()) as ex:
    list(ex.map(cpu_bound, nums))
# ③ asyncio：海量并发 IO（单线程协程，万级连接）——必须用异步库（aiohttp/httpx Async）
async def main():
    async with httpx.AsyncClient() as c:
        await asyncio.gather(*(c.get(u) for u in urls))
```

**答法（万能框架）**：

| 场景 | 选择 | 原因 |
|------|------|------|
| 网络/文件等待多 | 线程 或 asyncio | GIL 在 IO 时释放；协程切换更便宜 |
| 计算重（解析/加密） | 多进程 | GIL 让多线程退化单核 |
| 单机海量连接（10k+） | asyncio | 线程栈内存 vs 协程 KB 级 |
**追问"GIL 为什么存在"**：保护 CPython 引用计数的线程安全，代价是字节码执行期单核；**3.13 free-threading（no-GIL）** 是当下加分谈资。
**项目挂钩**：本项目清理任务是"低频 IO 型后台工作"→ daemon 线程足够（[01 Q3](./01-面试常问·项目已用.md)），选型跟着负载形状走，不为技术而技术。

**先讲清楚基础：GIL 是什么、为什么 Python 会有它**

概念先行：**GIL（全局解释器锁）= CPython 解释器层面的一把"大锁"**——同一时刻只允许**一个线程**执行 Python 字节码。注意它锁的不是"你的数据"，而是"解释器执行权"——所以 GIL 和"线程安全"不是一回事。

为什么会有它？——CPython 的内存管理靠**引用计数**（对象被引用几次、归零就回收）；多线程同时改计数会乱套，最简单省事的设计就是"拿一把全局锁保护一切"。代价：多线程在 CPU 计算上退化成单核。但注意——**IO 等待时 GIL 会释放**，所以 IO 密集的多线程依然有效——选型表背后的原理就在这。

**延伸追问（同一知识面）**
- GIL 和"线程安全"什么关系？——GIL 只保证**字节码级**的原子性（`x += 1` 其实是"读-改-写"多个字节码，仍可能交叉）；共享可变数据照样要自己加锁。
- 为什么计算密集要用多进程？——每个进程有**独立的解释器实例**（各自的 GIL），能真正吃到多核；代价是进程间通信（序列化、内存翻倍）。
- 3.13 的"无 GIL"是什么？——PEP 703 提供**实验性** no-GIL 构建（可选安装），生态还没全面适配——面试提一句"实验阶段、生产谨慎"即可。

## Q2. 手写装饰器（带参 + 保留元数据）

```python
import functools, time

# ① 不带参：被装饰函数套一层
def timer(fn):
    @functools.wraps(fn)                 # ④ 必须：保留 __name__/__doc__，否则调试/框架反射失效
    def wrapper(*args, **kwargs):
        t = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:                         # finally：函数抛错也记录耗时
            print(f"{fn.__name__} {time.perf_counter() - t:.3f}s")
    return wrapper

# ② 带参：外面再套一层参数层
def retry(times=3, exceptions=(Exception,)):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for i in range(times):
                try:
                    return fn(*args, **kwargs)
                except exceptions as e:
                    if i == times - 1:
                        raise           # 最后一次仍失败 → 原样抛出（保留异常链）
                    time.sleep(0.2 * 2 ** i)   # 指数退避
        return wrapper
    return deco

@retry(times=3, exceptions=(ConnectionError,))
def call_api(): ...
```

**答法**：装饰器=语法糖的高阶函数；三层结构（参数层→包装层→原函数）是带参的标准形状；**`functools.wraps` 和 `finally/raise` 是面试官盯的两个细节**。追问"类怎么做装饰器"——`__call__` + `__get__`（描述符，贴 `@property` 一起讲）。
**项目挂钩**：FastAPI 的 `@router.get`、`Depends` 本质就是这套机制的工程化。

**先讲清楚基础：装饰器是什么、`@` 语法到底做了什么**

一句话：**装饰器=接收一个函数、返回一个新函数的高阶函数**；`@deco` 只是语法糖——`@deco` 加在 `def fn` 上，等价于 `fn = deco(fn)`（定义完立刻把函数"过一遍"）。"包装"的本质：新函数内部调用原函数，但在前后加上额外动作（计时、重试、鉴权）。

"带参数的装饰器"为什么是三层的？——`@retry(times=3)` 先执行 `retry(times=3)` 得到一个**装饰器**，再用它去包原函数——多出来的第一层就是"参数层"。`functools.wraps` 也要讲清楚：它把原函数的 `__name__`/`__doc__` 等信息复制到包装函数上——不然调试输出、框架反射（按函数名注册路由）全会错乱。

**延伸追问（同一知识面）**
- `functools.wraps` 的原理？——把原函数的 `__module__/__name__/__qualname__/__doc__` 等属性复制给包装函数，并设置 `__wrapped__`——还能顺着 `__wrapped__` 找回原函数。
- 类装饰器和函数装饰器差别？——类实现 `__call__` 就能被"调用"（可以带状态）；再实现 `__get__` 还能当"方法装饰器"（描述符协议，`@property` 同族）。
- 多个装饰器叠加的顺序？——**从下往上包**（离函数最近的先包）；执行时最外层的先进入、最后退出。

## Q3. 生成器与迭代器：惰性求值解决什么问题？

```python
# ① 大文件逐行处理：内存 O(1)（不会 readlines 吃掉 8GB）
def read_large(path):
    with open(path, encoding="utf-8") as f:
        for line in f:                   # 文件对象本身就是迭代器
            yield line.strip()

# ② 管道组合：切割→过滤→映射，全部惰性，链起来只遍历一次
def pipeline(lines):
    return (parse(l) for l in lines if not l.startswith("#"))

# ③ 生成器表达式的内存收益量化
big = range(10_000_000)
sum(i for i in big)          # 生成器：无 40MB 列表分配
sum([i for i in big])        # 列表推导：先分配完整列表

# ④ 迭代器协议：__iter__ / __next__ + StopIteration
class Countdown:
    def __init__(self, n): self.n = n
    def __iter__(self): return self
    def __next__(self):
        if self.n <= 0: raise StopIteration
        self.n -= 1
        return self.n + 1
```

**答法**：**迭代器是协议（`__next__`），生成器是实现它的语法糖**（`yield` 自动挂起/恢复执行栈）；核心价值=惰性——大数据量、无限流、管道组合。追问 `yield from`——委托子生成器（省掉手写转发循环，协程基础）。
**项目挂钩**：存储层对账扫描"目录里可能有百万文件"，正适合迭代器逐个产出而不是全量列表。

**先讲清楚基础：生成器凭什么"省内存"、`yield` 在做什么**

核心机制：函数里出现 `yield` 后，调用它**不会执行函数体**，而是返回一个"生成器对象"；每次 `next()`（或 for 循环）才恢复执行，**遇到 `yield` 就"暂停并保存现场"**（局部变量、执行位置都留着），下次从这里继续——所以同一时刻内存里只有"一份现场 + 当前一个元素"，而不是整个列表。

这就是"惰性求值"：不预先算好全部，用到才算下一个。收益两个：① 内存 O(1)（读 8GB 文件不会先吃 8GB 内存）；② 支持"无限流"（理论上可以产出无穷个元素——列表做不到）。代价：**只能消费一次**（走完就空了），要重来就重新建一个。

**延伸追问（同一知识面）**
- 迭代器和生成器什么关系？——"迭代器协议"是规范（`__iter__`/`__next__` + `StopIteration`）；生成器是实现该协议的**语法糖**（不用手写类）。
- `yield from` 有什么用？——把迭代"委托"给另一个可迭代对象（省掉手写的 for + yield 转发循环）；生成器做协程（`send/throw`）时它是消息转发的关键。
- 生成器表达式和列表推导怎么选？——数据量大/只过一遍 → 生成器表达式 `(...)`；要重复用/需要下标 → 列表。

## Q4. 手写上下文管理器（with 的本质）

```python
# ① 类实现
class DBSession:
    def __init__(self, dsn): self.dsn = dsn
    def __enter__(self):
        self.conn = connect(self.dsn)
        return self.conn                # as 后面的变量
    def __exit__(self, exc_type, exc, tb):
        self.conn.close()
        return False                    # False=异常继续抛；True=吞掉（危险，勿乱用）

# ② 装饰器实现（contextlib）
from contextlib import contextmanager

@contextmanager
def timer(label):
    t = time.perf_counter()
    try:
        yield label                      # yield 之前 = enter，之后 = exit
    except Exception as e:
        log.error("%s failed: %s", label, e)
        raise                            # 重新抛出，保持异常语义
    finally:
        print(f"{label}: {time.perf_counter() - t:.3f}s")

with timer("load"): ...
```

**答法**：`with` = 异常安全的 `try/finally` 声明式写法；`__exit__` **天然拿到异常三元组**（这就是它比 finally 强的地方——能按异常类型决定要不要重抛）。追问"项目里最像的代码"——`get_db()` 的 `yield + finally close` 就是依赖注入版上下文管理器（[01 Q1](./01-面试常问·项目已用.md)）。

**先讲清楚基础：`with` 帮你管什么、协议怎么运作**

`with` 解决"**打开必须记得关**"这类成对操作：文件、连接、锁、事务——用 try/finally 也能做，但 `with` 把它变成声明式、不会忘。协议只有两个方法：进入上下文调用 `__enter__`（返回值给 `as` 后面的变量），离开时调用 `__exit__`——**关键是 `__exit__` 无论正常退出还是抛异常都会被调用**（这就是"异常安全"）。

`__exit__` 会收到三个参数（异常类型、异常对象、traceback）：正常退出时全是 None；返回 `True` 表示"异常我处理了"（不再往外抛）——**要非常克制**，大多数场景应该"记个日志、返回 False"（继续抛）。

**延伸追问（同一知识面）**
- `@contextmanager` 的原理？——把生成器"包装"成上下文管理器：`yield` 前的代码=enter、`yield` 后=exit；异常会被 throw 进生成器（所以在 yield 处 try/except 能拿到异常）。
- 多个资源一起管？——`with open(a) as f1, open(b) as f2:`；动态数量用 `contextlib.ExitStack`。
- 为什么 `get_db()` 那种 `yield + finally` 也算上下文管理器？——FastAPI 的依赖注入识别的正是"生成器式依赖"协议——同一思想在框架里的体现。

## Q5. 可变默认参数 / 深浅拷贝 经典坑

```python
# ① 可变默认参数：默认值在函数定义时创建一次，所有调用共享！
def append_to(item, bucket=[]):      # ❌ 第二次调用还带着上次的结果
    bucket.append(item)
    return bucket
append_to(1)  # [1]
append_to(2)  # [1, 2]  ← 惊吓
def append_to(item, bucket=None):    # ✅ 惯用法
    bucket = bucket if bucket is not None else []

# ② 闭包变量陷阱：lambda 捕获的是"变量"不是"值"
fns = [lambda: i for i in range(3)]      # 全部返回 2（共享同一个 i）
fns = [lambda i=i: i for i in range(3)]  # ✅ 默认参数绑定当时值 → 0 1 2
# 或 functools.partial / 工厂函数

# ③ 深浅拷贝
import copy
a = [[1, 2], [3, 4]]
copy.copy(a)[0] is a[0]          # True：浅拷贝——第一层新、内层共享（改内层互相影响）
copy.deepcopy(a)[0] is a[0]      # False：深拷贝——递归全新开辟

# ④ dict/字典合并的"拷贝语义"
d2 = {**d1}                        # 浅拷贝一层
d2 = copy.deepcopy(d1)             # 嵌套结构要深拷贝
```

**答法**：默认参数在**定义时求值一次**（函数对象属性）——这是"状态泄漏"类 bug 的鼻祖；浅/深拷贝的分界=**嵌套结构是否递归复制**，选型看"改动会不会穿透到内层"。

**先讲清楚基础：默认参数为什么"记得上一次的结果"**

关键事实：**默认值在 `def` 执行的那一刻求值一次**，之后存在函数对象里；所有调用共享同一个对象。所以 `bucket=[]` 只创建了**那一个列表**——第一次调用往里塞了元素，第二次调用用的还是它。修法用"哨兵值"：默认写 `None`（不可变、安全），函数体里"是 None 才新建"。

顺带把"闭包变量陷阱"用同一条规则讲透：lambda 捕获的是**变量本身**（循环里那个 i 一直在变），不是"当时的值"；`lambda i=i:` 是把当时的值绑到**参数**上——和"默认值在定义时求值"共用同一条机制。

**延伸追问（同一知识面）**
- 默认参数可以故意利用"共享"吗？——可以（memoization 技巧：默认 dict 当缓存），但要注释说明"这是故意的"。
- 深拷贝为什么要 `memo` 字典？——记录"已复制过的对象"（原对象→克隆），遇到循环引用（`a.b = a`）才不会无限递归——本质是"图遍历去重"。
- 还有哪些拷贝坑？——自定义对象可覆写 `__copy__/__deepcopy__`；deepcopy 对不可变对象（int/str/元组）会直接复用（优化，不新建）。

## Q6. 垃圾回收机制？

**答法（三件套）**：
1. **引用计数**为主：`sys.getrefcount()` 可观测；归零立即回收（可预测、无停顿）；
2. **分代回收**为辅：0/1/2 代，越老越少扫——基于"弱代假设"（多数对象朝生夕死）；
3. **循环引用**兜底：引用计数对环无能为力（`a.b = b; b.a = a`），靠分代 GC 的"不可达检测"清掉 → **CPython 3.4+ 增加 `gc.freeze`/按需关**（嵌入式场景）。
```python
import gc
gc.collect()                  # 手动触发（测试/长循环后释放内存）
gc.disable()                  # 关闭自动回收（实时性要求高、对象生命周期自己管）
gc.get_threshold()            # (700, 10, 10)：计数阈值触发分代扫描
```
**追问"怎么查内存泄漏"**：`tracemalloc`（快照 diff 定位增长点）+ `objgraph.show_backrefs()`（引用链可视化）——比"重启大法"专业一个段位。

**先讲清楚基础：为什么"引用计数 + 分代"要合起来用**

引用计数的直觉：每个对象记一个"被引用次数"，有人引用 +1、解除 -1，**减到 0 立刻回收**——优点：即时、可预测；缺点：① 计数维护有开销；② **环没法处理**——`a.b = b; b.a = a` 就算外部已没人用，两者计数都是 1，永远归不了零。

所以 CPython 再加一层"**分代标记清除**"专门兜环：从"GC Roots"出发做可达性检查，把"互相引用但整体已死"的环清掉；分三代是为了"越老的对象越少扫"（弱代假设：大多数对象活不长）。合起来 = 日常回收快（引用计数）+ 环不漏（分代）+ 可人工干预（`gc` 模块）。

**延伸追问（同一知识面）**
- `weakref` 有什么用？——弱引用**不增加**引用计数：缓存、观察者列表用它，避免"缓存帮忙延长对象寿命"。
- 什么时候手动 `gc.collect()`？——长循环/压测后想看"到底漏没漏"；或 `gc.disable()` 后自己挑时机（实时敏感场景，风险是环堆积）。
- 为什么说"Python 的 GC"要按实现讨论？——引用计数是 CPython 特色；PyPy 等实现不用引用计数（追踪式）——面试聊到 GIL/GC 时带上"实现相关"四个字更严谨。

## Q7. 手写一个滑动窗口限流（接口防刷）

```python
import time, collections

class SlidingWindowLimiter:
    """滑动窗口：比固定窗口精确（无临界翻倍），比令牌桶好解释——适合验证码/发帖频控"""
    def __init__(self, max_count: int, window_sec: float):
        self.max_count = max_count
        self.window = window_sec
        self.hits: dict[int, collections.deque] = {}   # userId -> 时间戳队列

    def allow(self, uid: int) -> bool:
        now = time.monotonic()
        q = self.hits.setdefault(uid, collections.deque())
        while q and now - q[0] >= self.window:         # 滚出窗口外的记录
            q.popleft()
        if len(q) >= self.max_count:
            return False                               # 超限拒绝
        q.append(now)
        return True

# 使用：60 秒内最多 1 条
# if not limiter.allow(user_id): return Result.error("发送过于频繁，请60秒后再试")
```

**答法**：三种限流的对比——固定窗口（临界点可翻倍）、**滑动窗口（精确、内存 O(窗口内请求数)）**、令牌桶（允许突发）、漏桶（恒定速率）。追问"分布式怎么办"——单机内存版只适合单实例；多实例用 **Redis + ZSET**（score=时间戳，`ZREMRANGEBYSCORE` 清窗外 + `ZCARD` 计数，一条 Lua 保证原子）。
**项目挂钩**：邮箱验证码 60s 限流 + 5 分钟过期 + 一次性消费就是这套语义的后端落地 → [更换邮箱验证码流程](../../../dixiyang-vue/docs/更换邮箱验证码流程.md)。

**先讲清楚基础：限流限什么、三种算法一句话**

限流=**给"单位时间的请求数量"设上限**，超了拒绝/等待——保护后端不被刷爆。三种经典算法一句话记住：**固定窗口**（"每分钟 100 个"——最简单，但窗口边界可能瞬间挤进 2 倍流量）；**滑动窗口**（"任意 60 秒内最多 100 个"——精确，代价是要记窗口内每个请求的时间戳）；**令牌桶/漏桶**（恒定速率放行——令牌桶允许攒额度应对突发、漏桶恒定速率流出）。

上面这份代码就是滑动窗口的"时间戳队列"版：每次请求先"弹掉过期的"，再看队列长度超没超。两个细节值得点出：时间用 `time.monotonic()`（单调时钟——不受系统时间调整影响）；存储用 `deque`（两端操作 O(1)）。

**延伸追问（同一知识面）**
- 单机版够用吗？——单实例够；多实例要挪到 **Redis**：`ZSET` 存时间戳，`ZREMRANGEBYSCORE` 清窗外 + `ZCARD` 计数 + `ZADD` 记录——**用 Lua 打包保证原子**。
- 被限了返回什么？——HTTP 语义用 429，并给出"多久后可重试"的提示（登录/验证码场景用业务话术）。
- 限流 / 熔断 / 降级什么关系？——限流=入口拦（防打爆）、熔断=依赖拖垮时快速失败（防拖死）、降级=关非核心功能保核心——三个词几乎总是一起被问。
