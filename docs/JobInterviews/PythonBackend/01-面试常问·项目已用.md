## Q1. FastAPI 的依赖注入与 DB 会话怎么管？

**代码**（`utils/database.py` 全文真实）：

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, sessionmaker
from ..config import DATABASE_URL

engine = create_engine(DATABASE_URL, echo=False)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

class Base(DeclarativeBase):
    pass

def get_db():                       # 生成器依赖：请求级会话，用完必关
    db = SessionLocal()
    try:
        yield db                    # 交给路由使用
    finally:
        db.close()                  # ① finally 保证异常路径也关闭，防连接泄漏
```
```python
# 路由侧（routers/sticky.py 真实用法）
@router.get("/notes")
async def list_notes(
    user_id: int = Depends(get_current_user_id),   # 鉴权也是依赖：复用+可测试
    db: Session = Depends(get_db),
):
    return sticky_service.list_notes(db, user_id, in_pool)
```

**答法**：
1. **`yield` 依赖 = 请求生命周期管理**——FastAPI 在请求结束后自动执行 `yield` 之后的清理代码（等价于 Servlet Filter 的 finally），这是替代手写 `try/finally` 的声明式方案；
2. **为什么 `finally: close()` 不 `remove()`**——close 归还连接到池；`SessionLocal` 是**会话工厂**，每个请求独立会话，天然隔离请求间状态；
3. **追问 `autoflush=False`**：禁止"脏对象自动刷库"的隐式行为——查询前不悄悄发 UPDATE，行为可预测（排查 SQL 神秘多出来时的第一嫌疑）；
4. **追问事务边界**：默认请求内同会话即同事务，`db.commit()` 显式提交（项目 service 层模式），异常路径靠 close 回滚。
**追问2**："连接池参数在哪调？"——`create_engine(..., pool_size=5, max_overflow=10, pool_recycle=1800)`，`pool_recycle` 防 MySQL `wait_timeout` 断连（经典 8 小时坑）。

## Q2. 没有 Flyway/Liquibase，存量库 schema 变更怎么做？

**代码**（`main.py` lifespan 真实节选——项目"启动自愈"模式）：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    Base.metadata.create_all(bind=engine)        # ① 只建缺失的表
    from sqlalchemy import inspect as sa_inspect, text

    # ② 既有表补列：create_all 不给旧表加列 → 缺列则增删改查全 500（Unknown column）
    cols = {c["name"] for c in sa_inspect(engine).get_columns("app_user")}
    if "role" not in cols:
        with engine.begin() as conn:
            conn.execute(text("ALTER TABLE app_user ADD COLUMN role VARCHAR(20) DEFAULT 'user'"))

    s_cols = {c["name"] for c in sa_inspect(engine).get_columns("sticky_note")}
    if "done" not in s_cols:
        with engine.begin() as conn:
            conn.execute(text("ALTER TABLE sticky_note ADD COLUMN done INT NOT NULL DEFAULT 0"))
    yield
```

**答法**：
1. **坑的来历**：`create_all()` 是"建表"不是"迁移"——表存在就跳过，**列差异一概不管** → 模型加了字段、线上表没有 → `Unknown column` 全站 500（项目真实事故，v1.2）；
2. **自愈模式三要素**：`inspect` 检测 → 带 `if not` 幂等判断 → `ALTER` 带 `DEFAULT` 兼容存量行；重启多次无副作用；
3. **何时该升级成正经迁移**：多环境/多版本并存、需要回滚 → Alembic（SQLAlchemy 官方迁移工具，版本化 revision）。**面试答题要主动说清这个边界**——知道临时方案的适用范围比会用工具更值钱；
4. **配套**：改列顺序=先发兼容版代码（读写旧列）→ 跑迁移 → 再发清理版（[灵感墙便利贴实施记录](../../../docs/灵感墙便利贴实施记录.md) §1.2 完整事故复盘）。

## Q3. FastAPI 里跑 CPU 密集/阻塞任务怎么不卡事件循环？

**代码**（项目后台任务真实模式：`idea_cache` + `sticky_cleanup`，daemon 线程 + stop event）：

```python
import threading

_stop = threading.Event()
_bg: threading.Thread | None = None

def start_background() -> None:
    global _bg
    if _bg and _bg.is_alive():          # 幂等：lifespan 重复触发不会起两个
        return
    _stop.clear()
    _bg = threading.Thread(target=_loop, name="sticky-cleanup", daemon=True)  # daemon：进程退出不阻塞
    _bg.start()

def _loop() -> None:
    while not _stop.is_set():           # 用 Event.wait 代替 sleep：可被立即打断
        try:
            sweep()                     # 真实工作：扫文件/查 DB
        except Exception as e:          # 后台任务绝不拖垮主服务
            log.warning("清理异常：%s", e)
        _stop.wait(INTERVAL)            # 等待期间不占 CPU，stop() 时立刻醒

def stop_background() -> None:
    _stop.set()                         # lifespan shutdown 优雅停机
```

**答法**（三层递进）：
1. **为什么不能直接在 async 路由里跑**——`def sweep()` 是同步阻塞调用，会卡住事件循环 → 所有并发请求停摆（FastAPI 规则：`async def` 里调阻塞库=自断经脉）；
2. **三个方案与取舍**：`run_in_executor`（任务型）/ `BackgroundTasks`（请求后轻任务）/ **独立 daemon 线程**（周期性任务，本项目选它）；CPU 密集才需要 `ProcessPoolExecutor`（绕 GIL，见 02 Q1）；
3. **工程细节**：`Event.wait(timeout)` 代替 `time.sleep`（停机秒响应）、`try/except` 包裹（后台任务挂了不能带崩主服务）、`daemon=True`（进程退出不被线程拖住）——这三条是**生产级与玩具级的分界线**。

## Q4. 大文本为什么进文件系统？存储层怎么设计？

**代码**（`services/storage_service.py` 真实节选）：

```python
def save_json(subdir: str, record_id: int, data) -> str | None:
    file_path = _get_file_path(subdir, record_id)          # {root}/{subdir}/{record_id}.json
    _ensure_dir(subdir)
    with open(file_path, "w", encoding="utf-8") as f:
        f.write(json.dumps(data, ensure_ascii=False, indent=2))
    return f"__file__:{subdir}/{record_id}.json"            # DB 只存这个引用

def load_json(subdir: str, record_id: int, db_value):
    if isinstance(db_value, str):
        if db_value.startswith("__file__:"):                # 前缀 = 可判定是引用还是内容
            try:
                with open(os.path.join(STORAGE_ROOT, db_value.replace("__file__:", "")),
                          encoding="utf-8") as f:
                    return json.load(f)
            except FileNotFoundError:
                log.warning("文件不存在: %s", db_value)      # 降级不抛错（弱一致业务）
                return None
        try:
            return json.loads(db_value)                     # 兼容老数据：内联 JSON
        except (json.JSONDecodeError, TypeError):
            return {"content": db_value} if db_value else None
```

**答法**：
1. **为什么**——聊天链/便签正文是长文本：进 DB 撑大行页、拖慢备份、膨胀 binlog；文件系统按需读、冷数据零成本；
2. **`__file__:` 前缀承担三职责**：可判定（引用 vs 内容）、可迁移（改 `STORAGE_ROOT` 换根）、可兼容（老内联数据平滑过渡）；
3. **DB 与文件的事务缝隙怎么补**（高频追问）：先提交行、后写文件，失败会产生"空内容行" → 用**对账任务**兜底（文件有 DB 无=删、DB 有文件无=告警），见 [Practical/08](../Practical/08-排错方法论.md) 的双向对账脚本；
4. **进阶**：量更大上对象存储（S3/OSS），本地文件是过渡形态——要主动讲出演进路径。

## Q5. Pydantic 校验放哪层？接口契约怎么防手滑？

**代码**（项目 schema 层模式，`schemas/sticky.py` 同构）：

```python
from pydantic import BaseModel, Field

ALLOWED_COLORS = {"yellow", "pink", "blue", "green", "purple"}  # 项目：schema 定义白名单集，service 层二次校验

class NoteCreate(BaseModel):
    content: str = ""                                  # ① 类型+默认值：缺省即校验
    color: str = "yellow"                              # ② 项目现状（str + service 白名单）；更优解见下方 Literal 演进
    x: float = Field(default=0.1, ge=0, le=1)          # ③ 范围约束：归一化坐标 0~1
    y: float = Field(default=0.1, ge=0, le=1)
    images: list[str] = []                             # ④ Pydantic 对模型字段默认值自动拷贝——不受 Python 可变默认坑影响

# 演进：color 收成 Literal["yellow","pink",...] → 枚举白名单在边界生效，OpenAPI 渲染成下拉
# from typing import Literal
# color: Literal["yellow", "pink", "blue", "green", "purple"] = "yellow"

# 路由：req: NoteCreate → 类型即文档（OpenAPI 自动生成）
@router.post("/notes")
async def create_note(req: NoteCreate, ...): ...
```

**答法**：
1. **校验在边界（schema 层）做，业务层只处理合法数据**——service 里到处 `if req.x > 1` 是边界失守的信号（项目 service 里只剩业务规则如 `MAX_CONTENT` 截断）；
2. **三层防线各管什么**：Pydantic 结构/类型/范围（422 自动返回）、service 业务规则（颜色白名单二次防御）、SQLAlchemy 列约束（最后防线）；
3. **追问"422 和业务错误的区别"**——422=请求本身不合契约（前端该修代码），`{code:400}`=业务不可行（前端该弹文案），混用会让前端没法区分；
4. **加分点（演进）**：项目现状 `color: str` + service 白名单——可讲把 color 收成 `Literal` 枚举后 **OpenAPI 文档直接渲染成下拉、校验即文档**，这正是从"能用"到"契约化"的一步演进。

## Q6. 环境配置与密钥怎么管？

**代码**（`config.py` 真实节选 + 关键注释）：

```python
from pathlib import Path
_env_path = Path(__file__).resolve().parent.parent.parent.parent / ".env"
if _env_path.exists():
    from dotenv import load_dotenv
    # override=True：项目 .env 优先于系统环境变量。
    # 系统级（Machine）存在 DEEPSEEK_API_KEY，默认不覆盖会导致 .env 的切换不生效。
    load_dotenv(_env_path, override=True)

DATABASE_URL = os.getenv("DATABASE_URL")               # 敏感项：无硬编码默认值
SECRET_KEY = os.getenv("SECRET_KEY") or os.getenv("JWT_SECRET_KEY")
UPLOAD_DIR = os.getenv("UPLOAD_DIR", "…/uploads")      # 非敏感：有合理默认
```

**答法**：
1. **敏感无默认、非敏感有默认**——两类配置分开写，敏感项取不到就该在启动时报错（而不是带弱默认裸奔）；
2. **`override=True` 的真实原因**：CI/开发机**系统级环境变量**里同名 key 会遮住 `.env`，导致"我明明改了 .env 怎么不生效"（项目踩过的真坑，注释就写在源码里）；
3. **追问"`.env` 提交吗"**——绝不进版本库（本项目 `.gitignore` + 克隆文档要求 `cp .env.example .env`，模板只放占位符）；
4. **追问多环境**——`.env.example` 进库、真 `.env` 本地/密钥管理系统（生产用环境变量注入或 Vault）。

## Q7. 统一响应怎么在 Python 侧实现？

**代码**（`utils/response.py` 项目用法 + Java 侧契约对照）：

```python
class Result:
    @staticmethod
    def success(msg: str = "success", data: Any = None) -> dict:
        return {"code": 200, "msg": msg, "data": data}

    @staticmethod
    def error(msg: str = "error", data: Any = None) -> dict:
        return {"code": 500, "msg": msg, "data": data}

    @staticmethod
    def not_found(msg: str = "资源不存在") -> dict:
        return {"code": 404, "msg": msg, "data": None}

# service 层用法（sticky_service.py 真实）：
# return Result.success("获取成功", [...])  /  Result.not_found("便签不存在")
```

**答法**：**契约跨语言对齐**——Python dict 形状与 Java `Result<T>` 完全一致（`{code,msg,data}`），前端拦截器**一个判断走两个后端**；追问"FastAPI 不是有 HTTP 状态码？"——双轨并存：HTTP 码给网关/运维（401/404/500），业务码给前端渲染文案；`code` 是**业务语义**（404=便签不存在，HTTP 仍 200，前端好处理列表空态）。这正是双后端迁移不炸前端的底层原因（[Java 01 Q5](../JavaBackend/01-面试常问·项目已用.md)）。
