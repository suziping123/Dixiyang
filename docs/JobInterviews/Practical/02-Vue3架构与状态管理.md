## 1. Pinia Store 设计：乐观更新 + 静默回滚

- **知识点**：便签 store 的 `patch()` —— 先改内存立刻渲染（乐观），再 `PUT` 后端；失败**保留乐观值**，靠下次 `fetch` 纠正（便签类弱一致场景），删除同理先 splice 再请求。
- **权衡点（必讲）**：为什么这里敢静默？——便签是低价值弱一致数据，弹错误反而打扰；而登录/支付类必须 toast 报错。**一致性策略按业务分级**。
- **面试话术**："乐观更新的难点不是'先改本地'，是失败路径的回滚策略设计——我按数据的业务等级选择'静默自愈'还是'立即提示'。"
- **关键代码**（`src/stores/stickyStore.ts`，真实节选）：

```ts
async function patch(id: number, body: NoteUpdateBody) {
  const idx = notes.value.findIndex((n) => n.id === id);
  const prev = { ...notes.value[idx]! };
  // ① 先算"只改本次涉及的字段"，构造乐观增量（不能整份替换，会丢并发更新的字段）
  const optimistic: Partial<StickyNoteItem> = {};
  if (body.content !== undefined) optimistic.content = body.content;
  if (body.x !== undefined) optimistic.x = body.x;
  // ...
  // ② 立即写入 store → 视图同步更新（用户零等待）
  notes.value[idx] = { ...prev, ...optimistic };
  try {
    const res = await updateNote(id, body);
    const data = (res as { data?: StickyNoteItem }).data;
    // ③ 服务端返回权威值 → 整份覆盖回填（含 rotation/createTime 等未乐观的字段）
    if (data) notes.value[idx] = data;
  } catch {
    /* ④ 失败：保留乐观值，下次 fetch 纠正（弱一致业务的选择） */
  }
}
```

**分析**（面试可展开的三层）：
1. **增量而非整份**——乐观只 patch 本次变更字段，避免覆盖并发修改；
2. **权威回填**——PUT 成功后用服务端整份覆盖，把 `rotation`、`updateTime` 这类"前端没算"的字段同步对齐；
3. **失败分支是设计出来的**——便签低价值弱一致 → 静默自愈；登录/支付类必须反向操作（回滚 + 报错）。

## 2. 失败静默的反面教材（讲给别人听的教训）

- **知识点**：`fetch/create/patch/remove` 全部 `catch {}` 不提示 → 后端 401/500 时 UI **毫无反应**，用户以为"没保存/没显示"，排错成本极高。这是"静默兜底"做过头的典型副作用。
- **面试话术**："我后来复盘：静默可以不打断用户，但**至少要保证下一次操作能自愈 + 日志可观测**，否则就是把排错成本转嫁给用户。"

## 3. 轮询改状态直连

- **知识点**：拖拽状态原本靠 `setInterval(120ms)` 扫 body class 通知素材池高亮 → 改为 store 里一个 `dragging` ref，**状态直连**：0 轮询、0 延迟、无 timer 泄漏。
- **面试话术**："凡是'用定时器去猜当前状态'的地方，都说明状态源没找对；改成单一状态源直连是更 Vue 的解法。"
- **关键代码**（改造前后，真实）：

```ts
// 改前：PoolWindow 每 120ms 扫 body class 猜"是否在拖拽"
setInterval(() => {
  dragging.value = document.body.classList.contains('sticky-dragging');
}, 120);

// 改后：状态源头直接写 store（StickyNote.vue）
function onPointerDown(e: PointerEvent) {
  dragging.value = true;
  store.dragging = true;   // ← PoolWindow 直接读这个 ref，0 轮询 0 延迟
  window.addEventListener('pointermove', onPointerMove);
  window.addEventListener('pointerup', onPointerUp, { once: true }); // once 防泄漏
}
```

**分析**：旧方案有三宗罪——常驻 timer（页面越多越卡）、120ms 延迟（高亮慢半拍）、class 与状态双源（可能不同步）。新方案 1 行赋值全解决；`{ once: true }` 顺手保证监听器不累积。**判断依据：凡是"轮询去读一个本来就能写"的状态，都该改成事件源头直写。**

## 4. API 封装层（接口收口）

- **知识点**：所有请求集中在 `src/api/*.Api.ts`，业务组件不直接碰 axios；`http.ts` 统一挂 token、统一解 `res.code === 200`、统一错误文案。
- **面试话术**："接口层的价值是**改 baseURL/换鉴权头只动一个文件**，业务代码零改动；同时天然成为前后端字段口径的防腐层。"

## 6. 本地优先存储（Local First）

- **知识点**：章节编辑器**先落 IndexedDB、再异步同步云端**——断网不丢稿、冲突按本地覆盖；是离线可用/防丢稿的标准解法。
- **面试话术**："编辑器类产品的底线是'不丢用户一个字'，所以同步是异步旁路，不是写入主路。"
