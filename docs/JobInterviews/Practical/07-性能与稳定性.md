## 1. 真瀑布流 + 游标无限滚动（⭐ 结构性优化）

- **背景**：原实现是 **CSS multi-column 伪瀑布流 + 页码器**——用户反馈"不是真瀑布流、还要求一次加载全部"。
- **方案**：
  - 前端手写**短列优先真瀑布流**（每次插入最短列，零第三方依赖），替代 multi-column（列填充不可控、DOM 顺序与视觉顺序错乱）；
  - 页码器换 **IntersectionObserver 触底追加** + 游标分页（游标 = `(热度分, id)` 元组，Redis ZSET 名次游标），**不 COUNT 全表**；
  - 终止态"已经到底啦"、四 Tab 中仅广场 Tab 改造（草稿/收藏保留页码器——范围控制）。
- **面试话术**："这个优化的关键词是**结构**：分页模型从 offset 改游标解决深翻页退化，渲染从列流改短列优先解决顺序不可控——不是调参，是换算法。"
- **关键代码**（`src/views/IdeaLibraryView.vue` 真实节选——短列优先核心 12 行）：

```ts
const relayout = () => {
  const cards = Array.from(box.querySelectorAll<HTMLElement>('.wf-item'));
  const cols = Math.max(1, Math.floor((w + gap) / (minCol + gap)));  // ① 列数由容器宽算出
  const colY = new Array<number>(cols).fill(0);                      // ② 每列当前高度
  cards.forEach((el) => {
    el.style.width = `${colW}px`;      // ③ 先统一定宽——无封面卡文字不定高，不先定宽量高无意义
    let col = 0;
    for (let j = 1; j < cols; j++) if (colY[j]! < colY[col]!) col = j; // ④ 找最矮列
    el.style.left = `${col * (colW + gap)}px`;
    el.style.top  = `${colY[col]}px`;
    colY[col] = colY[col]! + el.offsetHeight + gap;                  // ⑤ 该列长高
  });
  box.style.height = `${Math.max(...colY) - gap}px`;                 // ⑥ 容器 = 最高列
}

// 配套：rAF 节流（字体/图片加载导致卡片高度连发变化时合并为一帧）
const scheduleRelayout = () => { cancelAnimationFrame(wfRaf); wfRaf = requestAnimationFrame(relayout); };
```

**分析**（可深挖的点）：
- **为什么用 `left/top` 而不是 CSS columns**：multi-column 的列填充顺序由浏览器决定，DOM 顺序 ≠ 视觉顺序，且高度变化会整列重排"跳卡"；短列优先让**每张卡的位置可计算、可预测**；
- **`transform` 留给 hover 动效**——定位用 `left/top`、动效用 `transform`，两者不打架（若定位也用 transform 会互相覆盖）；
- **无 ResizeObserver 死循环防护**：只 observe 卡片高度，`width` 同值写入不触发、`transform` 不影响尺寸测量 → 观察与写入不成环。

## 6. 稳定性：启动自愈与定期清理

- **知识点**：
  - **启动自动补列**：`create_all` 不给旧表加列 → lifespan 里 `inspect` 缺列则 `ALTER TABLE`（`sticky_note.done`、`app_user.role`），否则缺列期间接口全 500——**迁移自愈模式**；
  - **定期清理**：孤儿文件（DB 无行）+ 空目录每日扫；**DB 查询失败时跳过孤儿判定只做空目录**（防 DB 不可用时盲删文件）。
- **面试话术**："存量库没有迁移框架时，把'补列'做成启动自愈 + 幂等，比手工执行 SQL 可靠；清理任务同理要设计失败降级路径。"
- **关键代码**（`DixyangFast/src/dixiyang/main.py` + `services/sticky_cleanup.py` 真实节选）：

```python
# ① 启动自愈：create_all 不给旧表加列 → inspect 缺列则 ALTER（幂等，重复启动无害）
s_cols = {c["name"] for c in sa_inspect(engine).get_columns("sticky_note")}
if "done" not in s_cols:
    with engine.begin() as conn:
        conn.execute(text("ALTER TABLE sticky_note ADD COLUMN done INT NOT NULL DEFAULT 0"))

# ② 定期清理：孤儿文件判定依赖 DB 全量行 → DB 失败时降级为"只清空目录"
try:
    db = SessionLocal()
    ids = {r[0] for r in db.query(StickyNote.id).all()}
except Exception as e:
    log.warning("DB 查询失败，本轮跳过孤儿文件判定（%s）", e)
    ids = None                       # ← 关键：None = 不判孤儿，绝不在 DB 不可用时盲删文件

if ids is not None:                  # 文件名 id 不在 DB 行集合 → 孤儿，删
    for f in os.listdir(d):
        if int(f[:-5]) not in ids: os.remove(os.path.join(d, f))
if not _has_file(d):                 # 目录树无任何文件 → 空目录，删
    os.rmdir(d)
```

**分析**：
- **缺列模式**是 SQLAlchemy 通病：`create_all()` 对已存在的表**只查不改**，所以"表在、列不在"时查询/插入全 500（`Unknown column`）——补列放 lifespan 且带 `if not in` 判断 = 天然幂等；
- **清理任务的失败路径才是设计重点**：孤儿文件的定义是"DB 没有对应行"，这个判断**必须依赖 DB 可用**——DB 挂了还硬判，就会把所有文件当孤儿删光。`ids = None` 这个降级分支是整个任务的安全阀。
