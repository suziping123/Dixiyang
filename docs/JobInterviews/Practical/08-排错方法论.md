## 方法 1：CDP 浏览器探针取证（不靠猜）

**做法**：headless Chrome 起 9222 → CDP 协议直接操作——`Runtime.evaluate` dump 计算样式、`Emulation.setDeviceMetricsOverride` 切 375 真机视口、`Page.captureScreenshot` 截图复核、断言 DOM 关键值。

**前置：探针要登录态，就用测试账号真登录**（`admin123` / `123456`，见 [开发环境与测试账号](../../开发环境与测试账号.md)）——`POST /api/auth/login` 拿真 token 后写 `token/username/userId/nickname/email/role` 六键再 `reload`。**不要注入伪造 JWT**：守卫能骗过，但接口一次 401 就被拦截器 `clearAuth()` 掉登录页，还会把假数据写进 localStorage 缓存（背景/自定义背景），后续肉眼验收全是脏数据（本项目踩过，见 [Home背景浮层移动端滚动修复](../../../dixiyang-vue/docs/Home背景浮层移动端滚动修复.md) §6）。同理要拦接口就用 `Fetch` 域且 pattern 只写 `*://localhost:5173/api/*`（写成 `*/api/*` 会误伤 `/src/api/*.ts` 模块请求 → 白屏）。

**三个实战**：
1. **毛玻璃蒙板**：聚焦态 dump `getComputedStyle(el).backdropFilter` → 定位全局 `blur(10px)` 规则与 EP `.el-select__input` 命中链——**前两轮肉眼判断全错，CDP 一轮定位**；
2. **移动端冒烟**：375 视口断言 `scrollWidth===375`、卡片 `left` 分两档判双列、Tab `scrollWidth<=clientWidth`，**最后必截图肉眼看**；
3. **落地页探针**：几何/交互/动效探针脚本量化验证。
- **面试话术**："视觉类 bug 我的流程是『假设 → CDP 取证 → 改 → 断言复测』，肉眼只做最后一遍复核。"
- **关键代码**（真实探针套路，脱胎自项目 AGENTS「验证套路」）：

```js
// ① 切 375 真机视口（与设备像素比、移动端行为一致）
await client.send('Emulation.setDeviceMetricsOverride',
  { width: 375, height: 812, deviceScaleFactor: 2, mobile: true });

// ② 一次 evaluate 拿三类证据：溢出断言 + 计算样式 + 布局关键值
const { result } = await client.send('Runtime.evaluate', {
  expression: `JSON.stringify({
    overflow: document.documentElement.scrollWidth - 375,          // 必须为 0
    backdrop: getComputedStyle(document.querySelector('.el-select__input')).backdropFilter, // 必须 "none"
    cols: [...document.querySelectorAll('.wf-item')].map(el => el.offsetLeft)
          .filter((v, i, a) => a.indexOf(v) === i).length           // 双列应为 2
  })`,
  returnByValue: true
});

// ③ 断言过后必截图——数字证明"没坏"，截图证明"好看"
await client.send('Page.captureScreenshot', { path: 'mobile_375.png' });
```

**分析**：这套的价值在**证据链**——`backdropFilter` dump 直接指认全局 `blur(10px)` 规则（前两轮肉眼全错）；`offsetLeft` 去重判列数比 `top` 可靠（CSS columns 按列填充，相邻卡 `top` 必不同）。**面试时把"我改了什么"换成"我怎么证明它是这个原因"，含金量立刻不同。**

## 方法 2：对账式排查（数据层一致性）

**做法**：用户报"没保存/不显示"→ 不先怀疑代码，写脚本 **DB 行 ↔ 磁盘文件全量对账**（`content_path` 是否存在、孤儿文件、空目录），一轮拿到事实：2 行 ↔ 2 文件、0 缺失 → 结论转向"历史 500 + 静默吞错 + 看错目录"三个真因。
- **面试话术**："报障描述往往不可信，我先用最小成本确认**数据到底在不在**，再决定查代码还是查认知偏差。"
- **关键代码**（当时一次定位问题的真实对账脚本 `Temp/opencode/check_sticky.py` 节选）：

```python
# DB 全量行 vs 磁盘文件：缺一个方向都不能下结论
rows = engine.connect().execute(text("SELECT id, user_id, content_path FROM sticky_note"))
missing = [r.id for r in rows
           if not os.path.exists(os.path.join(STORAGE_DIR, r.content_path.replace("__file__:", "")))]
# 反向：磁盘有、DB 无行 = 孤儿文件
ids = {r[0] for r in rows}
orphans = [f for uid in os.listdir(ROOT) for f in os.listdir(f"{ROOT}/{uid}")
           if f.endswith(".json") and int(f[:-5]) not in ids]

print(f"DB行={len(rows)} 文件缺失={len(missing)} 孤儿={len(orphans)}")
# 实跑结果：DB行=2 缺失=0 孤儿=0  →  数据是好的 → 真因转向：历史500 + 静默吞错 + 看错目录
```

**分析**：对账式排查的要点是**双向**——只查"文件缺没缺"会漏孤儿文件，只查"文件在不在"无法解释"看着没保存"。10 分钟脚本换一个确定性结论（数据完好），比直接扎进前端代码猜三小时高效；**结论随后落在三个真因**：缺列 500（历史）、`catch{}` 静默（体验）、看错目录（认知）——每层都有对应修复。

## 方法 4：500 类后端坑——"缺列"模式

- **现象**：查询/新增全部 500 `Unknown column`，但**建表时是好的**。
- **根因**：`Base.metadata.create_all()` **只建缺失的表、不给旧表加列**（SQLAlchemy 通病）。
- **修**：启动 lifespan `inspect()` 缺列自动 `ALTER TABLE`（幂等自愈）+ 一次性补列脚本救现网。
- **面试话术**："ORM 的 create_all 不是迁移工具，存量库必须自己补'列级'自愈逻辑。"
- **关键代码**（现象与根因对照，真实）：

```sql
-- 现象：接口全 500，日志里是这条
SELECT sticky_note.id, ... , sticky_note.done FROM sticky_note
-- Unknown column 'done': in 'field list'
```
```python
# 根因：SQLAlchemy create_all 的行为边界——只 CREATE 缺失的表，从不 ALTER 既有表
Base.metadata.create_all(bind=engine)   # 表已存在 → 对 done 列的缺失一无所知
```
**分析**：所以"建表时好好的、上线后字段一加就 500"这类现象，第一反应就该查**模型有列、库表没列**。修法见 [07 性能与稳定性](./07-性能与稳定性.md) §6 的 lifespan 自愈片段（inspect + ALTER，幂等）。
