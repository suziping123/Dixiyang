## 1. axios 统一封装（拦截器三件套）

- **知识点**：`http.ts` 单实例——请求拦截注入 `Authorization: Bearer`；响应拦截统一 `res.code === 200` 放行、否则 `reject(new Error(msg))`；错误侧从 `error.response?.data?.msg` 提取后端文案。**业务层拿到的永远是"成功值或 Error"，不用各处判 code**。
- **面试话术**："拦截器把'鉴权头 + 协议码 + 错误文案'三件散事收进一个文件，业务代码永远只写 happy path 的反面一个 catch。"
- **关键代码**（`src/utils/http.ts` 真实节选——注意它**比常见教程多了两层现实处理**）：

```ts
http.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

http.interceptors.response.use(
  (response) => {
    const res = response.data;
    if (typeof res === 'string') return res;                 // ① 聊天接口返回纯文本，兼容
    if (res?.code === 401) {                                  // ② 业务码 401（Java 侧规范）
      handleUnauthorized(extract401Message(res));             //    统一清态+跳登录，防重复跳
      return Promise.reject(new Error(res.msg || '登录已过期'));
    }
    return res;                                               // ③ 200/500 都透传，调用者判断
  },
  (error) => {
    if (error.response?.status === 401) {                     // ④ HTTP 401（FastAPI JWT 失败/顶号）
      handleUnauthorized(extract401Message(error.response.data));
      return Promise.reject(new Error('登录已过期'));
    }
    if (error.response?.data) return Promise.resolve(error.response.data); // ⑤ 非 2xx 但有规范 JSON → 透传
    return Promise.resolve({ code: -1, msg: error.message || '网络异常', data: null }); // ⑥ 断网/超时兜底
  }
);
```

**分析**（这套设计经历了什么）：
- **两套 401 并存**：业务码 `res.code === 401`（Java 后端规范）和 HTTP 状态 401（FastAPI 直接抛）都要处理——这是**双后端迁移期**的真实产物；
- **resolve 而非 reject 兜底**（⑥）：把断网也包装成 `{code:-1}` 走 resolve，让业务层**只有一个错误形状**要判断（`res.code !== 200`），代价是放弃 axios 原生 error 语义——这是刻意的取舍，不是不会用 reject；
- `redirectingToLogin` 标志：并发请求同时 401 时**只跳一次**登录页，典型竞态处理。

## 2. unwrap 口径坑：分页对象 vs 直接数组（⭐ 真实排错）

- **根因**：同一页混用两种后端口径——`GET /novel/listall` 返回 `{records:[...], total}` 分页对象，`getCharacters` 返回直接数组。按数组 unwrap → `null ?? []` **恒空** → 下拉/级联全灭，用户话术"后端发来的数据显示不了"。
- **修法**：`unwrap<{records:T[]}>(res)?.records ?? []`；**复制粘贴接口前先对齐口径**。
- **面试话术**："这是典型的'静默失败'——没有报错、只是永远为空。后来我在接口层把分页/非分页两种口径显式命名，新接口必须声明。"
- **关键代码**（同在 `src/api/` 目录下的两个文件，**口径却不同**——坑的现场）：

```ts
// api/ideaApi.ts —— 分页对象口径
export const getNovelOptions = () =>
  http.get<{ records: { id: number; title: string }[] }>('/novel/listall', { params: { page: 1, pageSize: 50 } });
// 正确解法：unwrap<{ records: T[] }>(res)?.records ?? []

// api/characterApi.ts —— 直接数组口径
export const getCharacters = (novelId: number) =>
  http.get<Character[]>(`/novelCharacter/all/${novelId}`);
// 正确解法：unwrap<T[]>(res) ?? []
```

**分析**：错误写法 `unwrap<Character[]>(getNovelOptions 的结果) ?? []` —— `data.records` 不是数组 → `null ?? []` **恒空**，且**不抛错**：下拉永远空白、级联回显失败，用户只能看到"后端发来的数据显示不了"。根因是后端 `GET /novel/listall` 返回 `{records,total}` 而相邻接口返回裸数组——**同页混用两种响应形状**。防御性改法是让 unwrap 带形状断言，形状不符直接在开发期报警而不是静默给空。

## 4. 大文本文件化存储约定（架构级约定）

- **知识点**：**DB 只存路径引用，正文/长文本落文件**——`storage/{module}/{userId}/{sessionId}/{recordId}.json`；DB 字段统一 `__file__:相对路径` 前缀；读取走 `StorageService.load_json()` 统一判前缀。聊天历史、便签正文、角色设定全按此约定。
- **面试话术**："大文本进文件系统、DB 只存引用，是为了控制表膨胀和备份体积；统一 `__file__:` 前缀让'存的是路径还是内容'可判定，读取层一个函数收口。"
- **关键代码**（`DixyangFast/src/dixiyang/services/storage_service.py` 真实节选）：

```python
def load_json(subdir: str, record_id: int, db_value) -> dict | list | None:
    """自动判断 db_value 是文件路径引用还是内联 JSON —— 兼容两种历史存量"""
    if isinstance(db_value, str):
        if db_value.startswith("__file__:"):            # ① 新规范：路径引用
            rel_path = db_value.replace("__file__:", "")
            try:
                with open(os.path.join(STORAGE_ROOT, rel_path), encoding="utf-8") as f:
                    return json.load(f)
            except FileNotFoundError:
                log.warning("文件不存在: %s", rel_path) # ② 只警告不抛错——读取层不炸接口
                return None
        try:
            return json.loads(db_value)                 # ③ 老存量：内联 JSON 字符串
        except (json.JSONDecodeError, TypeError):
            return {"content": db_value} if db_value else None  # ④ 兜底包装
```

**分析**：这个函数是"**存储层协议**"的具象——一个前缀 `__file__:` 承担了三件事：可判定（是引用还是内容）、可迁移（改 `STORAGE_ROOT` 即换根目录）、可兼容（老内联数据平滑过渡）。第 ② 步"文件缺失只 warning"也是刻意的：**读取失败降级为空内容，比 500 掉整个接口更符合弱一致业务**——和前端 `catch{}` 是同一套分级哲学（但前端那套因为完全无线索而过头了，见 §6）。

## 6. 静默失败的代价（错误处理哲学）

- **知识点**：接口层 `catch {}` 静默 + 无日志 → 用户报"没保存/不显示"时无从下手；本轮调查靠**DB 与磁盘文件对账**才定位"数据其实是好的"。
- **面试话术**："错误处理的底线是**可观测**——可以不打扰用户，但必须留下能排查的线索。"
