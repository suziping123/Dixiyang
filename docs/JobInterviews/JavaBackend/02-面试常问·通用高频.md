## Q1. ConcurrentHashMap 为什么线程安全？和 synchronized Hashtable 差在哪？

```java
// JDK8 实现：数组+链表/红黑树，节点级 synchronized + CAS（头节点空则 CAS 写入）
V putIfAbsent(K key, V value) {
    int hash = spread(key.hashCode());
    Node<K,V>[] tab; Node<K,V> f; int n, i, fh; V v;
    if ((tab = table) == null || (n = tab.length) == 0) n = initTable();     // CAS 初始化
    else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {                 // 桶空 → CAS 放头
        if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value))) break;  // 无需锁！
    }
    else if ((fh = f.hash) == MOVED) tab = transfer(tab, nextTab);           // 扩容协助
    else {                                                                   // 桶非空 → 锁住头节点
        synchronized (f) { /* 链表/树插入，锁粒度 = 单个桶 */ }
    }
}
```

**答法三层**：
1. vs **Hashtable**：Hashtable 锁整张表（`synchronized` 方法级）→ 任何写入全表阻塞；CHM 锁**单个桶**（粒度降 N 倍）；
2. vs **Collections.synchronizedMap**：后者本质还是对象锁包装；
3. JDK8 关键升级：**CAS 无锁写空桶 + synchronized 只锁链表头** + 扩容时多线程协助（`MOVED` 态）。
**追问**：`size()`/`get` 要不要锁？——`get` 全程无锁（volatile `val`），`size()` 在 JDK8 是**分段求和的弱一致**，要强一致用 `mappingCount` 也不保证——精确计数得加锁。
**陷阱**：`++i` 复合操作仍不安全（`map.compute` 或 `AtomicInteger` 解决）。

**先讲清楚基础：HashMap 为什么"不安全"、CHM 怎么做到"安全"**

先从最根上讲：`HashMap` 是"数组 + 链表/红黑树"的键值容器，单线程下很好用；但多线程同时写入会出事故——① 值互相覆盖（并发写同一位置，后者顶掉前者）；② JDK7 著名的"死循环"（并发扩容时链表被接成环形，之后查询在环里打转、CPU 跑满）。所以并发场景要换一个"线程安全版"。

让它变安全有三条路线，锁的粒度越来越细：**整表一把锁**（`Hashtable`/`synchronizedMap`——任何时刻只能一个线程读写，功能对、并发差）→ **分段锁**（JDK7 的 CHM：表拆成若干段、各段独立加锁，不同段互不阻塞）→ **桶级锁 + 无锁读**（JDK8：空桶用 CAS 原子写入、非空桶只锁"桶头节点"，读全程不加锁——靠 volatile 保证看见最新值）。CHM 的设计主线就是"锁得越来越少、越来越细"。

**延伸追问（同一知识面）**
- 为什么 CHM 不允许 null 键/值？——并发下 `get` 返回 null 有"二义性"：到底是"键不存在"还是"值就是 null"，分不清（`containsKey` 也补不了——判断完的下一秒状态可能又变）。
- `size()` 为什么是弱一致？——为了不锁全表，用的是"分散计数"（类似 LongAdder 的多格子累加），高并发下只是近似值；要精确计数得自己加锁。
- JDK8 的"防退化"设计有哪些？——桶内链表过长会树化成红黑树（查询从 O(n) 降到 O(log n)）；扩容时其他线程遇到搬迁标记（MOVED）会顺手帮忙搬——把一次性大暂停摊薄成多人协作。

## Q2. 线程池 7 个参数？为什么不用 Executors 直接创建？

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4,                                   // ① core：常驻线程
    8,                                   // ② max：峰值线程
    60L, TimeUnit.SECONDS,               // ③ 空闲线程存活
    new ArrayBlockingQueue<>(100),       // ④ 队列：core 满了先入队（不是先加线程！）
    Executors.defaultThreadFactory(),    // ⑤ 线程工厂（命名，便于日志排查）
    new ThreadPoolExecutor.CallerRunsPolicy() // ⑥⑦ 拒绝策略：由提交线程自己跑 = 天然限流
);
// 执行顺序：core 满 → 入队 → 队满 → 加线程到 max → 还满 → 拒绝策略
```

**必背追问链**：
- **Executors 的坑**：`newFixedThreadPool/newCachedThreadPool` 用**无界队列/无界线程** → 内存 OOM 或线程爆炸（阿里规约禁用原因）；
- **拒绝策略四选一**：`AbortPolicy` 抛异常、`CallerRunsPolicy` 反压降速、`DiscardPolicy` 静默丢（危险）、`DiscardOldestPolicy` 丢最老；
- **参数怎么定**：CPU 密集型 `core = CPU核数`（+1 上下文切换）；IO 密集型 `core = 核数 × (1 + 等待/CPU时间)`，压测定；
- **场景挂钩**：项目的 SSE 流式接口就是单线程池 + 有界超时 + `shutdownNow` 收尾（见 [01 Q2](./01-面试常问·项目已用.md)）。

**先讲清楚基础：为什么需要线程池、7 个参数各管什么**

线程不是免费的：创建/销毁要进内核、每线程占约 1MB 栈内存、数量一多 CPU 光"切换上下文"就忙不过来。**线程池就干三件事**：复用（干完活的线程留着接下一单）、排队（任务多了先攒着，别无限加线程）、兜底（真挤爆了怎么"拒绝"有策略）。7 个参数按三组记：**人数**——core（常驻班组）、max（峰值上限）；**接单方式**——workQueue（排队区）、keepAlive（超出 core 的线程空闲多久回收）；**管理**——ThreadFactory（线程命名，排查日志靠它）、拒绝策略（排队区也满时怎么办）。

接单顺序是反直觉的考点：**core 满 → 进队列 → 队列满 → 才扩到 max → 还满 → 拒绝**（不是"先扩线程再排队"）。

**延伸追问（同一知识面）**
- 为什么设计成"先排队再加线程"？——用少量线程消化突发（大多数任务很短）、把线程增长当最后手段；反过来"队列无界"会让 max 和拒绝策略**永远触发不了**（这正是 `Executors` 工厂方法的坑之一）。
- `execute` 和 `submit` 的区别？——`submit` 会把异常包进 `Future`：不调 `future.get()` 时任务异常**完全静默**（排查"任务没生效"的经典坑）；`execute` 直接抛。
- 线程池怎么优雅收尾？——`shutdown()`（不接新单、做完手头的）vs `shutdownNow()`（中断并返回没跑完的任务清单）。

## Q3. 手写双重检查锁单例，volatile 为什么不能少？

```java
public class Singleton {
    private static volatile Singleton instance;   // volatile 禁止指令重排
    public static Singleton get() {
        if (instance == null) {                   // 第一次检查：无锁快路径
            synchronized (Singleton.class) {
                if (instance == null) {           // 第二次检查：锁内防重复创建
                    instance = new Singleton();   // ← 非原子：①分配内存 ②初始化 ③引用赋值
                }
            }
        }
        return instance;
    }
}
```

**答法**：没有 volatile 时，②③ 可能重排成 ①③②——另一线程在 ①③③ 间拿到**未初始化完成的对象**（半初始化问题，JMM 教科书级考题）。第一层 `null` 检查省锁、第二层防并发重复——两层各司其职，删任何一层都错。
**追问**：更优解？——`Holder` 静态内部类（JVM 类加载锁天然安全）或 `Enum` 单例（防反射/反序列化攻击）。

**先讲清楚基础：单例的难点在哪、"双重检查"到底在检查什么**

单例=全局唯一实例。饿汉式（类加载就创建）简单但"不用也占地方"；懒汉式（第一次用时创建）遇到并发就麻烦："判断 null → 创建"不是一步操作，两个线程可能同时判断通过、各创建一个。**最笨的解法**是给整个 `get()` 加锁——功能对了，但此后**每次取实例都要抢锁**（其实只有第一次需要）。

**DCL 就是来省这把锁的**：第一层 `if (instance == null)` 是无锁快路径（实例建好后绝大多数调用直接返回）；第二层锁内再判一次（防"两个线程同时穿过第一层"）。**volatile 防的是更阴的问题**：`new Singleton()` 在机器层面是"①分配内存 ②初始化对象 ③引用赋值"三步，②③ 之间没有依赖、**可能被重排**——另一个线程看到"引用非空"就拿走用，结果拿到**没初始化完的半成品**。volatile 禁止这种重排 + 保证写立即可见，两个作用缺一不可。

**延伸追问（同一知识面）**
- `Holder`（静态内部类）为什么天生安全？——实例创建的时机推迟到"第一次访问内部类"，而**类的初始化由 JVM 类加载锁保证只执行一次**（`<clinit>`）——不用手写任何同步。
- `Enum` 单例强在哪？——反射 `newInstance()` 对枚举直接抛异常、反序列化也返回同一实例——把两条"单例破坏"路径都堵死。
- DCL 的第一层检查能删吗？——删了功能仍对（锁内再判也能防重复），但**每次调用都得进锁**；双层存在的意义就是"初始化完成后走无锁路径"。

## Q4. Spring @Transactional 什么时候会失效？

```java
@Service
public class NovelService {
    public void createNovel() {
        this.inner();          // ❌ 同类内部调用不走代理 → 事务不生效！
    }
    @Transactional
    public void inner() { /* 期望回滚 */ }
}
```

**失效清单（背全可加分）**：
1. **同类自调用**（上面）：Spring 事务基于 AOP 代理，`this.xxx()` 绕过代理 → 解法：注入自身 `@Lazy self`、拆类、或 `AopContext.currentProxy()`；
2. 方法非 `public`：代理只拦 public（CGLIB 默认）；
3. 异常被吞：`try-catch` 吞了 `RuntimeException` → 管理器认为成功；
4. 抛的是**受检异常**：默认只回滚 `RuntimeException/Error`，需 `@Transactional(rollbackFor = Exception.class)`；
5. 引擎不支持：MyISAM 无事务（项目 MySQL 8 默认 InnoDB 无虞）；
6. 多线程操作跨线程连接：事务绑定在 ThreadLocal，子线程拿不到。
**追问**：传播行为最常问——`REQUIRED`（默认，有则加入）/ `REQUIRES_NEW`（挂起当前开新事务，**日志表写入不随主流程回滚**就靠它）/ `NESTED`（savepoint 嵌套）。

**先讲清楚基础：事务要解决什么问题、Spring 靠什么"加"上去**

事务要的是"**一组操作要么全成功、要么全失败**"——扣了款没入账、建了小说没建章节，都是事故（对应 ACID 的 A：原子性）。Spring 的做法不是把事务代码写进你的方法，而是**用代理包一层**：调用先进代理对象 → 代理开事务 → 调真实方法 → 正常返回就提交、抛异常就回滚。**所以"事务失效"的本质几乎都是"调用绕过了代理"**——`this.inner()` 用的是原始对象、非 public 方法代理拦不住、异常被 try-catch 吞掉代理以为一切正常……背"失效清单"前先记"代理"这个总纲，清单自然推导得出来。

**延伸追问（同一知识面）**
- 为什么默认只回滚 `RuntimeException`？——语义约定：受检异常 = 调用方"预期之内、要处理"的（框架不擅自回滚）；要改就 `rollbackFor = Exception.class`。
- `REQUIRES_NEW` 的实战场景？——挂起外层、新开独立事务："主流程回滚了，操作日志也要留下"就靠它；注意它**额外占一个连接**（连接池要留量）。
- 事务里最怕什么？——**长事务**：远程调用/大循环塞进事务 → 连接和锁被长期占住 → 并发一上来互相拖死。纪律："事务里只放数据库操作"。

## Q5. MySQL 索引：为什么 B+ 树？回表与覆盖索引 + EXPLAIN

```sql
-- 表结构示意：(user_id, title) 联合索引
SELECT id, title FROM novels
WHERE user_id = 6 AND title LIKE 'A%';

EXPLAIN SELECT * FROM novels WHERE user_id = 6;
-- 关键列：type(range/ref/const 最好, ALL 全表最差)、key(实际用的索引)、rows(预估扫描)、Extra
-- Extra 出现 Using filesort / Using temporary → 优化信号
```

**答法**：
1. **为什么 B+ 树**：非叶节点存 key 不存数据 → 单节点扇出大 → 树矮（3 层存千万行，磁盘 IO 3 次）；数据全在叶子 + 叶子链表 → **范围查询顺链表扫**（B 树要中序遍历）；
2. **最左前缀**：`(a,b,c)` 索引，`b,c` 单独查用不上 → 联合索引列序即面试题；
3. **回表**：二级索引叶子存主键 → 非覆盖需回主键索引再查一次 → `SELECT` 只取索引列即**覆盖索引**，`Extra: Using index`；
4. **`LIKE 'A%'` 能走索引、`'%A'` 不能**（前缀通配破坏有序性）。
**项目挂钩**：广场游标分页替代 `OFFSET` 深翻页（`LIMIT 1000000,10` 每次扫百万行再丢弃）——真实落地的索引优化。

**先讲清楚基础：索引是什么、为什么 B+ 树是"最不坏"的选择**

索引=**书的目录**：没有它只能一页页翻（全表扫描），有它先定位再翻页（索引查找）。组织目录的唯一约束是"**磁盘 IO 很贵**"——目标是每次查询**踩最少的磁盘页**：二叉树每个节点只分两路、树太高（IO 次数多）；B 树虽然矮了，但**非叶节点也存数据**——一页装的分叉就少；**B+ 树**则非叶只存 key（一页几百个分叉、3 层装千万行）+ 数据全在叶子并用链表串起（范围查询顺链扫）——"矮"和"顺序扫"两个需求同时满足。

再补一个 InnoDB 关键设定：**主键索引的叶子直接存整行**（聚簇索引）；二级索引叶子里存的是**主键值**——按二级索引查完整行，要拿主键回主键树再查一次（**回表**）；`SELECT` 只要索引里有的列，就不用回（**覆盖索引**，`Extra: Using index`）。

**延伸追问（同一知识面）**
- 联合索引的列序怎么定？——常单独查的、区分度高的放前面：`(a,b)` 能服务 `a=?` 和 `a=? AND b=?`；反过来 `b=?` 就用不上（最左前缀）。
- 哪些写法让索引白建？——对列做函数运算（`YEAR(create_time)=2026`）、隐式类型转换、`LIKE '%x'` 前导通配——共同点：破坏有序性，只能全扫。
- 游标分页为什么比 `OFFSET` 快？——`WHERE id < 上页最后一个id LIMIT 10` 直接按主键有序定位；`LIMIT 1000000,10` 得先扫出一百万行再丢弃（项目广场列表的真实优化）。

## Q6. Redis：缓存穿透/击穿/雪崩，分别怎么办？

```java
// ① 穿透（查根本不存在的数据，绕过缓存打 DB）→ 空值缓存 + 布隆过滤器
public NovelVO get(long id) {
    String key = "novel:" + id;
    String v = redis.get(key);
    if ("NULL".equals(v)) return null;                       // 空值也缓存（短 TTL）
    if (v != null) return deserialize(v);
    NovelVO db = mapper.selectById(id);
    if (db == null) redis.setex(key, 60, "NULL");            // 防穿透：回填空标记
    else redis.setex(key, 300, serialize(db));
    return db;
}

// ② 击穿（热 key 过期瞬间并发打 DB）→ 互斥锁重建
if (redis.setnx("lock:" + id, "1", 5)) {                     // 只有一个线程能回源
    try { db = mapper.selectById(id); redis.setex(key, 300, serialize(db)); }
    finally { redis.del("lock:" + id); }
} else { Thread.sleep(50); return get(id); }                 // 其他人稍后重读缓存

// ③ 雪崩（同时大面积过期/Redis 宕机）→ TTL 加随机抖动 + 多级缓存 + 熔断降级
redis.setex(key, 300 + ThreadLocalRandom.current().nextInt(60), serialize(db));
```

**答法**：三个概念**按"打到 DB 的原因"区分**——穿透=查不存在的（空值/布隆挡）、击穿=单点过期（互斥重建/逻辑不过期）、雪崩=成片过期或缓存宕机（TTL 抖动/集群/降级兜底）。
**项目挂钩**：本项目 Redis 接入后 P95 1844→368ms（5×），且 Redis 宕机自动降级直查 DB、压测 0 错误——缓存**必须设计不可用路径** → [Redis优化效果对比](../../../docs/Redis优化效果对比.md)。

**先讲清楚基础：缓存凭什么能救 DB、三场"事故"各是怎么发生的**

缓存的定位：**把热点数据放内存**（Redis），请求先问缓存、命中就直接返回——DB 只接"缓存没有"的那部分流量，压力大减。所谓"穿透/击穿/雪崩"，本质都是"**请求绕过缓存、直接砸到 DB**"，区别只在绕过的原因：

- **穿透**：查的数据**根本不存在**（缓存永远没有、每次问 DB——恶意刷不存在 id 的典型）→ 空值也缓存（短 TTL）+ **布隆过滤器**提前挡；
- **击穿**：**某个热点 key 恰好过期**的瞬间——大量并发同时发现"缓存没了"、一起涌向 DB 重建 → **互斥锁**（只放一个线程回源，其余等待）或逻辑过期（不设物理 TTL、异步单飞重建）；
- **雪崩**：**大批 key 同时过期**或 **Redis 整体宕机**——缓存层集体失效、全量流量砸 DB → TTL 加**随机抖动**（错开死亡时间）+ 集群高可用 + 熔断/降级兜底。

**延伸追问（同一知识面）**
- 布隆过滤器怎么做到"提前挡"？——位数组 + 多个哈希：测"不存在"**一定准**（直接拒绝）；测"存在"**可能误报**（放行去查，查空再回填空值、两层配合）。
- 互斥锁方案要注意什么？——等锁的线程要**自旋等待且设上限**；锁本身必须**带过期时间**（持锁者挂了不能锁死全场）。
- Redis 真挂了怎么办？——必须事先设计"不可用路径"：降级直查 DB + 限流整流 + 恢复后逐步放量（项目实测过这条路径：降级直查、压测 0 错误）。

## Q7. JVM 排查 OOM 的完整动作

```bash
# ① 启动期兜底：OOM 自动 dump
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/app/heap.hprof -jar app.jar

# ② 现场快照
jps -l                     # 找进程 PID
jmap -heap:live <pid>      # 堆概况（老年代持续涨 = 泄漏嫌疑）
jstat -gcutil <pid> 1000   # 每秒 GC 情况：O 列老年代只增不减、FGC 频繁 → 即将 OOM

# ③ 分析 dump
jhat heap.hprof            # 或 MAT / VisualVM：支配树找 "Retained Heap" 最大的对象
# MAT 重点看：Dominator Tree + "疑似泄漏"报告（如 ClassLoader 链、静态集合持有）
```

**答法框架**：**先判断泄漏还是溢出**——`jstat` 老年代单调上涨+FGC 后不降=泄漏（找引用链：静态 Map、未关闭连接、监听器未注销）；涨到顶才炸=溢出（调 `-Xmx` 或减小批处理）。附 JVM 分代直觉：新生代 MinorGC 便宜（复制算法）、对象晋升老年代的路径（大对象/年龄阈值/ Survivor 满）。
**项目挂钩**：前端同款思路——`{ once: true }` 监听器、定时器清零，防的是 JS 侧的"泄漏"。

**先讲清楚基础：OOM 是什么、排查为什么先从 GC 看起**

OOM（`OutOfMemoryError`）一句话：**要分配新对象，但内存腾不出来了**。JVM 内存分好几块（堆装对象、元空间装类信息、另有直接内存），绝大多数的 OOM 是"堆"的问题；堆又分两种剧本——**内存泄漏**（对象早该回收、却被"看不见的引用"抓着：静态集合越积越多、监听器没注销、连接没关）vs **内存不够（溢出）**（对象都在正常使用，就是业务量/批处理/缓存太大装不下）。

**为什么排查第一步是 `jstat` 看趋势**：为了区分这两种剧本——Full GC 之后老年代**能降**（对象可回收，只是峰值高）→ 加容量/优化批处理；**降不下来**（有东西死死抓着）→ 泄漏，必须找到"谁在抓"。找"谁"就是 dump + MAT：**支配树（Dominator Tree）** 看 Retained Heap 最大的对象链——"干掉它能释放多少内存"，沿引用链就能找到持有者。

**延伸追问（同一知识面）**
- OOM 还有哪些"兄弟"？——`Metaspace`（动态类/类加载器泄漏）、`Direct buffer memory`（NIO 堆外内存）、`GC overhead limit exceeded`（GC 耗 98% 时间却回收不足 2%）、`unable to create native thread`（线程栈内存撑爆）。
- GC Roots 是什么？——可达性分析的起点（栈上引用、静态变量、常量等）；"对象被谁抓着"=从 Roots 能不能到达它。
- 生产怎么防患于未然？——`-XX:+HeapDumpOnOutOfMemoryError` 自动留现场、监控老年代趋势（只涨不降就告警）、`-Xmx` 设合理并压测定基线。
