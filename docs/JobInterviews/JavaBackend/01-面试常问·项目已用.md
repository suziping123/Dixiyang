## Q1. JWT 认证过滤器怎么写？怎么做单点登录（顶号）？

**代码**（`dixiyang-engine/.../Config/JwtAuthenticationFilter.java` 真实节选）：

```java
@Override
protected void doFilterInternal(HttpServletRequest request,
                                HttpServletResponse response,
                                FilterChain filterChain) throws ServletException, IOException {
    String authHeader = request.getHeader("Authorization");
    if (authHeader != null && authHeader.startsWith("Bearer ")) {
        String token = authHeader.substring(7);
        try {
            Claims claims = jwtutils.parseClaims(token);
            String userId = claims.getSubject();
            String sid = claims.get("sid", String.class);
            // 单点登录：token 带会话号(sid) 才比对；旧版 token 无 sid 兼容放行至自然过期
            if (sid != null) {
                AppUser user = appUserMapper.selectById(Long.parseLong(userId));
                if (user == null || !sid.equals(user.getSessionId())) {
                    write401(response, "账号已在其他设备登录");   // ① 新设备登录 → 旧 token 立即失效
                    return;
                }
            }
            // 构建认证对象并放入上下文（核心两步）
            UsernamePasswordAuthenticationToken authentication =
                    new UsernamePasswordAuthenticationToken(userId, null, Collections.emptyList());
            SecurityContextHolder.getContext().setAuthentication(authentication);
            request.setAttribute("userId", Long.parseLong(userId));
        } catch (RuntimeException e) {          // 解析失败 = 过期/篡改
            write401(response, "Token已过期或无效");
            return;
        }
    }
    filterChain.doFilter(request, response);    // 无 token 也放行 → 交给 URL 级授权规则决定
}
```

**答法**：
1. **过滤器链路**：取头 → 解析 claims → 建认证对象 → `SecurityContext` → 放行；解析失败直接 401 不进业务；
2. **单点登录机制**：登录时生成 `sid` 写入 **token claim + 用户表**，每次请求比对——不一致即顶号踢出。比"服务端 session 黑名单"轻（无需存 Redis），代价是**旧 token 在 sid 变更前天然有效**，所以靠 sid 比对兜底；
3. **兼容性设计**（可加分）：旧 token 无 `sid` 放行至自然过期——**存量凭证不能一刀切作废**，否则全体被踢。
**追问**："不查库能验签吗？"——能验签不等于有效，验签管伪造、sid 比对管吊销，两件事。

## Q2. SSE 流式接口怎么实现？线程模型是什么？

**代码**（`Controller/ChatController.java` 真实节选）：

```java
@PostMapping(value = "/chat/stream")
public SseEmitter chatStream(@RequestBody ChatRequest request) {
    SseEmitter emitter = new SseEmitter(1800000L);        // ① 30 分钟超时（AI 生成可能很长）
    ExecutorService executor = Executors.newSingleThreadExecutor(); // ② 专用线程，不阻塞 Tomcat 工作线程

    executor.execute(() -> {
        try {
            String fullPrompt = buildFullPrompt(request);
            Flux<String> flux = chatClient.prompt(fullPrompt).stream().content(); // ③ Spring AI 真流式
            CountDownLatch latch = new CountDownLatch(1);

            StringBuilder buf = new StringBuilder();
            AtomicReference<String> state = new AtomicReference<>("INIT");         // ④ 状态机

            flux.subscribe(
                token -> {
                    buf.append(token);
                    // 实时检测 <thinking> 标签边界，拆分 thinking/content 两路事件
                    if ("INIT".equals(state.get())) { /* 见源码：64 字节无标签即判纯内容 */ }
                    if ("THINKING".equals(state.get())) { /* 检测 </thinking>，安全推送留尾匹配 */ }
                },
                error -> { emitter.completeWithError(error); latch.countDown(); },
                () -> { emitter.complete(); latch.countDown(); }
            );
            latch.await();                                 // ⑤ 桥接：Servlet 线程等流结束
        } catch (Exception e) {
            emitter.completeWithError(e);
        } finally {
            executor.shutdown();
        }
    });
    emitter.onTimeout(() -> executor.shutdownNow());       // ⑥ 超时/客户端断开要收尾线程
    return emitter;
}
```

**答法**（四个必讲点）：
1. **为什么新开线程**：`SseEmitter` 是异步的，但 Spring AI 的 Flux 订阅/阻塞等待不能占住 Tomcat 工作线程池——否则并发两个对话就耗尽线程；
2. **状态机拆标签**：LLM 输出是逐 token 的，`<thinking>` 开始/结束标签**可能被切在两个 token 中间** → 缓冲区 + 状态机 + "留尾匹配"（末尾可能属于未完标签的字符不外发），这是流式解析的通用套路；
3. **生命周期收尾**：超时、客户端断开（前端 AbortController）都要 `shutdownNow`，否则线程泄漏；
4. **追问"为什么不用 WebFlux"**：SseEmitter 是 MVC 下的轻量异步方案，改动小；WebFlux 全异步收益更大但整栈迁移成本高——**存量项目的务实选择**。

## Q3. 统一响应 + 全局异常处理怎么设计？

**代码**（接口约定真实 + 项目 AGENTS 建议方案）：

```json
// 统一响应格式（前后端契约，Java/Python 双端一致）
{ "code": 200, "msg": "success", "data": {} }
```
```java
// 全局异常处理（按 dixiyang-engine/AGENTS.md 规范方案；系统异常文案收紧为通用语，不透出内部 message）
@ControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(RuntimeException.class)
    public Result<String> handleRuntime(RuntimeException e) {
        log.warn("业务异常: {}", e.getMessage());
        return Result.error(e.getMessage());              // 业务异常 → 前端可展示文案
    }
    @ExceptionHandler(Exception.class)
    public Result<String> handleException(Exception e) {
        log.error("系统异常", e);                          // 系统异常 → 记全栈，只回通用文案
        return Result.error("服务器内部错误");
    }
}
```

**答法**：**契约先行**——`{code,msg,data}` 一个形状走全站（前端拦截器只需判一处，见前端 Q1）；异常分两级：业务异常回原文案、系统异常记日志回通用文案（**不把堆栈/SQL 泄给前端**，安全点）。追问"为什么不每个接口 try-catch？"——AOP 横切收口，Controller 专注业务，且不会漏。
**项目挂钩**：前端 http.ts 的"只有一个错误形状"就建立在这份契约上。

## Q4. MyBatis Plus 怎么防 SQL 注入 + 分页怎么写？

**代码**（MyBatis Plus 标准用法；项目 Mapper 现用同款 `LambdaQueryWrapper` 做全量条件查询，`selectPage` 为同栈分页演进）：

```java
// 分页：Page 由插件自动改写 SQL（物理分页，不是内存截断）
Page<Novels> page = new Page<>(pageNum, pageSize);
LambdaQueryWrapper<Novels> qw = new LambdaQueryWrapper<Novels>()
        .eq(Novels::getUserId, userId)          // ① 参数绑定：值进 ? 占位，永不拼接
        .like(rights != null, Novels::getTitle, keyword)   // ② 条件为 false 自动忽略该段
        .orderByDesc(Novels::getUpdateTime);
Page<Novels> result = novelMapper.selectPage(page, qw);

// ❌ 反面（拼接即注入）：
// "SELECT * FROM novels WHERE title LIKE '%" + keyword + "%'"   →  keyword = ' OR 1=1 --
```

**答法**：
1. **注入原理**：SQL 结构被用户输入改变 → 一律**预编译参数绑定**（`#{}`/`?`），`${}` 才是拼接、只能用于白名单（如列名）；
2. **分页**：MyBatis Plus 分页插件生成 `LIMIT`（物理分页）；深分页 `LIMIT 1000000,10` 退化问题 → 游标/延迟关联（项目广场游标分页就是这个解法的落地，可联动前端 Q4 讲）；
3. **动态条件**：`eq(boolean, ...)` 第一参控制段落是否存在——避免手拼 if 漏空格/引号。

## Q6. 密码存储怎么做才安全？

**代码**（项目安全规范 + 标准用法）：

```java
// 项目真实用法：Spring Security BCryptPasswordEncoder（SecurityConfig 注入 PasswordEncoder Bean）
// 注册：BCrypt 加盐哈希（每用户盐内嵌于哈希串，无需额外字段）
String hash = passwordEncoder.encode(rawPassword);   // 内部自动 gensalt，默认 work factor 10（可 new BCryptPasswordEncoder(12) 调高）
user.setPassword(hash);

// 登录：库函数比对（内部提取 salt + 恒定时间比较，不会短路泄露前缀）
boolean ok = passwordEncoder.matches(inputPassword, user.getPassword());
// ❌ 反面：MD5/SHA1 无盐 → 彩虹表秒破；equals 比对哈希 → 计时侧信道
```

**答法**：**不可逆 + 每用户盐 + 慢哈希**（BCrypt 的 work factor 就是为拖慢暴力破解设计）；比对用库函数不做字符串 `equals`。追问"存库的是密文吗？"——不是加密（无解密需求），是哈希，方向不同。
**项目挂钩**：登录风控（60s 限流、验证码 5 分钟过期、一次性消费）+ JWT 顶号，构成完整认证闭环 → [单点登录与登录风控](../../../docs/单点登录与登录风控.md)。
