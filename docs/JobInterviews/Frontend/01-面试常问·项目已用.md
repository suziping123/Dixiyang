## Q1. axios 怎么封装的？401 怎么处理？

**代码**（`src/utils/http.ts` 真实节选）：

```ts
http.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});
http.interceptors.response.use(
  (response) => {
    const res = response.data;
    if (typeof res === 'string') return res;                  // 聊天接口纯文本兼容
    if (res?.code === 401) {                                   // 业务码 401（Java 后端规范）
      handleUnauthorized(extract401Message(res));
      return Promise.reject(new Error(res.msg || '登录已过期'));
    }
    return res;                                                // 200/500 透传，调用者判断
  },
  (error) => {
    if (error.response?.status === 401) {                      // HTTP 401（FastAPI JWT 抛出）
      handleUnauthorized(extract401Message(error.response.data));
      return Promise.reject(new Error('登录已过期'));
    }
    if (error.response?.data) return Promise.resolve(error.response.data); // 有规范 JSON → 透传
    return Promise.resolve({ code: -1, msg: error.message || '网络异常', data: null }); // 断网兜底
  }
);
// 防并发重复跳登录：
let redirectingToLogin = false;
export function handleUnauthorized(message?: string) {
  if (redirectingToLogin) return;
  clearAuth();
  if (window.location.pathname === '/login') return;   // 已在登录页：只清态不跳转
  redirectingToLogin = true;
  if (message) ElMessage.warning(message);
  window.location.href = '/login';
}
```

**答法**：三层——① 请求层收 token；② 响应层区分**业务码 401**（Java 规范 `res.code`）和 **HTTP 401**（FastAPI 直接抛），双后端共存期两套都要接；③ 断网/超时也 `resolve` 成 `{code:-1}`，让业务层**只有一个错误形状**判断。追问"为什么不 reject？"——刻意统一错误形状，代价是放弃 axios error 语义，属于取舍不是不会用。

**先讲清楚基础：拦截器是什么、"401"是什么**

axios 拦截器 = 每次请求/响应都会路过的"关卡"：**请求发出前**过一遍（请求拦截器）、**响应回来时**过一遍（响应拦截器）。封装的目标是"所有请求都要干的事，只写一遍"——带 token、识别登录过期、统一报错，不必在每个页面重复。

**为什么会遇到"两种 401"**：HTTP 规范里 401 = 未通过身份认证（403 = 认证了但没权限）。本项目两代后端习惯不同：**Java 后端**把业务结果都压进 HTTP 200 的响应体（登录过期体现为业务码 `res.code === 401`）；**FastAPI 后端**按规范直接抛 HTTP 401 状态码。拦截器两条分支都接，是双后端过渡期的兼容层——能主动说明这一点，比只说"我处理了 401"加分。

**token 是怎么工作的（存放位置是道安全取舍题）**：登录成功后前端拿到 token（一串凭证），之后每个请求由请求拦截器塞进 `Authorization: Bearer <token>` 头，服务端验过就知道"你是谁"。为什么存 `localStorage`：简单、跨域可用；代价是页面一旦有 XSS，token 就能被偷走。更严的方案是 `httpOnly Cookie`（JS 读不到），但要额外防 CSRF——没有免费的午餐，按威胁模型选（本项目选前者，属简化取舍）。

**"断网也 resolve"为什么是有意设计**：把网络故障也整形为 `{code:-1, msg}`，让调用方**永远只判断一种错误形状**——不用在每处写 `error.response?.data?.msg` 的三层兜底。代价：丢掉 axios 原始错误对象（调试信息变少）。这是显式取舍，主动讲出来。

**延伸追问（同一知识面）**
- 多个拦截器谁先执行？——实测本项目 axios 版本：请求拦截器**后注册的先执行**、响应拦截器**先注册的先执行**（合成"洋葱"：后注册的在外层，请求先穿过它、响应最后穿过它）；新版提供配置项可切换为注册顺序——面试讲清洋葱模型、说明"以所用版本实测为准"即可。
- token 过期怎么无感续期？——标准方案：短效 access token + 长效 refresh token，401 时静默刷新、重放原请求。本项目用"长效 token + 顶号机制"简化处理，要能讲清 trade-off。

## Q2. 说说乐观更新，失败怎么办？

**代码**（`src/stores/stickyStore.ts` 真实节选——注释重点在失败路径）：

```ts
async function patch(id: number, body: NoteUpdateBody) {
  const idx = notes.value.findIndex((n) => n.id === id);
  if (idx < 0) return;
  const prev = { ...notes.value[idx]! };            // ① 写入前快照：失败本可拿它回滚——但本项目故意不回滚（见 ④）
  const optimistic: Partial<StickyNoteItem> = {};
  if (body.content !== undefined) optimistic.content = body.content;
  // …只带本次要改的字段（防覆盖拖拽过程中的并发写入）
  notes.value[idx] = { ...prev, ...optimistic };    // ② 先改 UI：零网络等待
  try {
    const data = (await updateNote(id, body)).data;
    if (data) {
      const i = notes.value.findIndex((n) => n.id === id); // 等待期间列表可能增删，重新定位
      if (i >= 0) notes.value[i] = data;            // ③ 成功：服务端权威整份回填（rotation/updateTime 本地没算）
    }
  } catch {
    /* ④ 失败：故意保留乐观值、不回滚——弱一致业务，下次 fetch 权威对齐。
       回滚反而有害：拖拽中弹回旧坐标打断手势；await 期间快照也可能已被后续乐观写入超越 */
  }
}
```

**答法（题眼是"失败怎么办"，先答失败兜底，成功路径被追问再展开）**：
1. **失败兜底三种策略，按业务分级**：① 回滚快照——失败时恢复更新前原值+提示"保存失败"，标准做法；② 自动重试——网络抖动类错误重试，重试耗尽再回滚；③ **不回滚、靠下次 fetch 自愈**——弱一致业务。便签选 ③。
2. **为什么敢不回滚**：便签显示值短暂偏差刷新即对齐；而回滚反而有害——拖拽进行中弹回旧坐标会打断手势，且快照会过期（await 期间 zIndex 已被后续乐观写入改过，源码注释原话"勿拿旧快照覆盖"）。
3. **边界**：强一致业务（支付/删除/登录）必须回滚+报错——"下次对齐"兜不住"钱扣了 UI 没扣"这种事故。
4. **追问**："用户看到的和库里不一致？"——接受，这是一致性换交互流畅度的显式取舍；fetch 全量覆盖内存保证收敛（下次拉取/刷新自动对齐）。
5. **追问**："为什么不做成失败自动回滚？"——回滚本身也会失败（网络还是断的），且要处理"回滚期间用户又操作了"的二次竞态；弱一致自愈是**用最小机制换可预期行为**。

**先讲清楚基础：什么叫"乐观更新"**

用户一操作，两处状态要变形：**屏幕上的 UI** 和**服务器里的数据**。
- **悲观更新**：先等服务端确认，再改 UI——稳，但要等一个网络往返（弱网下就是"点了没反应"）；
- **乐观更新**（本项目便签）：**先改 UI**（乐观假设会成功），再异步发请求；成功用服务端权威值回填，失败走兜底。

体验差异：乐观更新"点下去立即有反应"；代价是"结果没落定前，UI 展示的是假设"。选择标准 = 业务对"短暂不一致"的容忍度——正式说法就是"**最终一致 vs 强一致**"：便签/点赞属最终一致（晚几秒对齐没人损失）；支付/库存必须强一致（"钱扣了 UI 没扣"是事故）。

**本项目失败路径的两处真实设计（源码注释为证）**：
1. **不回滚**：拖拽中失败弹回旧位置会打断手势；且快照会过期——await 期间用户又拖了一次，拿旧快照覆盖等于**用更旧的数据盖掉更新的数据**（注释原话"勿拿旧快照覆盖"）。靠"下次 fetch 全量覆盖"自愈；
2. **只提交本次改动的字段**（乐观子集），不整对象覆盖——防止把拖拽中的并发改动（如 zIndex）写回旧值；成功回填前**重新 findIndex**——await 期间列表可能增删，旧下标已失效。

**延伸追问（同一知识面）**
- 服务端怎么防并发覆盖？——**乐观并发控制（OCC）**：记录带 `version` 字段，更新时校验 `UPDATE ... WHERE id=? AND version=?`，不匹配返回 409、客户端重新拉取。本项目未做版本校验（靠全量 fetch 兜底）——能主动讲出这个差距；
- 重试的前提是什么？——**幂等**：同一请求执行一次与多次结果相同（PUT 语义天然幂等、POST 通常不）；不幂等的接口重试会出"重复提交"事故；
- 失败策略全家桶：回滚 / 重试 / 离线入队重放 / 权威拉取对齐（reconcile）——真实系统常组合"重试耗尽 → 回滚 → 提示"。

## Q3. 拖拽和点击冲突怎么处理？（事件冲突实战）

**代码**（`src/components/sticky/StickyNote.vue` 真实节选）：

```ts
let moved = false;         // 信号1：是否真发生了位移
let suppressClick = false; // 信号2：抑制拖拽后浏览器补发的 click

function onPointerDown(e: PointerEvent) {
  if ((e.target as HTMLElement).closest('button, textarea, input')) return; // 控件不进拖拽
  moved = false;                                              // 每次按下必须重置！
  window.addEventListener('pointerup', onPointerUp, { once: true });
}
function onPointerUp() {
  if (!moved) return;                    // 没位移 = 普通点击，不抑制
  suppressClick = true;                  // 位移过 → 补发 click 作废
  setTimeout(() => { suppressClick = false; }, 0);  // 兜底：click 被 .stop 吞掉时标记不残留
}
function onClick() {
  if (suppressClick) { suppressClick = false; return; }  // 消费即复位
  /* 正常点击逻辑 */
}
```

**答法**：显式双信号状态机（`moved` + `suppressClick`）。追问点1 "为什么 `moved` 要在 down 里重置？"——不重置则拖过一次后永远 true，后续单击全走拖拽分支（真实 bug：单击误投喂）。追问点2 "为什么 `setTimeout(0)`？"——click 若被别的 `.stop` 吞掉，标记会残留吞掉下次合法点击，下一宏任务强制清零。

**先讲清楚基础：为什么"拖拽"之后还会来一个 click**

浏览器的事件序列：`pointerdown` → `pointermove`×N → `pointerup` →（若判定为"点击"）`click`。规范里 click 的触发条件是"先按下、后在**该元素上**抬起"——**不要求"全程没移动"**。所以拖完一次，浏览器仍会追发 click；不识别的话，"拖拽的尾巴"会被当成"点击"再触发一次业务逻辑（本项目真实 bug：拖完便签被误投喂）。

区分两种意图的办法：**看有没有发生位移**——没位移 = 点击；有位移 = 拖拽（后续 click 作废）。这是所有手势库的共同地基。

**本项目的双信号设计（为什么不是一个变量）**：
- `moved`：记录"这次按下是否拖动过"（事实）；`suppressClick`：记录"下一个 click 是否要作废"（指令）——pointerup 和 click 之间有浏览器内部处理，必须"提前设标记、click 时消费"；
- 细节 1：`moved` 必须在**按下的瞬间重置**——否则拖过一次后永远是 true，之后所有单击都被吞（真实踩坑）；
- 细节 2：`setTimeout(0)` 兜底清标记——若 click 被其他 `.stop` 吞掉（别处组件的写法），标记会残留、误杀下一次合法点击；下一宏任务强制清零；
- `{ once: true }`：监听器触发一次后自动移除，等价于手动 `removeEventListener`。

**延伸追问（同一知识面）**
- 为什么用 `pointer` 系列事件？——一套事件统一鼠标/触摸/手写笔，不用写 `touchstart + mousedown` 两套；
- `setPointerCapture` 是什么？——把后续 pointer 事件"锁定"到元素，拖出元素边界/窗口也不丢（拖拽的标准做法）；
- 为什么不用"位移 ≥ 3px 才算拖"的阈值？——更精细（防手抖误判），手势库普遍采用；二值判定是最低成本版本，讲得清演进即加分。

## Q4. 瀑布流怎么实现的？为什么不 CSS columns？

**代码**（`src/views/IdeaLibraryView.vue` 真实节选，短列优先 12 行）：

```ts
const relayout = () => {
  const cards = Array.from(box.querySelectorAll<HTMLElement>('.wf-item'));
  const cols = Math.max(1, Math.floor((w + gap) / (minCol + gap)));   // 列数由容器宽算
  const colY = new Array<number>(cols).fill(0);                       // 每列当前高度
  cards.forEach((el) => {
    el.style.width = `${colW}px`;                                     // 先定宽再量高
    let col = 0;
    for (let j = 1; j < cols; j++) if (colY[j]! < colY[col]!) col = j; // 找最矮列
    el.style.left = `${col * (colW + gap)}px`;
    el.style.top  = `${colY[col]}px`;
    colY[col] = colY[col]! + el.offsetHeight + gap;
  });
  box.style.height = `${Math.max(...colY) - gap}px`;
};
const scheduleRelayout = () => { cancelAnimationFrame(wfRaf); wfRaf = requestAnimationFrame(relayout); }; // rAF 节流
```

**答法**：CSS columns 的问题是**列填充顺序浏览器说了算**（DOM 序 ≠ 视觉序）+ 高度变化整列重排跳卡。手写短列优先让位置可计算可预测；补充三件配套——`transform` 留给 hover 不与定位打架、`ResizeObserver + rAF` 应对字体图片加载后的高度变化、`IntersectionObserver` 哨兵触底加载下一页。

**先讲清楚基础：瀑布流难在哪、现成方案为什么不给力**

目标：不等高的卡片排成多列，**每张紧贴上一张**、像水流一样填满。难在"列"不是文档流的天性——普通布局都按"行"组织：

- **CSS `columns`**：内容按顺序**竖着一列列排**（阅读顺序是"竖着读"），且默认做"列高平衡"——图片/字体加载、高度一变就重新平衡，卡片会"跳"；"第几列"也由浏览器决定，业务上不可控；
- **`flex-wrap` / Grid**：都按行排——同一行的卡片会被拉齐高度，"等高缝隙"出不来；
- **Grid 的 masonry**：仍在标准化路上（只有实验性开关），生产不能依赖。

所以**手写**（本项目）：每张卡 `position: absolute`，用 JS 算出"第几列、什么坐标"——位置完全由代码控制。

**算法：矮列优先（贪心）**：维护"每列当前高度"数组；每来一张卡，放到**当前最矮的列**，更新该列高度。复杂度 O(卡数×列数)，几百张卡毫无压力。位置自算 → 可预测、可动画（进场、hover、点击重排都建立在已知坐标上）。

**配套的三个工程细节（源码里都有）**：
- `scheduleRelayout` 用 `requestAnimationFrame` 节流：多次触发合并为"下一帧算一次"——比时间节流更贴渲染节奏（每帧 60Hz≈16.7ms 一次）；
- 图片/字体加载会改变卡片高度 → 用 `ResizeObserver` 监听后触发重排；
- 触底加载下一页 → `IntersectionObserver` 用"哨兵元素"进视口触发，比监听 scroll 事件轻。

**延伸追问（同一知识面）**
- 为什么**先定宽再量高**？——`offsetHeight` 依赖宽度，宽度不定量出的高度没意义（源码里 `el.style.width` 先行就是这个原因）；
- `left/top` 还是 `transform` 定位？——`left/top` 触发局部 layout（静态定位用它）；`transform` 只走合成（留给 hover 动画）——两者别在同一元素上打架；
- 贪心是最优排布吗？——不是（装箱问题的近似解），但顺序稳定、可预期，工程上够用。

## Q5. 一个"元素看不见/被盖住"的 bug 怎么排查？

**定位链**（项目真实案例，三个页面同根因）：

```css
/* 根因：根容器 position:static → 不构成层叠上下文 → 子层 absolute 逃逸、z-index 全局化比较 */
.idea-page { position: relative; }   /* 一行修复，源码里留了给后来者的警告注释 */

/* 嫌疑人二号：全局规则命中 */
input, textarea, select { backdrop-filter: blur(10px); }   /* 聚焦把下层糊成白雾 */

/* 取证手段：CDP dump 计算样式，不靠猜 */
await client.send('Runtime.evaluate', {
  expression: `getComputedStyle(document.querySelector('.el-select__input')).backdropFilter`
});  // → "blur(10px)" 直接指认
```

**答法**：分两步——① 原理定位：`z-index` 只在同一层叠上下文内比较，先查根容器有没有 `position: relative`；② 工具取证：CDP 打开实测 `getComputedStyle`，把"我觉得"变成"我测到"。三个项目案例（404 页/点子库/小说编辑页）都是同一根因。

**先讲清楚基础：z-index 不是"谁大谁说话"**

元素叠放有条隐藏规则：**z-index 只在同一个"层叠上下文"里比较**。层叠上下文可以理解成一个"组"——元素一旦进了某个组，它的 z-index 再大也压不过别的组里的元素（组内排序、组间由"组本身"的层级决定）。哪些东西会"开组"？比想象的多：`position: relative + z-index`（非 auto）、`opacity < 1`、`transform`、`filter`、`backdrop-filter`、`will-change`、`position: fixed/sticky` 等——"我设了 z-index: 9999 还是不显示"多数就是掉进了别的组。

**本项目两个真实案例（两种典型翻车）**：
- **案例一：absolute 逃逸**——页面根容器是 `position: static`（不开组）→ 子层绝对定位跑到更外层、z-index 与全页元素"裸比"→ 被别的层盖住。修复就一行 `position: relative`，把子层的定位与层叠收回自己范围（源码里留了给后来者的警告注释）；
- **案例二：全局样式糊白雾**——一条全局 `input { backdrop-filter: blur(10px) }` 让输入框聚焦时把下层内容糊成白雾。`backdrop-filter` 要对"背后的内容"采样做滤镜，本身也会开新组——所以既是视觉问题也是层叠问题；根治是弹窗内输入控件关闭 backdrop-filter（改实底背景）。

**排查方法（把"我觉得"变成"我测到"）**：用 CDP 跑 `getComputedStyle(el)` 读出**实际生效**的样式——不是源码里写了什么，而是浏览器最终算了什么（谁覆盖谁一目了然）；再沿父链找"是谁开的组"。这套取证流程可以写成断言脚本固化进回归，比肉眼 grep 快一个量级。

**延伸追问（同一知识面）**
- `visibility: hidden` / `opacity: 0` / `display: none` 的区别？——占位但不可见（可被读屏）/ 占位不可见不可读 / 不占位（布局与可访问性影响各不同）；
- 怎么临时"逃出"某个组？——把元素挪到组外（改 DOM 层级）或去掉祖先的开组属性——但要评估连带影响；
- 为什么会被 `transform` 坑到？——父级加了位移动画（transform）就开了新组，子级弹窗的 z-index 从此被"锁"在父级组内——"弹窗被父容器盖住"的常见根因。

## Q6. 表单回车提交怎么做的？

**代码**（`src/utils/enterSubmit.ts` 真实节选）：

```ts
export function enterSubmit(fn: () => unknown, e?: Event) {
  const run = (ev: Event) => {
    const el = ev.target as HTMLElement;
    if (el.tagName === 'TEXTAREA' || el.tagName === 'SELECT') return;         // 不接管
    if (el.closest('button, a, .el-select, [role="button"], [role="combobox"]')) return;
    const root = el.closest('form, .el-form, .creating-card, ...');          // 容器清单见真实源码（5 种）
    if (root) {
      const fields = collectFields(root);                                    // 数可见可聚焦控件
      const current = fields.find((f) => f === el || f.contains(el) || el.contains(f)) ?? el; // 焦点归一：input 可能藏在组件内部
      const idx = fields.indexOf(current);
      if (idx > -1 && idx < fields.length - 1) {                             // 非末框 → 跳焦点+全选
        ev.preventDefault?.();
        fields[idx + 1]?.focus();
        (fields[idx + 1] as HTMLInputElement).select?.();
        return;
      }
    }
    return fn();                                                             // 末框才提交
  };
  if (e) return run(e);   // 传 $event：立即执行
  return run;             // 不传：返回处理器——这就是模板必须传 $event 的原因
}
```

**答法**：约定 + 一个坑——全局统一"非末框跳焦点、末框提交"；**模板必须传 `$event`**，否则返回包装函数，拿不到事件直接走提交（项目真实 bug）。边界：textarea 回车换行不提交、删除确认禁止回车（`autofocus:false` 防误删）。

**先讲清楚基础：浏览器对"回车"本来就有约定**

HTML 规范里表单回车**有默认语义**：表单只有一个文本框时，回车直接触发提交；多个文本框时**不提交**（除非存在 type=submit 的按钮——隐藏的也算，浏览器会"代点"它）。所以"回车没反应"往往不是"没写监听"，而是默认规则没被满足。

**本项目要的更聪明（所以自己接管）**：非最后一个输入框回车 = **跳到下一个框**（并全选，方便直接重输）；最后一个输入框回车 = **提交**。"哪个算最后"是业务规则、浏览器不知道——于是 `enterSubmit` 把流程重写：每次回车判断"当前焦点框是不是最后一个"，不是就阻止默认 + `focus()` 下一个；是就调用提交函数。

**模板必须传 `$event` 的坑（项目真实 bug）**：Vue 模板里 `@keyup.enter="enterSubmit(fn)"` 的编译语义是"每次按键调用 `enterSubmit(fn)`，返回值直接丢弃"——而返回值恰是"处理器函数"，被丢 = 什么都不发生；必须写 `enterSubmit(fn, $event)` 才会立即执行、处理这次按键。记住结论：**Vue 事件表达式里，函数调用的返回值不会自动当作处理器**。

**边界（源码都标了）**：textarea 回车是换行（不接管）；删除确认弹窗**禁止回车**（`autofocus: false`，防误删）；select/按钮上下文不接管。

**延伸追问（同一知识面）**
- `keyup` 还是 `keydown`？——`keydown` 在字符进框前触发、`keyup` 在之后（能拿到已更新的值）——判断"该不该提交"用 keyup 更稳；
- 中文输入法怎么处理？——候选词上屏也按回车，严格实现要判断 `event.isComposing`（合成中不处理）——能提到这层是中文场景加分项；
- `keypress` 呢？——已废弃（无法表达功能键），别用；`keydown`/`keyup` 配 `event.key`（语义键）与 `event.code`（物理位置键，布局无关）是标准姿势。

📎 延伸阅读：[Practical/06 交互体验](../Practical/06-交互体验与表单.md)

## Q7. Pinia 怎么组织"跨路由全局 + 一堆子组件"的状态？

**代码**（`src/stores/stickyStore.ts` 设计要点，真实）：

```ts
export const useStickyStore = defineStore('sticky', () => {
  const notes = ref<StickyNoteItem[]>([]);
  const loaded = ref(false);
  const dragging = ref(false);                       // 替代旧的 120ms 轮询（单一直观状态源）
  async function fetch() {
    if (loaded.value) return;                        // 幂等：一次拉全量，之后内存读
    try { notes.value = (await listNotes()).data ?? []; loaded.value = true; }
    catch { /* 拉取失败按空渲染，不阻塞页面 */ }
  }
  function visibleOn(routePath: string) {            // 派生数据用 computed/函数，不落库
    return notes.value.filter((n) => !n.pinnedRoute || n.pinnedRoute === routePath);
  }
  return { notes, dragging, visibleOn, fetch, create, patch, remove, reset };
});
```

**答法**：**一次拉全量 + 内存派生**（便签量小，换简单）；`loaded` 守卫保证幂等；派生状态（按路由可见/池内）不存 store 字段而是 computed——**存的只有事实，视图状态靠推导**。追问"量大了怎么办？"——改分页 + 按需失效，不硬撑全量模式。

**先讲清楚基础：Pinia 解决什么问题**

组件之间传数据的常规办法是 props 一层层传——"跨页面、多处都要用"的数据（比如便签列表）这么传会变成"接力搬运"。**状态管理库**把这类全局数据和方法集中成一个"仓库"（store），任何组件直接引入使用——Pinia 就是 Vue3 官方的那个（`defineStore` 创建一个仓库）。

它为什么"改一处、多处更新"？——仓库建立在 Vue 响应式之上：组件读到 store 数据时被记下依赖，数据一变，用过它的组件自动重渲染——和普通 ref 同一套机制，没有"第二套魔法"。

**本项目的三个设计决策（重点讲"为什么"）**：
1. **一次拉全量 + 内存过滤**：便签是个人数据、量小——全量拉取比"分页 + 缓存失效"简单一个量级。**按数据规模选方案**，不是越"高级"越好；
2. **`loaded` 守卫**：多个组件同时挂载都可能触发 `fetch`，守卫保证只请求一次——"初始化加载"的标配写法；
3. **派生数据不落库**：`visibleOn(routePath)` 用"事实 + 路由"现算，不存成字段——**少存一份副本，就少一份"会过期、要同步"的隐患**（和前后端口径问题同一哲学）。

**延伸追问（同一知识面）**
- 和 Vuex 的区别？——Vuex 改状态要走 mutation（样板多）；Pinia 直接改、组合式写法 + TS 推导更顺，是 Vue3 官方推荐；
- 数据量大了怎么办？——分页 + "先展示旧数据、后台刷新"（stale-while-revalidate）+ 按 key 失效——这正是 TanStack Query / SWR 这类数据请求库解决的，本项目是手写子集；
- store 怎么拆分？——按领域（sticky/novel/user）拆，跨 store 用 computed 引用数据而非互相调方法（减少耦合与环）。

## Q8. 前后端字段口径不一致怎么防？

**代码**（`src/api/` 两个文件的真实差异）：

```ts
// ideaApi.ts：分页对象口径
http.get<{ records: { id: number; title: string }[] }>('/novel/listall', { params: { page: 1, pageSize: 50 } });
// 正确解法：unwrap<{ records: T[] }>(res)?.records ?? []

// characterApi.ts：直接数组口径
http.get<Character[]>(`/novelCharacter/all/${novelId}`);
```

**答法**：混用两种响应形状的代价是**恒空且难察觉**（`null ?? []`），用户只看到"下拉永远空白"。防御三层：接口层显式标注返回形状、unwrap 统一判 `code===200` 不符则 toast 提示并返 null（不炸页面）、联调用接口对照表全量核对。**主动讲治理债**：项目 `unwrap` 在 6 个组件里各自复制定义——正确做法是提炼公共工具函数，这正是"口径不一致"在代码组织上的病根。

**先讲清楚基础：什么叫"口径"**

同一份数据，前端"以为的形状"和后端"实际的形状"不一致——比如"列表"：有的接口直接返回数组 `[...]`，有的返回分页对象 `{ records: [...], total }`。按错的形状取数就拿到 `undefined`；而代码里常有 `?? []` 兜底——**于是错误被"优雅"地变成空数组：不报错、不崩溃，只表现为"下拉框永远空白"**。这类 bug 最阴险之处就是"静默"。

**为什么会有两套口径**：项目两代后端并存——Java 侧（MyBatis 系）分页天然是 `{records,total}`；FastAPI 侧是 REST 风格直出数组。历史演化产物，不是谁写错。

**防御三层（从浅到深）**：
1. **接口层把期望"画出来"**：`http.get<{records: T[]}>(...)` 写清形状——但注意：**TS 类型只是"编译期声明"，运行时不会校验**——写错了不会报错，只是"骗了自己"，所以这层是"文档"不是"防线"；
2. **统一拆壳（unwrap）**：判 `code===200` 取 `data`，不符则提示并返 `null`——用**一处实现**统一拆掉"响应信封"；
3. **联调用对照表**：接口 ↔ 返回形状 ↔ 使用点全量核对（把"我记得"换成"清单上写着"）。

**要主动讲的项目债**：`unwrap` 在 6 个组件里各自复制了一份定义——正解是提成一个公共工具函数（一处改、处处改）。"指出自己的债 + 给出还法"是加分项。

**延伸追问（同一知识面）**
- 怎么从根上消灭手抄？——**契约先行**：OpenAPI/JSON Schema 当单一事实源，前端类型由机器生成（codegen）；改接口先改契约、CI 里跑一致性检查；
- 类型不可信，运行时校验怎么做？—— zod / valibot 在"接口层"解析并校验，格式不符就抛错（把静默错误变成显式错误）；
- 为什么 `null ?? []` 会掩盖问题？——它把"形状不对"和"本来就是空"合并成同一种表现，排错方向被藏掉了。

## Q9. 断网/弱网下怎么不丢用户数据？

**方案**（项目：章节编辑器 Local First，文档真实记录）：

```ts
// 策略：内容先落 IndexedDB（真实封装 src/utils/draftDB.ts），云端同步是异步旁路
async function saveDraft(chapterId: number, content: string) {
  const old = await getDraft(chapterId);
  await putDraft({ ...old!, chapterId, content,
                   updatedAt: Date.now(), isDirty: true });   // ① 本地必成功（IDB 不可用自动降级内存 Map）
  saveToServer(chapterId, content)                            // ② 云端异步补传，不阻塞输入
    .then(() => clearDirtyByChapter(chapterId));              // ③ 成功清 dirty；失败保持 isDirty 待重试
}
```

**答法**：编辑器底线是"不丢一个字"——**同步是旁路不是主路**；IndexedDB 比 localStorage 强在容量与结构化（可存版本/时间戳做冲突判断）；断网恢复后队列补传。追问冲突——本地覆盖 + 版本号兜底。

**先讲清楚基础："不丢数据"为什么先写本地**

网络可靠性不由你控制（断网、超时、服务端打嗝）。若每次输入都"直连服务端成功才算保存"，第一个网络波动就丢内容。**Local First 的思路**：把"本地写入"当**必达路径**（浏览器本地几乎不会写失败），"云端同步"当**异步旁路**（失败可重试、可补偿）——断网可继续编辑不是"加了个功能"，而是**结构上的保证**。

**为什么选 IndexedDB 而不是 localStorage**：localStorage 是同步 API（读写卡主线程）、约 5MB、只能存字符串；IndexedDB 异步、容量按磁盘配额（可达 GB 级）、能直接存对象、支持事务与索引——"章节大文本 + 按 id 更新"只有后者撑得住。

**同步机制怎么保证不丢、不重**：
- **dirty 标记**：本地写时标"未同步"，服务端确认后才清除——等价于一张"待办清单"，断网恢复/下次打开按清单补传；
- **幂等**：补传可能重复发送（比如"服务端已成功、响应丢了"），同步接口要保证"同一内容传两次结果一致"。

**冲突怎么处理（断网期间两端都改过）**：最常见的简化是"**本地覆盖 + 版本号兜底**"（本项目）：同步时比较版本信息，本地陈旧就不让覆盖新内容。更严格有版本向量、CRDT（自动合并）——知道名词和适用场景即可。

**延伸追问（同一知识面）**
- IDB 打不开怎么办？——代码做了**降级**：拿不到 IndexedDB 就退回内存 Map（刷新会丢、但不崩）——"可退化的设计"思路值得讲；
- localStorage / sessionStorage / Cookie 怎么选？——按生命周期与用途：长期配置 / 会话内 / 请求自动携带（小容量）；
- 这套模式的通用名字？——离线优先（Offline-First）；服务端对应思想是"先写日志、再异步处理"（WAL / outbox）。
