## Q1. 事件循环：说出输出顺序

```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3')).then(() => console.log('4'));
async function f() { console.log('5'); await 6; console.log('7'); }
f();
console.log('6');
// 输出：1 5 6 3 7 4 2
```

**先讲清楚基础：事件循环是什么**

JavaScript 是单线程语言——同一时刻只有一条代码在跑。那网页为什么还能同时处理点击、请求、定时器，不会卡死？靠的是一套调度规则：**事件循环**。把所有待执行的东西想象成几个筐：

1. **调用栈**：正在执行的代码，一条一条同步往下跑；
2. **宏任务队列**：`setTimeout`/`setInterval` 的回调、IO 完成、UI 事件等排在这里——事件循环**每轮只取一个**宏任务执行；
3. **微任务队列**：`Promise.then` 的回调、`await` 恢复执行的代码、`queueMicrotask` 排在这里——**当前宏任务执行完，必须把微任务队列全部清空（包括执行过程中新加进来的），才轮到下一个宏任务**。

于是整个调度规则可以浓缩成一句话：

> 同步代码跑完 → 清空微任务 → （浏览器可能趁机渲染）→ 取下一个宏任务 → 清空微任务 → …

"Promise 回调比 setTimeout 快"不是玄学：只是它排在微任务队列、`setTimeout` 排在宏任务队列，**调度位置不同**。

**本题一步步分析**

1. 同步开始，打印 `1`；
2. `setTimeout(..., 0)`——回调（打印 2）进宏任务队列；
3. `then(打印3).then(打印4)`——打印 3 立即进微任务队列；注意**打印 4 此刻还没入队**，它要等打印 3 执行完、`.then` 生成新 Promise 时才入队；
4. `f()` 调用：先打印 `5`；`await 6`——6 不是 Promise，只把"恢复执行（打印 7）"排进微任务队列，然后让出；
5. 同步代码继续，打印 `6`。至此调用栈清空；
6. **清空微任务**：打印 `3`（它执行时把打印 4 追加进队列尾部）→ 打印 `7` → 打印 `4`；
7. 下一个宏任务：打印 `2`。

输出：**1 5 6 3 7 4 2**。最容易错的是 4 和 7 的顺序——4 要等 3 执行完才入队，所以排在早就入队的 7 后面。

**面试怎么答**：先报输出顺序 → 给依据"同步 → 微任务（边执行边追加）→ 宏任务" → 主动点破易错点（`await` 恢复是微任务、`.then` 链逐个注册），显示是真理解而不是背答案。

**延伸追问（同一知识面）**
- `setTimeout(0)` 是立即执行吗？——不，只保证"不早于"；实际最小延迟约 1ms，嵌套超 5 层后强制 4ms。
- 微任务里又产生微任务？——继续全部清空（所以死循环的微任务会卡死页面，永远轮不到渲染）。
- 渲染什么时候发生？——每轮微任务清空后、下一个宏任务前，浏览器**可能**渲染（每轮最多一次）；`requestAnimationFrame` 是渲染前的回调，做动画对齐帧节奏用它。
- Node.js 一样吗？——大体一致，但多了 `process.nextTick`（比 Promise 更优先）和 `setImmediate`。
- 项目挂钩：瀑布流 `relayout` 的 rAF 节流、SSE 流式逐字渲染，本质都是"把更新对齐到调度节奏"。

## Q2. 手写防抖与节流

```js
// 防抖：停手 N ms 才执行（搜索联想、resize）
function debounce(fn, ms) {
  let t;
  return function (...args) {
    clearTimeout(t);
    t = setTimeout(() => fn.apply(this, args), ms);
  };
}

// 节流：每 N ms 至多一次（滚动、拖拽、埋点）
function throttle(fn, ms) {
  let last = 0, t;
  return function (...args) {
    const now = Date.now(), remain = ms - (now - last);
    if (remain <= 0) { last = now; fn.apply(this, args); }
    else { clearTimeout(t); t = setTimeout(() => { last = Date.now(); fn.apply(this, args); }, remain); }
  };
}
```

**先讲清楚基础：它们解决什么问题**

浏览器里有一类"高频事件"：input 每敲一下、scroll 每滚一像素都会触发——一次操作下来几十上百次。如果每次都跑重活（发请求、算布局），页面必卡。防抖和节流是两种"控制执行频率"的策略：

- **防抖（debounce）**："等你说完我再办"——事件一直来就一直不执行，**停手 N 毫秒后才执行一次**。适合只要最终结果的场景：搜索联想（输入稳定后才发请求）。
- **节流（throttle）**："不是不办，是慢慢办"——不管来得多快，**每 N 毫秒最多执行一次**。适合过程中要持续反馈的场景：滚动位置、拖拽跟随。

**代码逐行拆解**

防抖：用一个闭包变量 `t` 存定时器 id。事件每次来：先 `clearTimeout(t)` 干掉上一次的预约，再重新预约——"等待期重启"，所以只有最后一次能活到点火。`fn.apply(this, args)` 把调用现场的 `this` 和参数原样透传给真正的函数。

节流（时间戳 + 定时器混合版）：`last` 记上次执行时刻；事件来时算 `remain`（离冷却期结束还差多久）——已过冷却期立即执行并刷新 `last`；没过则用定时器在冷却期结束时补一次（**保证最后一次必达**）。纯时间戳版会丢掉最后一次（滚到底停手前的那一段不再触发），混合版补上了这一点。

**面试就这三板斧**：区别（只认最后一次 vs 固定频率）、场景（搜索防抖 / 滚动节流）、手写（写得出、每行讲得清）。

**延伸追问（同一知识面）**
- 为什么 `apply(this, args)` 不能省？——事件回调里的 `this` 和事件参数；透传才能"原样重演"。
- **立即执行版（leading）**：第一次立即执行、之后冷却——按钮防重复提交用的就是它。
- lodash 的 debounce 完整形态：`leading`（首次立即）+ `trailing`（尾部补一次）+ `maxWait`（被连续触发太久时强制落一次，防止永远等不到停手）+ `cancel/flush`（手动取消/立即执行）。
- **rAF 节流**：更轻的节流——每帧最多一次，自动对齐屏幕刷新节奏（60fps≈16.7ms 一帧），不用选时间参数；项目瀑布流 `relayout` 就是这么做的。
- 与前面知识连起来：防抖/节流靠**闭包**记住定时器；`setTimeout` 的返回值用于取消（搭配 Q1 事件循环理解）。

## Q3. 手写 Promise.all / 竞态取消

```js
function all(promises) {
  return new Promise((resolve, reject) => {
    const arr = [...promises], out = new Array(arr.length);
    let cnt = 0;
    if (!arr.length) return resolve([]);
    arr.forEach((p, i) => {
      Promise.resolve(p).then((v) => {
        out[i] = v;                 // ① 按下标保序
        if (++cnt === arr.length) resolve(out);
      }, reject);                   // ② 任一失败即整体失败
    });
  });
}
```

**追问：搜索框快速输入，怎么防止旧响应覆盖新响应？**（真实高频）

```js
let seq = 0;
async function search(q) {
  const my = ++seq;
  const res = await fetchResults(q);
  if (my !== seq) return;           // 过期响应直接丢弃
  render(res);
}
// 或 AbortController：新请求 abort 旧请求，省服务端资源
```

**先讲清楚基础：`Promise.all` 是干什么的**

它解决一个常见需求：**等多个异步任务全部完成，再一起处理**。比如进页面要同时拉"用户信息 + 订单列表 + 未读消息"，三个都回来了才算加载完成。用法：`const [a, b, c] = await Promise.all([p1, p2, p3])`。

先复习 Promise 本身：它是异步结果的"占位符"，状态有三种——pending（未完成）、fulfilled（成功）、rejected（失败），**一旦改变就不可逆**；`.then` 注册"完成之后做什么"，且返回新 Promise（所以能链式）。

**手写逐行拆解**：

- 用 `new Promise(...)` 包壳，手里有 `resolve/reject` 两个开关；
- `out[i] = v`：**按下标存**而不是 push——因为"完成顺序"不等于"传入顺序"（第一个传进去的可能最慢），按下标才能保证输出和输入顺序一致；
- `cnt` 计数器达到 `arr.length` 才 resolve：全部完成才交付；
- 空数组直接 `resolve([])`：边界处理——否则计数器永远到不了 length，Promise 永远悬挂；
- `Promise.resolve(p)`：把"可能不是 Promise 的值"统一包成 Promise（all 允许混入普通值）；
- `then(..., reject)`：任何一个失败，整体立刻失败——**"快速失败"**语义（其余任务还在跑，但结果没人接收了）。

**顺带讲清楚"接口竞态"**：搜索框里快速输入 "ab"，先发了 "a" 的请求、又发了 "ab" 的请求——如果 "a" 的响应慢、后回来，就会把 "ab" 的结果**覆盖**成旧内容。竞态 = 结果的先后由网络快慢决定，不由代码顺序决定。两种解法：

- **序号守卫**（上面第二段代码）：每次请求领一个递增号 `my = ++seq`；响应回来先对号，不是最新号就直接丢弃。零成本，缺点是请求都白发（费带宽）；
- **AbortController**：`const c = new AbortController(); fetch(url, { signal: c.signal })`——需要取消时调 `c.abort()`，请求直接终止（抛 AbortError）。省服务端资源，但只对支持 signal 的 API 有效。

**面试怎么答**：用法和语义（全成才成、一败即败）→ 手写要点（下标保序 + 计数 + 空数组 + 快速失败）→ 竞态题给出两个标准答案并讲取舍。

**延伸追问（同一知识面）**
- Promise 四兄弟：`all`（全成才成）、`allSettled`（全部结束，拿每项状态，不快速失败）、`race`（第一个有结果就定，无论成败——常用做超时控制）、`any`（第一个成功）；
- "一败即败"后其余任务会怎样？——照常跑完，只是结果没人接收（不是被取消）；
- 超时控制怎么写？——`Promise.race([fetch(), 超时Promise])` 的组合技；
- 异步演进脉络：回调 → Promise（治回调地狱）→ async/await（Promise 的语法糖）——一句话带出即加分。

## Q4. 闭包 + 手写 call/apply/instanceof

```js
// 闭包经典坑：循环里拿异步回调（var 作用域共享）
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 3 3 3
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 0 1 2（每轮新绑定）

// 手写 call
Function.prototype.myCall = function (ctx, ...args) {
  ctx = ctx ?? globalThis;
  const key = Symbol();               // 临时属性避免覆盖
  ctx[key] = this;
  try { return ctx[key](...args); } finally { delete ctx[key]; }
};

// 手写 instanceof（沿 __proto__ 链找 prototype）
function myInstanceof(obj, Ctor) {
  let proto = Object.getPrototypeOf(obj);
  while (proto) { if (proto === Ctor.prototype) return true; proto = Object.getPrototypeOf(proto); }
  return false;
}
```

**先讲清楚基础：闭包是什么**

先记一个事实：**函数可以定义在另一个函数里面，还可以作为返回值传出去**。闭包一句话——"**内层函数记住了它定义时所在的外层环境；即使外层函数执行完了，这些外层变量依然活着、能被内层函数访问**"。

第一段代码就是最经典的演示：`setTimeout(() => console.log(i))` 里的箭头函数就是内层函数，它用到了外层变量 `i`。

- `var i`：整个循环**只有一个** `i`（var 的作用域是函数级、不是块级）；循环瞬间结束、`i` 停在 3；等定时器真正执行时（至少几毫秒后），读到的都是同一个 `i` → **3 3 3**；
- `let i`：**每一轮循环创建一个新的 `i`**，每个箭头函数记住各自那轮的那个；定时器执行时各读各的 → **0 1 2**。

（"闭包坑"和"用 let 修"讲的是同一件事的两面：内层函数抓的是"**变量本身**"，不是"当时的值"。）

**手写 call 的思路（"借位"）**

`call/apply/bind` 是所有函数自带的方法，作用是**指定 this 来调用**。要手写，先抓住 this 的一条规则：**`obj.fn()` 调用时，this 就是 obj**。手写 call 就是"曲线救国"利用这条规则：

- 把函数临时挂到目标对象上（`ctx[key] = this`）；
- 用 `ctx[key](...args)` 调用——调用形态是"点号调用"，this 自然就是 ctx；
- 调用完 `delete` 掉临时属性，别污染对方；
- 用 `Symbol()` 当键名有两个理由：**不会和对象已有属性重名**（防覆盖）、**Symbol 键不出现在 for...in / JSON.stringify 里**（防枚举污染）。

**instanceof 是什么**：判断"这个对象是不是这个构造函数的实例"——底层做法是**沿对象的原型链一层层往上找**，看能不能遇到 `Ctor.prototype`。手写版三行：取 `obj` 的上级原型（`Object.getPrototypeOf`）→ 和 `Ctor.prototype` 比对 → 没中就把"上级"再当对象取它的上级，直到 null（没找到 → false）。

**面试怎么答**：闭包先给一句话定义 + var/let 对照输出；call 手写讲"临时属性借位 + Symbol 两个理由"；instanceof 讲"沿链找 prototype"。

**延伸追问（同一知识面）**
- 闭包的内存问题：被闭包引用的变量不会被回收——事件回调/定时器误捕大对象是常见泄漏源，组件卸载要记得解绑；
- `IIFE`（立即执行函数）是老代码的"造作用域"手法：块级作用域普及前用它隔离变量；
- `apply` 与 `call` 的区别：apply 第二个参数传数组（`fn.apply(ctx, [a,b])`），call 挨个传（`fn.call(ctx, a, b)`）；bind 不执行、返回预置好 this 的新函数（Q11 有手写）；
- `instanceof` 的边界：跨 iframe/window 时两边 `Object.prototype` 不是同一个，判断会失效。

## Q5. Vue3 响应式原理：手写 mini reactive

```js
const targetMap = new WeakMap();   // target -> { key -> deps(Set) }
let activeEffect;
function track(target, key) {
  if (!activeEffect) return;
  let deps = targetMap.get(target) ?? new Map();
  targetMap.set(target, deps);
  (deps.get(key) ?? new Set()).add(activeEffect);   // get 收集依赖
}
function trigger(target, key) {
  targetMap.get(target)?.get(key)?.forEach((fn) => fn());  // set 触发更新
}
function reactive(obj) {
  return new Proxy(obj, {
    get(t, k, r) { const v = Reflect.get(t, k, r); track(t, k); return v; },
    set(t, k, v, r) { const ok = Reflect.set(t, k, v, r); trigger(t, k); return ok; },
  });
}
```

**先讲清楚基础：响应式是什么**

Vue 的核心魔法是——**改了数据，页面自己就更新**。这不是自动发生的，是 Vue 做了两件事：

1. **收集依赖（track）**：在"**读取**"数据时，记住"谁在读它"（比如渲染函数）；
2. **触发更新（trigger）**：在"**修改**"数据时，通知所有读过它的人重新执行。

上面这段代码就是响应式的最小实现（真实源码同款思路）：

- `activeEffect`：记录"当前正在执行的函数"（比如渲染函数）；
- `track(target, key)`：把当前函数记进 `targetMap`——结构是**"对象 → 属性名 → 用过这个属性的函数集合"**三层嵌套；
- `trigger(target, key)`：把用过该属性的函数挨个重新跑；
- `reactive(obj)` 用 `Proxy` 包住对象：`get` 时顺手 track、`set` 时顺手 trigger——**"顺手"是关键**：不提前遍历，等别人访问时再登记。

**为什么用 Proxy，不用 Vue2 的 defineProperty**（面试真正的考点）：

| 场景 | Vue2 `defineProperty` | Vue3 `Proxy` |
|------|----------------------|--------------|
| 新增/删除属性 | ❌ 感知不到（靠 `$set/$delete` 打补丁） | ✅ 能拦截 |
| 数组下标/长度变化 | ❌（重写了 7 个数组方法打补丁） | ✅ 能拦截 |
| 初始化 | 递归遍历所有属性（大对象慢） | 不用预遍历（访问到才代理，"懒"） |

`WeakMap` 的作用：`targetMap` 的键是被代理的对象——用普通 Map 存的话，**就算对象在页面里已经没人用了，Map 还强引用着它，内存永远回收不掉**；WeakMap 弱引用，对象被回收、依赖表自动消失。

**面试怎么答**：一句话"track 收集、trigger 触发，Proxy 在 get/set 里顺手干这两件事"→ 手写讲清三层结构 → 对比题答出 Vue2 的三个痛点。追问 `Object.freeze`：冻结对象的 set 会失败，trigger 无从谈起——响应式对它是死的。

**延伸追问（同一知识面）**
- 为什么改完数据立刻读 DOM 读不到、要 `await nextTick()`？——trigger 不马上跑渲染，而是把更新推进微任务队列**批量、去重**执行（连改 3 次只渲染 1 次）；nextTick 回调排在这个队列后面；
- `ref` 和 `reactive`：`ref` 把原始值（数字/字符串）**装箱**成带 `.value` 的容器再做依赖收集（所以用的时候要 `.value`），`reactive` 只能代理对象；`shallowRef/shallowReactive` 不做深层代理（大列表性能优化）；
- 依赖收集的粒度为什么是"函数"——精确记到"哪个函数用了哪个属性"，更新时只重跑用到的部分。

## Q6. 虚拟 DOM / diff 的要点 + `key` 的作用

**先讲清楚基础：虚拟 DOM 是什么、为什么需要它**

直接操作真实 DOM 的麻烦：改数据时要自己想清楚"哪些节点该改、怎么改"（查元素 → 手动改属性），代码又长又易漏。Vue/React 走"**声明式**"路线：

> 你只描述"UI 现在应该长什么样"，框架负责把它同步到真实 DOM。

中间的工具就是**虚拟 DOM（vnode）**——用普通 JS 对象描述一个节点：

```js
// <div class="a">你好</div> 的虚拟节点大致长这样（简化示意）
{ tag: 'div', props: { class: 'a' }, children: '你好' }
```

数据变化时：生成**新 vnode 树** → 和旧树**对比（diff）**找出最小差异 → 只把差异应用到真实 DOM。收益：写代码简单 + 跨平台（同一份 vnode 可渲染到 Web/小程序/App）+ 更新可以批量优化。

**diff 怎么做的（考点）**：全树两两比较是指数级代价（不可能做），所以做了工程取舍——**只比同一层**（不跨层找）、同类型节点才深入比较；子节点列表用"**新旧头尾四指针**"快速命中常见情况（头对头、尾对尾等），剩下的节点用 **key 建映射表**查——`key` 从这里进入画面。

**key 是干什么的**：key 是给列表节点发的"**身份证**"。diff 时框架靠它判断"新节点和旧节点是不是同一个"——是就复用（DOM、组件内部状态如输入框内容全保留），不是就重建。

```vue
<!-- 反例：index 当 key = "按位置的身份证" -->
<div v-for="(item, i) in list" :key="i">{{ item.text }}</div>
<!-- 正例：业务 id 当 key = "永久身份证"，挪到哪都认得出 -->
<div v-for="item in list" :key="item.id">{{ item.text }}</div>
```

**为什么 index 会出事**：在列表**头部**插入/删除一项，所有元素的位置都变了——index key 集体错位，框架以为"1 号位还是原来那个 1 号"，把旧 DOM（连同输入框里已输入的内容）当新元素复用，内容全串。稳定 id 不受位置影响，头插时老元素还是老 id、原地复用。

**面试怎么答**：虚拟 DOM = "JS 对象描述 UI + diff 找最小改动"→ diff 要点"同层比较、四指针 + key 映射"→ 用"身份证"比喻把 index 错位讲透。

**延伸追问（同一知识面）**
- 虚拟 DOM 一定比手动操作 DOM 快吗？——不一定（极端场景手写更优）；它的真正价值是**可维护性 + 跨平台**，性能是"足够好"的工程折衷；
- Vue3 的编译优化：静态提升（纯静态节点只创建一次）、`patchFlag`（编译期标记"这里会变"）——让运行时跳过大部分对比；
- 组件列表为什么也要给 key？——同理，保证组件实例与数据项的对应关系（内部状态不串）。

## Q7. 跨域：CORS 与开发代理的区别

```nginx
# 开发期：vite dev server 反代（同源，无 CORS 问题）
server: { proxy: { '/api': { target: 'http://localhost:8084', changeOrigin: true } } }

# 生产期：nginx 承担同样角色
location /api/ { proxy_pass http://backend:8084/; proxy_set_header Host $host; }
```

```java
// 后端直连方案：Spring 允许来源（项目 SecurityConfig/CORS 配置同款思路）
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override public void addCorsMappings(CorsRegistry r) {
        r.addMapping("/api/**").allowedOrigins("https://your.com")
        .allowedMethods("GET,POST,PUT,DELETE").allowCredentials(true);
    }
}
```

**先讲清楚基础：同源策略是什么、为什么存在**

这是浏览器的安全基石：**页面只能访问"同源"的资源**。"同源" = **协议 + 域名 + 端口**三者完全相同。以下全是跨源：`http://a.com` vs `https://a.com`（协议不同）、`a.com` vs `b.a.com`（子域不同）、`a.com` vs `a.com:8080`（端口不同）。

为什么要有它：没有同源策略的话，你打开一个恶意网页，它就能在后台悄悄请求你登录着的银行网站（cookie 会自动带上）并**读取返回数据**——余额就被读走了。注意：它保护的核心是"**读取**"。

**跨域请求是怎么发生的、CORS 是什么**

比如页面在 `http://localhost:5173`，请求 `http://localhost:8084/api/...`——端口不同，跨源。浏览器放行的机制叫 **CORS（跨源资源共享）**：**服务器用响应头声明"我允许哪些来源访问我"**，浏览器按声明决定"是否把结果交给 JS"。

两种流程：
- **简单请求**（GET/HEAD/POST + 只用基础头 + Content-Type 是表单三种之一）：直接发出，浏览器检查响应头 `Access-Control-Allow-Origin` 是否放行；
- **预检请求**：不符合"简单"的（PUT/DELETE、自定义头、**Content-Type: application/json**）——浏览器先自动发一个 `OPTIONS` 问服务器"我打算用 PUT 带 json 访问，同意吗"，服务器回 `Access-Control-Allow-Methods/Headers` 同意后才发真请求。

**开发代理为什么能解决**：vite 的 `server.proxy`、nginx 反代——让请求先发给**同源的开发服务器/自己的域名**，由它转发给后端。同源策略**只管浏览器**，服务器之间没有任何限制——请求换了个"传话人"，浏览器全程只看到同源请求，自然没有跨域这回事。生产同理：nginx 把 `/api/` 反代到后端，前端代码一行不用改。

**面试怎么答**：同源定义（协议+域名+端口）→ 为什么有（防恶意站点偷读数据）→ CORS 是"服务器声明、浏览器执行"→ 代理是"服务端转发绕开浏览器限制"→ 项目里 vite/nginx 两次收口。

**延伸追问（同一知识面）**
- 带 cookie 的跨域：`credentials: 'include'` 时，服务器 `Access-Control-Allow-Origin` **必须回显具体来源**（不能写 `*`）且要给 `Access-Control-Allow-Credentials: true`——两个条件缺一不可；
- 预检缓存：`Access-Control-Max-Age` 让浏览器若干秒内不再重复发 OPTIONS；
- CORS 和 CSRF 的关系：CORS 是"限制读取"；CSRF 是"利用'请求会自动带 cookie'发起恶意请求"——防 CSRF 靠 token / SameSite cookie，不是 CORS；
- 线上排查"跨域报错"：先看 Network 里真请求是否发出——OPTIONS 被拒还是响应头缺失，一眼定位。

## Q8. 浏览器缓存：强缓存 vs 协商缓存

```nginx
# 实践配法（nginx）
location /static/ {
  expires 30d;                                  # 强缓存：Cache-Control: max-age=2592000
  add_header Cache-Control "public, immutable";
}
location /api/ {
  add_header Cache-Control "no-store";          # 接口不缓存
}
# 改变的入口 HTML：no-cache → 每次协商，拿到新 hash 后加载新 chunk
```

**先讲清楚基础：两种缓存的分工**

浏览器缓存解决的事：同一份资源（js/css/图片）第二次要的时候，别重新下载（省流量），或至少先问一句"变没变"（省内容重传）。两种机制：

- **强缓存**：浏览器**直接用本地副本、压根不联系服务器**——响应头 `Cache-Control: max-age=秒数` 告诉它"这个资源 N 秒内放心用"。命中时 Network 面板显示 `200 (from disk/memory cache)`；
- **协商缓存**：有效期过了（或没设强缓存），浏览器**发请求问服务器"我本地这份还能用吗"**，并带上"我这份的标识"（`If-None-Match: 上次拿到的ETag`）——服务器比对：没变 → 回 `304 Not Modified`（无 body、只有头，省流量）；变了 → 回 `200` + 新内容。

两个"标识"机制：`ETag` 是**内容指纹**（内容变则指纹变，最精确）；`Last-Modified` 是**最后修改时间**（精度只到秒、依赖服务器时钟，算降级方案）。

**实战为什么要"hash 文件名 + 长缓存"**

| 资源 | 配置 | 原因 |
|------|------|------|
| 打包产物 `app.a1b2c3.js` | `max-age=31536000` + immutable | 内容变了 hash 就变、**文件名就换了**——对浏览器来说"这是个新 URL"，不是"旧缓存过期"，压根不用协商 |
| 入口 `index.html` | `no-cache`（每次协商） | 它是"指向新 hash 资源的跳板"——必须保证拿到最新引用，否则用户永远打开旧版本 |

这套组合的闭环：发版 → 用户刷新 → HTML 协商拿到新版 → 里面引用的 js/css 全是新 hash 的 URL → 没变的老文件强缓存直接命中、变了的下载新文件。**"缓存永不脏"的秘诀 = 把缓存单位的名字和内容绑定**。

**面试怎么答**：强缓存"不问、直接读"vs 协商缓存"先问、没变用旧的"→ 头字段对照（Cache-Control/ETag）→ 实战组合拳（hash + 长缓存 + HTML 协商）讲出闭环。

**延伸追问（同一知识面）**
- `no-cache` ≠ `no-store`（最易错）：no-cache 是"可以缓存，但每次都要拿服务器验证"；no-store 是"彻底不存"（敏感数据）；**`no-cache` 不是"不缓存"**；
- 浏览器的刷新行为：地址栏回车正常走缓存链、F5 一般触发协商验证、Ctrl+F5 强制完全重新下载；
- `immutable` 的意义：普通强缓存在用户点刷新时，浏览器仍可能发协商请求；immutable 声明"有效期内连刷新都别问"；
- `Vary`：告诉缓存"同一 URL 但请求头不同（如 Accept-Encoding）要分开存"。

## Q9. `v-if` / `v-for` / `computed` / `watch` 快问快答

```vue
<!-- v-if vs v-show：切换少用 v-if（真卸载，省 DOM）；频繁切换用 v-show（display:none） -->
<!-- 同节点别混用 v-for+v-if：Vue3 中 v-if 优先级更高、拿不到迭代项直接报错；Vue2 反之（v-for 优先、每次迭代都判断）-->
<!-- 需要依赖列表过滤 → 用 computed，别在 watch 里手动赋值 -->

const full = computed(() => props.first + props.last);   // 惰性、可缓存
watch(() => props.id, async (v, old) => {                 // 副作用：请求、埋点
  loading.value = true;
  try { await load(v); } finally { loading.value = false; }
}, { immediate: true });
```

**逐条讲清楚**（这四个是 Vue 模板里最常用的家伙，面试官爱连着问）：

**v-if vs v-show 怎么选**：
- `v-if`：条件为假时**真的不渲染、DOM 不存在**——切换时创建/销毁，组件走销毁重建 + 生命周期；好处是初始渲染省（可能根本不用创建）；
- `v-show`：DOM 一直都在，只切 `display: none`——初始渲染成本高（永远要渲染一次），但切换开销极低；
- 选择标准看"**切换频率**"：很少切用 v-if（省 DOM），频繁切（比如 toggle 面板）用 v-show。

**为什么 v-if 和 v-for 别放在同一个节点上**：
- Vue2：v-for 优先级更高——v-if 在**每一轮迭代里**执行（能拿到迭代项，但每次都判断，浪费）；
- Vue3：**v-if 优先级更高**——v-if 求值时迭代项还不存在，直接报错；
- 正确姿势：过滤放到 `computed` 里（`list.filter(...)`），别在模板里混写。

**computed 和 watch 的区别（"算"和"做"）**：
- `computed`：**算出一个派生值**——声明式（"这个值等于什么"）、**带缓存**（依赖没变就直接拿缓存、不重算）；适合"模板要展示的、由其他数据推导出来的值"；
- `watch`：**执行副作用**——命令式（"当 X 变了，就去做 Y"：发请求、埋点、存本地）、能拿到新旧值；适合"数据变化后要做的动作"。

一句话记忆：**"能算出来的别 watch"**——`computed(() => a + b)` 天然和源数据同步；写成 `watch(a, () => { c = a + b })` 就多维护了一份"手动同步的副本"，迟早不同步。

**面试怎么答**：v-if/v-show 讲"切换频率 vs 渲染成本"；v-for/v-if 讲优先级差异 + computed 过滤；computed/watch 讲"派生值 vs 副作用 + 缓存机制"。

**延伸追问（同一知识面）**
- computed 的缓存怎么实现的？——依赖变化时打"脏标记"，下次**被访问**时才重算；所以 computed 里别写副作用（它可能根本不执行）；
- watch 常用选项：`immediate`（先立即执行一次）、`deep`（深度监听对象内部，代价是递归遍历）、flush（回调时机）；
- watch 里发异步请求要防竞态（旧请求晚到覆盖新值——见 Q3 的序号守卫）。

## Q10. 原型链：prototype / __proto__ / constructor 的关系

```js
function Person(name) { this.name = name; }
const p = new Person('x');

Person.prototype === p.__proto__;        // ① 实例的 __proto__ 指向构造函数的 prototype
p.constructor === Person;                // ② constructor 挂在 prototype 上，实例沿链找到它
Object.getPrototypeOf(p) === p.__proto__; // ③ 标准读法（__proto__ 是非标 getter，浏览器都实现了）

// 查找机制：调用 p.toString() 时——
// p 自身没有 → 沿 __proto__ 找到 Person.prototype → 再往上 Object.prototype → 都没有则 undefined
// （访问中断返回 undefined；若中间某层是 null 则抛 TypeError，链的终点是 null）
console.log(Object.getPrototypeOf(Object.prototype));   // null ← 链的尽头
```

**手写 `new`**（必考）：

```js
function myNew(Ctor, ...args) {
  const obj = Object.create(Ctor.prototype);   // ① 新对象，__proto__ = Ctor.prototype（不走实例赋值）
  const ret = Ctor.apply(obj, args);           // ② 执行构造函数，this 绑到新对象
  return ret !== null && (typeof ret === 'object' || typeof ret === 'function')
    ? ret                                      // ③ 构造函数返回对象则以它为准（new 的特殊规则）
    : obj;
}
```

**四种继承与演进**（答出演进路径而不是背代码）：

```js
// 1) 原型链继承：共享 prototype → 改一个全变（属性串扰，最大缺陷）
Child.prototype = new Parent();
// 2) 借用构造：实例属性独立了，但方法还得复制一份（prototype 断了）
Parent.call(this);
// 3) 组合继承：以上两者叠加 → 调用两次 Parent（优化点）
// 4) ES6 class extends（寄生组合，Object.setPrototypeOf 接链）——现代标准答案
class Child extends Parent { constructor(x) { super(x); } }
//   拓展：Object.create(Parent.prototype) + Parent.call(this) = 手写版寄生组合，几乎等价
```

**把上面的代码讲清楚**

- **原型链是什么**：每个对象都有一个隐藏的"上级"（内部槽 `[[Prototype]]`，日常用 `__proto__` 访问）——自己身上找不到的属性/方法，就去"上级"身上找，还没有就再往上找，直到 `null` 为止。`p.toString()` 能调用：p 自己没有 → 找 `Person.prototype` 没有 → 再找到 `Object.prototype`（toString 在这）→ 执行。这条"往上级找"的链就是原型链；
- **三者的关系**（配上面 ①②③ 三行验证）：`new Person()` 造出的对象，其"上级"就是 `Person.prototype`（①）；`prototype` 上挂着一个 `constructor` 指回构造函数本身（②）；`__proto__` 是"访问上级"的非标叫法，标准写法是 `Object.getPrototypeOf`（③）；
- **prototype 和 __proto__ 怎么区分**（最易混）：**`prototype` 是函数才有的属性**——表示"用我 new 出来的对象，上级是谁"；**`__proto__` 是每个对象都有的**——表示"我的上级是谁"。一句话：prototype 是"爹准备的族谱模板"，`__proto__` 是"娃指向族谱的指针"。

**手写 new 的四步**（逐行）：① 造一个空对象、把它和 `Ctor.prototype` 接起来（`Object.create`）；② 让构造函数以这个空对象为 this 执行（`apply`）；③ 特例——构造函数**如果返回了一个对象**，就以它为准；④ 否则返回新对象。

**四种继承为什么这样演进**（每一版都在修上一版的坑，答"演进史"比背代码得分高）：
1. **原型链继承**：`Child.prototype = new Parent()`——链通了，但 Parent 的**引用属性挂在原型上、被所有实例共享**（改一个全变）；
2. **借用构造**：`Parent.call(this)`——属性独立了，但 Parent 原型上的方法没继承到，方法得复制；
3. **组合继承**：1+2 叠加——能力齐了，但 Parent 被调用了两次（一次造原型、一次造实例），有浪费；
4. **寄生组合**（现代标准）：`Object.create(Parent.prototype)` + `Parent.call(this)`——只调一次、链完整、方法复用。ES6 的 `class Child extends Parent` 就是它的语法糖。

**面试怎么答**：先讲"找属性沿链找"的机制 + 三者关系 → 手写 new 四步 → 继承当"修改史"讲。

**延伸追问（同一知识面）**
- `class` 和构造函数的差异：class 不会提升（先声明后使用）、必须 new 调用、方法不可枚举、默认严格模式；
- `Object.create(null)`：造一个没有原型的"纯字典"——存用户可控的键名时防原型污染；
- `instanceof` 原理 = 沿 `__proto__` 链找 `Ctor.prototype`（Q4 有手写）；跨 iframe 时两边 `Object.prototype` 不是同一个，会失效。

## Q11. `this` 指向规则 + 手写 bind

```js
// 四条规则（优先级从高到低）：
// ① new 调用 → this = 新建对象（bind/call 对 new 无效，被 new 压制）
// ② call/apply/bind 显式指定 → this = 指定对象
// ③ 对象方法调用 obj.fn() → this = obj
// ④ 默认：严格模式 undefined / 非严格全局对象（箭头函数：永远取定义时外层的 this）

// 手写 bind（返回绑定函数，可配合 new）
Function.prototype.myBind = function (ctx, ...args) {
  const self = this;
  function bound(...rest) {
    // new 调用时 this 指向新对象 → 忽略绑定的 ctx，走原构造逻辑
    return self.apply(this instanceof bound ? this : ctx, [...args, ...rest]);
  }
  bound.prototype = Object.create(this.prototype);   // 保留原型链（配合 new）
  return bound;
};

// 面试输出题
const obj = { name: 'a', hello() { console.log(this.name); } };
const f = obj.hello;
f();                         // undefined（丢失 this → 严格模式报错）
const g = obj.hello.bind({ name: 'b' });
g();                         // 'b'
setTimeout(obj.hello, 10);   // undefined / window —— 回调丢 this 的经典场景
setTimeout(() => obj.hello(), 10);  // 'a' —— 箭头函数保住词法 this
```

**先讲清楚基础：this 是什么、由谁决定**

`this` 是函数执行时的"**当前操作对象**"——它不由函数定义决定，而是**由调用方式决定**。同一个函数，调用方式不同，this 完全不同。上面四行注释就是全部规则，从高到低：

1. **new 调用**（`new Fn()`）：this = 新建出来的那个对象；
2. **显式指定**（`fn.call(obj)` / `fn.apply(obj)` / `fn.bind(obj)`）：this = 你指定的对象；
3. **对象方法调用**（`obj.fn()`）：this = 点号前面的对象；
4. **裸调用**（`fn()`）：严格模式下 this = `undefined`；非严格 = 全局对象（浏览器 window）。

口诀：**new > bind > 点 > 裸**。为什么 `const f = obj.hello; f()` 就丢了 this？——因为**脱离了"点号调用"的形态**：规则 3 没命中，落到规则 4。

**箭头函数**：没有自己的 this——它内部的 this"焊死"在**定义时**外层作用域的 this 上（不参与上面四条规则，call/bind 也改不动）。这就是 `setTimeout(() => obj.hello(), 10)` 能保住 this 的原因；它也不能当构造函数（没有 prototype、不能 new）。

**手写 bind 逐行**：
- `bind(ctx, ...args)`：不立即执行，返回一个"预置好 this 的新函数"；args 是预置参数（柯里化）；
- `bound` 里的 `this instanceof bound` 判断：处理"绑定后的函数还被 new"的场景——此时应该走构造函数那套逻辑（this = 新对象），**忽略绑定的 ctx**（new 优先级最高，符合规则 1）；
- `bound.prototype = Object.create(this.prototype)`：保住原型链，让 `new bound()` 出来的对象也能 instanceof 原构造函数。

**面试怎么答**：口诀"new > bind > 点 > 裸"→ 对输出题现场推（f() 丢、g() 绑住、setTimeout 裸传回调丢、箭头包一层保住）→ bind 手写讲"预置 this + 处理 new 特例"。

**延伸追问（同一知识面）**
- 为什么 `setTimeout(obj.hello)` 丢？——回调被内部"裸调用"，不是 `obj.hello()` 的形态；
- call/apply/bind 区别：call 挨个传参、apply 传数组、bind 不执行只返回新函数；
- Vue/React 里为什么 this 总出问题？——事件回调/异步回调被"提取"成了裸调用；Vue3 setup 里用箭头函数或直接闭包调用，天然没有这个问题。

## Q12. 手写深拷贝（含循环引用与特殊类型）

```js
function deepClone(x, seen = new WeakMap()) {
  if (x === null || typeof x !== 'object') return x;      // 原始值直接返回
  if (x instanceof Date)  return new Date(x);
  if (x instanceof RegExp) return new RegExp(x);
  if (seen.has(x)) return seen.get(x);                    // ① 循环引用：a.b = b → 否则栈溢出
  const res = Array.isArray(x) ? [] : {};
  seen.set(x, res);                                       //    进栈前登记
  for (const k of Reflect.ownKeys(x)) {                   // ② 含 Symbol 键（普通 for..in 漏）
    res[k] = deepClone(x[k], seen);                       // ③ 可枚举描述符做了简化
  }
  return res;
}
```

**先讲清楚基础："浅拷贝"和"深拷贝"差在哪**

对象里装的可能是别的对象的**引用**（地址）。拷贝时：
- **浅拷贝**（`{...obj}`、`Object.assign`）：只复制第一层——内层对象**还是同一个**（改内层互相影响）；
- **深拷贝**：递归地把每一层都复制成全新对象——怎么改都互不影响。

```js
const a = { list: [1, 2] };
const b = { ...a };          // 浅：b.list 和 a.list 是同一个数组
b.list.push(3);              // a.list 也变成了 [1, 2, 3]
```

**手写深拷贝逐行拆解**：
- 递归的尽头是"原始值"：`x === null || typeof x !== 'object'` 直接返回（**必须先判 null**——`typeof null === 'object'` 是 JS 著名陷阱）；
- 特殊类型特判：Date/RegExp 用构造新实例的方式复制（内部状态不能靠遍历复制）；
- **循环引用**：对象自己指向自己（`a.b = a`）时，天真递归会无限下钻到栈溢出——用 `seen`（原对象 → 克隆）登记"拷贝过了"，再次遇到直接返回已建的克隆（本质是"图遍历去重"）；
- `Reflect.ownKeys`：比 `for...in` 全——不漏 Symbol 键；
- `WeakMap` 存 seen：对象被回收后登记自动消失，不阻碍 GC。

**什么时候真的需要它**：不可变更新（改新对象触发框架更新）、把数据存到本地前防相互污染、函数入参防外部改动。

**面试怎么答**：先一句话区分浅/深（"改内层是否互相影响"）→ 手写要点（null 守卫、Date、WeakMap 防环）→ 追问时给三套现成方案的对比（见下）。

**延伸追问（同一知识面）**
- **`JSON.parse(JSON.stringify(x))` 丢什么**（高频）：函数、undefined、Symbol 丢（对象里消失、数组里变 null）；Date 变字符串；NaN/Infinity 变 null；循环引用直接抛错——"能背出丢什么"才算会用这招；
- **`structuredClone(x)`**（2022+ 浏览器原生）：支持循环引用/Map/Set/Date，但**不能克隆函数、DOM 节点；类实例会丢原型**（变普通对象）；
- 生产里通常直接用 lodash 的 `cloneDeep`（完备度最高），更快的替代是 `rfdc`。

## Q13. 事件模型：冒泡、捕获、事件委托

```js
// 捕获(top→target) → 目标 → 冒泡(target→top)，addEventListener 第三参控制哪阶段监听
list.addEventListener('click', (e) => {
  // 事件委托：不给每个 li 绑，监听容器 —— 动态新增子节点自动生效 + 监听器数量 O(1)
  const li = e.target.closest('li');            // ① target 是源头，closest 找最近祖先
  if (!li || !list.contains(li)) return;
  console.log('点了', li.dataset.id);
  // e.preventDefault();   // 阻止默认行为（表单提交、a 跳转）
  // e.stopPropagation();  // 阻止冒泡（局部逻辑不外泄）；捕获阶段要用 stopImmediatePropagation
}, false);                                       // true=捕获阶段
```

**先讲清楚基础：事件是怎么"流动"的**

点一下按钮，浏览器内部的动作：产生一个事件对象，**从顶层往下传**到目标元素（**捕获阶段**）→ 在目标身上触发（**目标阶段**）→ 再**从目标往上冒**回顶层（**冒泡阶段**）。`addEventListener(type, fn, useCapture)` 的第三参决定监听哪个阶段：默认 false 监听冒泡、true 监听捕获。

（为什么设计成两段？历史原因：Netscape 主张捕获、IE 主张冒泡，后来标准把两条路都保留了下来。捕获到今天也有实用场景——在顶层"拦截"，对不冒泡的事件同样有效。）

**事件委托是什么**：不给每个 `li` 单独绑监听器，而是**在共同父容器上绑一个**——冒泡机制保证"任何 li 被点，父容器都会收到"，然后用 `e.target`（真正被点的元素）定位。上面代码用 `closest('li')` 从被点元素往上找最近的 li。两大收益：

1. **性能**：监听器从 N 个变 1 个；
2. **动态列表自动生效**：新增的 li 无需重新绑定（v-for 渲染的列表同理，框架内自动代理）。

**几个必须分清的方法**：
- `e.target`（事件**源头**，最初被点的那个元素）vs `e.currentTarget`（**监听器绑在谁身上**，也等于回调里的 this）——委托题必问；
- `e.preventDefault()`：阻止**默认行为**（a 跳转、表单提交）；
- `e.stopPropagation()`：阻止**冒泡**（父容器/上层不再收到）；`stopImmediatePropagation` 更狠——同元素上后续监听器也不执行。

**面试怎么答**：三阶段一句话（捕获→目标→冒泡）→ 委托"绑父不绑子 + e.target 定位 + 两大收益"→ 区分 preventDefault / stopPropagation 的语义。

**延伸追问（同一知识面）**
- 哪些事件不冒泡？——focus/blur、mouseenter/leave（冒泡版是 focusin/focusout、mouseover/out）；
- `{ passive: true }`：声明"我不会 preventDefault"——浏览器不必等 JS 执行，滚动立即响应（移动端滚动优化的关键）；
- React 的合成事件也是"极致委托"（17 前挂 document、17+ 挂根容器）——原理与本节相同，顺带能提。

## Q14. 回流与重绘：怎么让页面不卡？

```js
// 读写分离：交错读写 → 强制同步回流（每写一次就渲染一次）
// ❌ bad
els.forEach((el) => { el.style.height = el.scrollHeight + 'px'; });
// ✅ good：先批量读，再批量写
const h = els.map((el) => el.scrollHeight);
els.forEach((el, i) => { el.style.height = h[i] + 'px'; });

// 批量写用 rAF 合并到下一帧（本项目瀑布 scheduleRelayout 同款）
requestAnimationFrame(() => { /* 所有样式变更集中在这里 */ });
```

**先讲清楚基础：浏览器怎么把网页画出来**

一次渲染大致五步：**JS 改样式 → 样式计算（Style）→ 布局（Layout：算每个盒子的位置大小）→ 绘制（Paint：画像素）→ 合成（Composite：拼图层上屏）**。优化就是想清楚"操作会让哪几步重跑"：

- **回流（Reflow ≈ Layout）**：元素**几何**变了（宽高、位置、增删节点）——重新算布局，代价高，可能牵一发动全身（父容器、兄弟节点跟着动）；
- **重绘（Repaint ≈ Paint）**：几何没变、只是**外观**变了（颜色、背景）——只重画像素，代价低；
- 只改 `transform/opacity` 更高一等：**只做合成**（Composite）——动画首选它俩的原因。

**上面代码的 bad/good 就是这个坑**：**读布局属性也会触发回流**——`el.offsetHeight` / `scrollTop` / `getBoundingClientRect()` 要求"给我最新准确的数"，若前面有未应用的样式改动，浏览器只能**立刻同步做一次布局**再回答（"强制同步布局"）。交错读写 → 每轮循环都"写→强制布局→读"，性能杀手；批量读再批量写 → 只布局一次。

**常用优化手段**（对应"减少哪一步"）：① 批量读写分离（少布局次数）；② `transform/opacity` 做动画（跳过布局与绘制）；③ `DocumentFragment` 一次性插入批量节点（少 DOM 变更）；④ 长列表**虚拟滚动**（只渲染可视区，减少总渲染量）；⑤ `will-change` 提前升为独立合成层（用完移除，图层过多吃显存）。

**面试怎么答**：渲染五步 → 回流/重绘区别（几何 vs 外观）→ 三板斧"读写分离 + transform/opacity 动画 + 虚拟滚动"→ 主动点出"读 offsetHeight 也会触发回流"。

**延伸追问（同一知识面）**
- 为什么 rAF 里改样式更稳？——回调对齐"下一帧渲染之前"（见 Q1 的调度时机），改动在同一帧生效；
- `visibility: hidden` vs `display: none`：前者仍占位（只重绘）、后者移除布局（回流）；
- DevTools 怎么排查：Performance 面板录制看 Layout（紫条）频率；Rendering 面板开 "Paint flashing" 看哪些区域在重绘。
